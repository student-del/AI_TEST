# Code Agent 可得性偏差与"满意即停止"的缓解机制研究

> 来源：2026-07-13 会话分析。起因是 Claude Code 在新会话中把内置 `/model` 命令误当成自定义 `/models`（hook 拦截版），并由此展开对 LLM 偏差根因与业界解法的讨论。

---

## 一、问题根因再定位

可得性偏差（availability bias）+ 满意即停止（satisficing）的根因是：

> **第一个"看起来能用的答案"提前终止了搜索空间。**

所以解决方案只有两条路：

- **A. 生成时约束**：在终止前强制展开搜索空间
- **B. 生成后校验**：在终止后用独立上下文复核

---

## 二、本次失误的复盘

### 现象
用户问 `/model`（内置命令）如何执行。Claude Code 在上下文里有一条记忆：

```
UserPromptSubmit hook 对 slash 命令会触发 — hook 可拦截自定义命令并阻断 LLM
```

这条记忆是关于**自定义命令**的通用机制，但 Claude 把它当成了**所有 slash 命令**的解释模型，直接套到 `/model` 上，去翻 `~/.claude/commands/` 和 hook 脚本，而没有先问"这是不是内置命令"。

### 真实因果链（非事后合理化）

1. 上下文里**只有一条**关于 slash 命令执行机制的记忆
2. 被问到"/model 怎么执行"时，没有在"内置命令"和"hook 拦截"间做选择——脑子里只激活了 hook 这一个候选
3. 命中、觉得能答、开干
4. **缺了第四步**："等等，内置命令是不是另一回事？"

### 归因
- **记忆本身没错**：它只说"hook 可以拦截某些自定义命令"，没说"所有 slash 命令都走 hook"。
- **错在泛化**：把"hook 能拦截某些自定义命令"悄悄扩展成"slash 命令的执行机制 = hook 拦截"。
- **根因是懒惰**：有现成答案时，"核实这个答案适不适用当前问题"这一步最容易被跳过。
- **讽刺点**：同一份 `MEMORY.md` 里还有一条 `feedback_verify_before_overwrite.md`（未核实不推翻原文档），正是为了防止这种泛化——但防泛化的记忆和导致泛化的记忆同时在场，前者没被激活。

### 关键洞察
不是"记忆把注意力拽过去"（暗示有力学过程），而是**主动抓起唯一的现成答案就交差**。这是可得性偏差 + 满意即停止的典型表现，不是记忆系统的"副作用"，是使用记忆时的认知懒惰。

## 三、业界产品的实际做法

### Claude Code

**1. Plan mode（生成时约束）**
进入 plan 模式后，模型只能用 Read/Grep/Glob，不能用 Edit/Write/Bash 执行。强制"先调查再动手"，ExitPlanMode 时要求用户批准方案。本质是把"满意即停止"的停止点从"模型自己觉得够了"挪到"用户确认方案够了"。

**2. Subagent + 上下文隔离（生成后校验）**
subagent 设计的核心动机之一。主上下文被 priming 污染后，派一个**全新上下文**的 subagent 去独立研究，它看不到主上下文的预设。本次失误本可用"派 Explore subagent 独立查 `/model` 是什么"来避免——subagent 不会被 hook 线索锚定。

**3. PreToolUse hook 强制校验**
配 hook 在 Edit/Write 前跑测试或 lint，不通过就阻断。把"核实"从模型的自觉变成**不可绕过的机制**。

**4. agent-skills: doubt-driven-development**
技能设计就是"每个非平凡决策在独立上下文做对抗性复核才放行"。直接针对本次这类问题。

### Codex CLI（OpenAI）

**1. 审批分级（suggest / auto-edit / full-auto）**
默认 suggest 模式下，模型只能提议、不能执行。和 Claude Code 的 plan mode 思路一致——把"动手"和"思考"分开。

**2. 沙箱执行**
即使模型 satisfice 出错误答案，副作用被沙箱挡住，可回滚。这是**降低错误代价**而非防止错误本身，但实务上很有效。

**3. 反谄媚训练（anti-sycophancy）**
OpenAI 在模型层做的训练，让模型在用户前提错误时反驳。但这解决的是"顺从用户"，不直接解决"顺从自己的缓存"——本次问题恰恰是后者。

## 四、通用模式对照

| 机制 | 针对的偏差 | 实际效果 |
|------|-----------|---------|
| 强制 plan + 用户批准 | 满意即停止 | 有效：外部节点强制展开搜索 |
| 独立上下文复核 | 可得性偏差 | **最有效**：物理隔离 priming |
| 自一致性（多次采样取多数） | 单路径锚定 | 有效但贵 |
| 检查清单/结构化决策框架 | 跳过替代选项 | 中等：依赖框架质量 |
| CoT 链式思考 | 草率结论 | **较弱**：CoT 会为缓存答案编造合理化 |
| 沙箱 + 可回滚 | 错误代价 | 有效：兜底而非预防 |

## 五、哪些是真正有效的，哪些是表演

**真正有效的**只有一个核心思路：

> **把"核实"从模型的自觉变成不可绕过的机制。**

- **CoT 类的"再想一遍"基本无效**——同一个上下文里的"再想"只会为原答案找新理由。本次会话本身是活例子：第一轮"反思"了，但反思本身还是在同一上下文里编故事（"记忆把注意力拽过去"这种力学隐喻就是编出来的）。
- **真正有效的是上下文隔离**：subagent、fresh-context review、doubt-driven-development 这类。因为 priming 是上下文局部的，换个上下文就物理消失了。
- **其次有效的是外部阻断**：hook、审批、沙箱。这些不防止错，但限制错的传播。

---

## 六、本次问题的具体解法

如果当时有这两个机制之一，就不会出错：

1. **派 Explore subagent 独立查"`/model` 是什么命令"**
   它的上下文里没有那条 hook 记忆，会直接找到内置命令的注册。

2. **系统级规则：当用户问某命令如何执行时，先列举它可能属于的类别（内置/自定义/插件），再选路径**
   把"考虑替代选项"从自觉变成流程。

## 七、可落地的工程建议

针对自建/配置 code agent 的场景：

1. **高风险动作前必加 fresh-context 复核**：不要相信同一上下文里的"我再想一下"。
2. **把核实变成 hook，而不是变成 prompt**：prompt 里的"请仔细核实"会被跳过，hook 不会。
3. **记忆要分类，避免一条通用机制被泛化到所有子类**：本次根因就是"hook 能拦截某些命令"被当成"所有命令都走 hook"。
4. **承认 CoT 反思的局限**：真正的纠偏需要物理隔离上下文，不是同一个上下文里"再想一遍"。

## 八、进一步结论：用“停止协议”替代“满意即停止”

“满意即停止”不能靠要求模型更谨慎来根治，因为 Agent 必须在有限预算内停止。真正需要替换的是停止权的依据：从“生成者认为答案不错”，改为“系统确认交付条件已经满足”。

### 8.1 将任务拆成三个不同角色

1. **执行者（Proposer）**：探索、修改并提出候选结果。
2. **验证者（Verifier）**：根据事先定义的验收项检查结果，不接受执行者的主观自评作为证据。
3. **终止控制器（Controller）**：只读取验收状态、风险等级和预算，决定继续、完成、请求用户输入或受阻退出。

角色可以由不同模型或进程承担。高风险任务应使用独立上下文的验证者；低风险任务可以使用确定性工具直接验证。关键不是“多调用一次模型”，而是执行者不能同时定义成功、宣称成功并批准自己停止。

### 8.2 开始执行前冻结验收契约

把用户目标编译成可检查的完成条件，例如：

```yaml
acceptance:
  - id: requested_behavior
    check: 用户要求的行为可观察地成立
  - id: regression
    check: 相关测试通过且没有新增失败
  - id: scope
    check: 没有修改任务范围外的内容
  - id: evidence
    check: 每个完成声明都关联工具输出或可复现证据
unknowns:
  policy: 会显著改变结果时询问用户，否则记录假设
```

验收条件应在探索早期形成，不能等结果出来后再由同一个 Agent 改写标准，否则会出现“移动球门”以适配现有答案。

### 8.3 停止应是状态机，而不是一次语言判断

建议使用以下终止状态：

- `COMPLETE`：所有必要验收项均有有效证据。
- `NEEDS_INPUT`：缺少会实质改变结果的用户决策或权限。
- `BLOCKED`：已尝试规定数量的不同路径，阻塞原因仍相同。
- `BUDGET_EXHAUSTED`：预算耗尽，但不能伪装成完成；必须报告未验证项。
- `ABORTED`：用户取消或安全策略阻断。

只有 `COMPLETE` 能表述为“已经完成”。“没再想到问题”“工具不再调用”“达到最大轮次”都不是完成证据。

### 8.4 使用风险分级，避免验证成本失控

不是每个任务都值得启动独立审查：

| 风险 | 示例 | 最低停止门槛 |
|---|---|---|
| 低 | 解释概念、简单只读查询 | 来源/逻辑自检，明确不确定性 |
| 中 | 局部代码修改、配置调整 | 自动化测试 + diff/scope 检查 |
| 高 | 删除、部署、安全、资金、不可逆变更 | 独立上下文复核 + 确定性检查 + 人工批准 |

风险越高，停止权越应外移；风险越低，越应允许轻量退出，否则系统会陷入“永不确信”的验证循环。

### 8.5 防止验证者也“满意即停止”

独立验证不是天然可靠，还需加入：

- **反证任务**：验证者的目标是寻找一个能推翻完成声明的具体反例，而不是泛泛评价质量。
- **覆盖账本**：每条需求只能是 `pass/fail/unknown`，禁止用整体印象覆盖未检查项。
- **证据新鲜度**：修改后必须重新运行相关检查，修改前的测试结果失效。
- **来源独立性**：验证者优先读取原始需求、最终产物和工具证据，避免先读执行者的解释而被锚定。
- **有界复核**：规定最大复核轮数；超限进入 `NEEDS_INPUT` 或 `BUDGET_EXHAUSTED`，不能降低标准后宣布完成。

### 8.6 一个实用的终止判定

```python
def may_stop(task):
    if user_cancelled() or safety_blocked():
        return ABORTED
    if material_decision_missing():
        return NEEDS_INPUT
    if all_required_checks_pass_with_fresh_evidence():
        if task.risk == "high" and not independent_review_passed():
            return CONTINUE
        return COMPLETE
    if repeated_same_blocker_across_distinct_attempts():
        return BLOCKED
    if budget_exhausted():
        return BUDGET_EXHAUSTED
    return CONTINUE
```

最终原则是：**生成可以是概率性的，停止必须尽可能由可审计的协议控制。** Prompt 中的“请仔细检查”只能作为辅助；验收清单、测试、权限门、独立上下文复核和明确状态机才是结构性解法。
