# LLM 输出约束机制与方案概览

> 涵盖约束解码的原理、多方案对比及选型指南。

---

## 一、核心问题

LLM 的输出是自由文本。如何让它严格按 JSON 格式输出？

三种方法，可靠性递增：

| 方法 | 可靠性 | 原理 |
|------|--------|------|
| 提示词 | 低 | prompt 中写"请输出 JSON"，模型可能出错 |
| JSON Mode | 中 | `response_format: { type: "json_object" }`，保证合法 JSON，不保证结构 |
| Structured Outputs / Tool Use | **100%** | 传入 JSON Schema，API 层面 token 级约束 |

---

## 二、为什么响应天然遵守格式

### 外壳是 API 服务器拼装的，不是模型生成的

```
┌──────────────────────────────────────────────────┐
│  API 服务器（确定性的 C++/Rust/Go 代码）          │
│                                                  │
│  {                                               │
│    "id": "chatcmpl-xxx",       ← 服务器生成      │
│    "choices": [{ message: {    ← 服务器拼装      │
│      "role": "assistant",      ← 服务器写死      │
│      "content": null,          ← 服务器置空      │
│      "tool_calls": [{          ← 服务器解析后组装 │
│        "id": "call_abc123",    ← 服务器生成      │
│        "type": "function",     ← 服务器写死      │
│        "function": {           ← 服务器拼装      │
│          "name": "Read",       ← 模型输出的       │
│          "arguments": "{...}"  ← 模型输出的       │
│        }                       │                │
│      }]                        │                │
│    }]}                         │                │
│  }                             │                │
└──────────────────────────────────────────────────┘

模型实际只生成两段内容:
  <tool_call_start>Read{"file_path": "E:/AI_TEST/CLAUDE.md"}<tool_call_end>
  → 服务器解析出工具名 Read
  → 服务器解析出参数 {"file_path": "..."}
  → 其他所有外壳字段都是服务器代码写死的
```

### Anthropic 原生格式更进一步

```javascript
// Anthropic API: tool_use.input 直接就是 dict
response.content[1].input  // { "file_path": "..." }  不需要 json.loads

// OpenAI 兼容格式: arguments 是 JSON 字符串
response.choices[0].message.tool_calls[0].function.arguments  // '{"file_path":"..."}'  需要 json.loads
```

Claude Code 用的是 Anthropic 原生格式，不需要 `json.loads`——`tool_use.input` 天然就是结构化对象。

### 这也解释了为什么 tool_calls 模式比纯 prompt 可靠

| | 纯 prompt "Return JSON" | tool_calls 模式 |
|---|---|---|
| content 字段 | 模型自由生成，可能有前言/注脚 | 服务器置为 null |
| 结构化数据 | 混在 text 里，需要正则提取 | 独立在 `arguments` 字段中 |
| 可靠性 | 80-90% | 90-95%（+ 约束解码 = 100%） |

结论：**外壳 100% 遵守格式是因为它是服务器代码拼装的，不是模型生成的。模型只生成填充进外壳的内容，而内容的可靠性取决于约束解码。**

## 三、约束解码原理

```
模型前向推理 → 输出 100,000 个 token 的 logit 分数
       ↓
约束引擎计算 → 根据 JSON Schema，当前只有 ~20 个 token 合法
       ↓
施加掩码     → 其余 token 的 logit = -∞，概率 = 0
       ↓
采样         → 模型只能从合法 token 中选择
```

**两层保证**：
- **模型层**（概率性）：训练/RLHF 阶段学会了看到 tools 参数输出 tool_use 块
- **API 服务器层**（确定性）：约束解码在每一步 token 采样时，非法 token 的数学概率强制为 0

关键优化：
| 优化 | 说明 |
|------|------|
| 上下文无关预计算 | 99% token 编译时固化到查找表，O(1) 查表 |
| 上下文相关运行时检查 | 1% 结构字符需要栈深度判断 |
| 语法缓存 | 编译后的语法缓存 24 小时 |
| 总开销 | 仅 1-3% 生成延迟 |

## 四、方案全景

所有方案分三层：

```
可靠性
  ↑ 100%  ┌──────────────────────────────────────┐
  │       │  约束解码（Token 级强制）              │
  │       │  ├ API 原生: Anthropic/OpenAI/Gemini   │
  │       │  ├ FSM:     Outlines                   │
  │       │  ├ PDA:     XGrammar / Guidance        │
  │       │  └ 字符级:  LM Format Enforcer         │
  │ 95%   ┌─────────────────────┐                  │
  │       │  事后校验 + 重试     │                  │
  │ 82%   ┌──────────────┐      │                  │
  │       │  提示词工程    │      │                  │
  └─────────────────────────────────────→ 工程复杂度
```

### 各方案对比

| 方案 | 格式保证 | 语义质量 | 工程复杂度 | 适用 |
|------|---------|---------|-----------|------|
| 提示词 | 82-95% | 最高 | 零 | 原型 |
| 校验+重试 | 有上限 | 可能降 | 低 | 黑盒 API |
| API 原生约束 | **100%** | 最优 | 零 | 生产首选 |
| Outlines(FSM) | 100% | 质量税 5-20% | 中 | 简单 Schema |
| XGrammar(PDA) | 100% | 质量税 5-20% | 中 | 复杂嵌套 |
| LMFE(字符级) | 100% | 零样本最佳 | 高 | 零样本 |

### 性能对比

| 框架 | 效率 | Schema 覆盖 | 质量 |
|------|------|------------|------|
| Anthropic Tool Use | 服务端 | 宽 | **最佳** |
| OpenAI strict | 服务端 | 宽 | **最佳** |
| Guidance | 快 | **最广** | 好 |
| XGrammar | **最快** | 好 | 中等 |
| Outlines | 慢 | 广 | 好 |
| llama.cpp | 中等 | 中等 | 中等 |

### 子方案详解

**API 原生**：Anthropic/OpenAI/Gemini，服务端约束解码，质量最优但封闭、成本高。

**FSM 方案（Outlines）**：初始化一次性遍历词汇表构建"FSM 状态→合法 Token"映射，推理时 O(1) 查表。缺点是深层嵌套会 DFA 状态爆炸。详见 `02_FSM约束解码详解.md`。

**PDA 方案（XGrammar/Guidance）**：下推自动机 + 栈，自然处理嵌套，vLLM 默认后端。比 FSM 快 ~100x。

**字符级方案（LMFE）**：token 展开为字符序列判断。零样本幻觉率最低（8.9%），但计算开销大。

## 五、质量税问题

所有约束解码方案都会导致语义质量下降 5-20%：
- **枚举塌陷**：模型倾向安全的枚举值
- **数值漂移**：未提及的数值字段倾向填语料均值
- **可选字段跳过**：把可选字段当作零成本跳过

缓解：推理/CoT 不约束，只在最终输出约束；用更强的基座模型。

## 七、国产模型的现状

国产模型在约束解码上明显滞后，大部分不是真正的 token 级约束：

| 模型 | 约束解码 | 实际机制 |
|------|---------|---------|
| Anthropic Claude | ✅ 原生 | 服务端约束解码，100% |
| OpenAI GPT | ✅ 原生 | `strict: true`，100% |
| DeepSeek V3.2 | ⚠️ Beta | `strict: true` 有 bug |
| DeepSeek V4 | ❌ | `tool_choice="required"` 报 400 |
| Qwen API | ❌ | `response_format: {type:"json_object"}`，只保证外层 |
| Qwen3 开源 | ❌ | 纯提示词驱动，~80% |

### DeepSeek 的 provide_answer 模式

DeepSeek 没有 `response_format: {type:"json_schema"}`，但有 `tools`。于是把想要的 Schema 伪装成一个工具。

核心思路：**定义假工具 `provide_answer`，强制模型调用它来"交卷"，从 `tool_calls` 中提取结构化结果。**

```python
# Step 1: 把 JSON Schema 包装成工具
tools = [{
    "type": "function",
    "function": {
        "name": "provide_answer",
        "parameters": {  # ← 这里就是你的 JSON Schema
            "type": "object",
            "properties": {
                "name": {"type": "string", "description": "姓名"},
                "age":  {"type": "integer", "description": "年龄"}
            },
            "required": ["name", "age"]
        }
    }
}]

# Step 2: 强制调用
response = client.chat.completions.create(
    model="deepseek-chat",
    messages=[{"role": "user", "content": "张三，25岁"}],
    tools=tools,
    tool_choice={"type": "function", "function": {"name": "provide_answer"}}  # 强制
)

# Step 3: 从 tool_call 提取结果
result = json.loads(response.choices[0].message.tool_calls[0].function.arguments)
# {"name": "张三", "age": 25}
```

**为什么比纯提示词强**：

| | 提示词 "Return JSON" | provide_answer 模式 |
|---|---|---|
| 输出通道 | `message.content`（自由文本） | `tool_calls[0].function.arguments`（结构化） |
| 随机加前言 | 常见："好的，结果如下：\n{...}" | 不会 |
| Schema 引导 | 无 | API 根据 `parameters` 做一定约束 |
| 可靠程度 | 80-90% | 90-95% |

**局限**：不是真正的约束解码——DeepSeek 的 `parameters` 校验远不如 Anthropic/OpenAI。V4 默认 thinking 模式下 `tool_choice="required"` 直接报 400（~40% 请求回退到自由文本）。生产环境必须搭配 `jsonrepair` + Schema 校验 + 3-5 次重试。

### 唯一例外：本地部署 + 推理引擎

当 DeepSeek/Qwen 开源模型本地部署在 vLLM/SGLang 上时，可通过推理引擎的 xgrammar/guidance 后端实现真正的约束解码。但这与模型本身无关——是引擎层补齐的能力。

```python
llm = LLM(model="deepseek-ai/DeepSeek-V3")
params = SamplingParams(guided_decoding=GuidedDecodingParams(json=schema))
# 此时才是真正的 token 级约束
```
