# 长文本如何结构化生成并绑定证据

## 核心结论

结构化生成不是要求模型把参考文献原文直接拼接起来，也不是要求最终用户只能看到 JSON。结构化的是答案的 **中间表示**：模型自己撰写的 claim、claim 使用的证据、段落结构及引用位置。

```text
多篇证据原文
  -> 模型综合为结构化 claim
  -> claim 逐项验证
  -> 按段落结构渲染为自然语言长文本
```

最终长文本仍可以是流畅的综合、解释和归纳；只是其中每个可验证事实都能反向定位到证据。

## 一、证据和 claim 不是复制关系

假设检索到两段证据：

```text
e1：本规则自2026年1月1日起施行。
e2：本规则适用于在本辖区登记并开展支付服务的机构。
```

模型可以自己综合成：

```text
该规则于2026年初生效，适用对象是在本辖区登记并提供支付服务的机构。
```

这句话不是原文拼接，而包含两个 claim：

```text
c1：该规则于2026年初生效。       <- e1
c2：该规则适用于本辖区登记并提供支付服务的机构。 <- e2
```

验证器判断的是 `e1 -> c1`、`e2 -> c2` 是否成立，而不是检查输出是否逐字复制原文。

## 二、推荐方式：先生成答案计划和 claim

模型先不输出最终散文，而输出结构化中间表示：

```json
{
  "title": "规则适用范围说明",
  "sections": [
    {
      "heading": "生效时间与适用对象",
      "paragraphs": [
        {
          "paragraph_id": "p1",
          "claims": [
            {
              "claim_id": "c1",
              "text": "该规则于2026年初生效。",
              "evidence_ids": ["e1"]
            },
            {
              "claim_id": "c2",
              "text": "适用对象是在本辖区登记并提供支付服务的机构。",
              "evidence_ids": ["e2"]
            }
          ]
        }
      ]
    }
  ]
}
```

这里的 `claim.text` 是模型自己生成的总结，不要求与证据逐字相同。

Schema 可以保证：

- 每个段落都有稳定 ID；
- 每个 claim 都有 `claim_id`；
- 每个可验证 claim 至少有一个 `evidence_id`；
- `evidence_id` 只能从本次检索集合中选择；
- 段落和 claim 的顺序能够被确定性还原。

## 三、逐项验证后再渲染

验证阶段：

```python
for section in answer_plan.sections:
    for paragraph in section.paragraphs:
        for claim in paragraph.claims:
            evidence = evidence_store.load(claim.evidence_ids)
            claim.verification = verify(claim.text, evidence)
```

得到：

```json
{
  "claim_id": "c1",
  "status": "pass",
  "supporting_spans": [
    {
      "evidence_id": "e1",
      "quote": "自2026年1月1日起施行"
    }
  ]
}
```

所有 claim 通过后，renderer 可以生成：

```markdown
## 生效时间与适用对象

该规则于2026年初生效 [1]，适用对象是在本辖区登记并提供支付服务的机构 [2]。
```

其中 `[1]` 和 `[2]` 由程序根据 `evidence_ids` 渲染，不让模型手工编写 URL 或脚注编号。

## 四、如何形成流畅段落

如果只是把 `claim.text` 用句号连接，段落可能比较生硬。可以采用三种方式。

### 方式 A：claim 本身写成可直接连接的句子

让模型在结构化阶段同时考虑段落上下文，使 claim 按阅读顺序自然衔接。渲染器只负责连接和插入引用。这种方式最容易保证引用边界。

### 方式 B：验证后做受控改写

```text
已验证 claim 列表
  -> 第二次模型调用进行衔接和去重复
  -> 重新拆 claim 并验证
  -> 输出最终段落
```

第二次模型调用可能增加新事实，所以改写后必须重新验证。提示词只能要求“不增加事实”，不能把它当作确定性保证。

### 方式 C：模板渲染

对法律、医疗、财务等固定报告使用模板：

```text
该规则于 {{effective_date}} 生效，适用于 {{applicable_subjects}}。
```

字段值由已验证 claim 填充。可读性灵活度较低，但可控性最高。

## 五、一个 claim 依赖多篇文献时怎么办

综合结论可能需要多条证据：

```json
{
  "claim_id": "c3",
  "text": "现有研究总体显示该干预可能降低短期风险，但长期效果仍不确定。",
  "evidence": [
    {
      "evidence_id": "paper-a#results",
      "role": "supports_short_term_benefit"
    },
    {
      "evidence_id": "paper-b#follow-up",
      "role": "supports_long_term_uncertainty"
    }
  ],
  "composition": "all"
}
```

这里应拆出两个子命题：

```text
c3.1：现有研究显示可能降低短期风险。 <- paper-a
c3.2：长期效果仍不确定。             <- paper-b
```

然后再允许它们组成一个复合句。`composition: all` 表示最终句子的完整含义需要所有证据共同支持。

若写成“多项研究一致证明长期有效”，验证器必须检查每项研究是否都支持“一致、证明、长期有效”这些强限定词，不能因为引用数量多就自动通过。

## 六、解释性文字如何处理

长答案不仅包含事实，还包含组织性语言：

```text
下面分三个方面说明。
换句话说，这里的关键区别在于适用对象。
综合来看，需要特别注意时间范围。
```

可以给每个片段标注类型：

```json
{
  "type": "transition",
  "text": "下面分三个方面说明。",
  "verifiable": false,
  "evidence_ids": []
}
```

常见类型包括：

- `factual_claim`：必须有证据；
- `inference`：必须显示推理所依赖的证据，并标明是推断；
- `recommendation`：需要规则依据或明确属于建议；
- `transition`：纯组织语言，可以无证据；
- `quotation`：必须保存精确原文和位置；
- `uncertainty`：说明证据不足或冲突。

这样不会错误地要求“下面分三点说明”也绑定文献，同时能防止模型把事实伪装成普通解释。

## 七、另一种方式：先生成长文本再标注

也可以让模型先输出自然语言和引用标记：

```text
该规则于2026年初生效 <cite:e1>，适用于本辖区登记的支付机构 <cite:e2>。
```

随后 parser 将它转换为：

```json
{
  "sentences": [
    {
      "text": "该规则于2026年初生效",
      "evidence_ids": ["e1"]
    },
    {
      "text": "适用于本辖区登记的支付机构",
      "evidence_ids": ["e2"]
    }
  ]
}
```

这种方式对通用聊天模型更容易，但可靠性较低：

- 一句话可能包含多个 claim，却只在句末放一个引用；
- 引用范围不明确；
- parser 很难判断引用支持前半句还是整句；
- 模型可能遗漏标记。

因此高风险系统更适合“先结构化 claim，后渲染长文本”。

## 八、长文本的推荐 Schema

```json
{
  "type": "object",
  "properties": {
    "sections": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "heading": {"type": "string"},
          "blocks": {
            "type": "array",
            "items": {
              "type": "object",
              "properties": {
                "block_type": {
                  "enum": [
                    "factual_claim",
                    "inference",
                    "transition",
                    "recommendation",
                    "uncertainty"
                  ]
                },
                "text": {"type": "string", "minLength": 1},
                "evidence_ids": {
                  "type": "array",
                  "items": {
                    "type": "string",
                    "enum": ["e1", "e2", "e3"]
                  }
                }
              },
              "required": ["block_type", "text", "evidence_ids"],
              "additionalProperties": false
            }
          }
        },
        "required": ["heading", "blocks"],
        "additionalProperties": false
      }
    }
  },
  "required": ["sections"],
  "additionalProperties": false
}
```

JSON Schema 本身不容易表达“当 `block_type=factual_claim` 时，`evidence_ids` 必须非空”的全部业务规则时，可以用 `if/then`，也可以在 Pydantic/Zod 的跨字段 validator 中实现。

## 九、完整工程流程

```python
evidence_store = retrieve_and_freeze_sources(question)

answer_plan = model.generate_structured(
    question=question,
    evidence=evidence_store,
    schema=ANSWER_PLAN_SCHEMA,
)

schema_validate(answer_plan)

for block in answer_plan.all_blocks():
    if block.block_type == "factual_claim":
        require_non_empty(block.evidence_ids)
        require_allowed_ids(block.evidence_ids, evidence_store)
        verify_entailment(block.text, evidence_store.load(block.evidence_ids))

    elif block.block_type == "inference":
        require_non_empty(block.evidence_ids)
        verify_inference_is_labeled_and_supported(block)

    elif block.block_type == "transition":
        reject_if_contains_verifiable_fact(block.text)

final_answer = render_markdown(answer_plan, evidence_store)
```

如果需要第二个模型把 blocks 润色成长段落，润色结果必须再次进入 claim 拆分与验证流程。

## 十、答案与证据之间的真正关系

```text
不是：答案文本 = 证据原文 A + 证据原文 B

而是：
证据 A ─支持─> claim 1 ┐
                       ├─组织/改写─> 最终段落
证据 B ─支持─> claim 2 ┘
```

强制溯源约束的是每条事实的支持关系，不是要求答案成为参考文献的复制品。
