# 强制溯源回答系统实现原理

## 核心结论

“回答必须强制溯源”不是单一模型能力，而是一套系统工程控制。模型只负责在证据范围内组织语言；系统负责确定可信来源、检索证据、绑定事实与引用、验证引用是否支持事实，以及在证据不足时拒答。

即使每句话都有引用，也不能由此推出答案绝对正确。引用可能真实但不支持该断言，来源本身可能有误，模型也可能把多个来源错误组合。高风险系统真正能够强制的是：**没有通过证据规则的内容不得发布**。

## 典型流水线

```text
用户问题
  -> 风险与问题分类
  -> 检索可信知识库或网络候选页面
  -> 打开原始网页/PDF，冻结原文和元数据
  -> 建立本次请求的 evidence store
  -> 生成“章节/段落 + 原子 claim + 证据 ID”中间结构
  -> JSON 解析与 Schema/类型校验
  -> 逐 claim 检查引用、蕴含、适用性、冲突和数值
  -> 只用通过验证的 claim 渲染自然语言答案
  -> 记录审计日志；失败则拒答或转人工
```

## 六层实现

### 1. 来源控制与检索

系统先定义允许引用的来源：法规官网、标准组织、同行评审论文、机构内部已批准文档等。证据记录需要保存 URL/文档号、发布机构、版本、发布日期、生效区间、抓取时间、内容哈希、段落或页码。

用户提问后，系统使用关键词检索、向量检索或二者混合召回候选片段，再做 rerank。RAG 的价值是把回答建立在显式的非参数知识库上，使知识可更新并提供出处，而不是只依赖模型参数中的模糊记忆。

对于网络检索，搜索结果摘要只能用于发现候选页面。系统必须打开原网页或 PDF、提取实际正文，并保存当时版本的原始快照或至少保存片段、抓取时间和哈希。

### 2. 证据存储与身份管理

验证不强制要求长期本地数据库，但要求生成器和验证器读取同一份冻结证据。证据层可以是单次请求内存、短期缓存，也可以是版本化数据库与对象存储。

```json
{
  "evidence_id": "web-17#section-4-p2",
  "url": "https://authority.example/rule-17",
  "retrieved_at": "2026-07-14T10:00:00+08:00",
  "section": "第四条",
  "text": "本规则自2026年1月1日起施行。",
  "content_hash": "sha256:..."
}
```

模型只能引用当前 evidence store 中存在的 ID。长期可审计系统还应保存原始网页/PDF，内容变化时创建新版本，不能覆盖历史证据。

### 3. 结构化生成与证据绑定

不要让模型直接输出最终散文，而是先生成受约束的中间结构。结构化的是模型自己归纳的 claim 和证据关系，不是把参考文献原文直接拼接：

```json
{
  "sections": [
    {
      "heading": "生效时间",
      "blocks": [
        {
          "block_type": "factual_claim",
          "claim_id": "c1",
          "text": "该规则于2026年初生效。",
          "evidence_ids": ["doc-17#p42"]
        }
      ]
    }
  ]
}
```

JSON Schema 可以声明必填字段、数组类型、`minItems` 和 evidence ID 枚举。提供商 strict Structured Output 或推理引擎的约束解码可以在 token 生成阶段限制格式；普通函数调用则仍可能需要生成后的本地校验。

完整的数据入口是：

```text
模型输出字符串
  -> JSON parser 转成对象
  -> Schema validator 检查结构和值
  -> 业务 validator 检查 ID、权限和状态
  -> 语义 validator 检查证据是否支持 claim
```

Schema 只能保证结构。例如一个合法 evidence ID 被填入 `evidence_ids`，不等于该证据支持 `claim.text`。

### 4. 逐项验证

验证器将答案拆成原子事实，为每个 claim 输出 `pass`、`fail` 或 `uncertain` 的结构化记录：

- **引用有效性**：文档存在、可访问、未撤回，版本与适用日期正确。
- **引用完整性**：所有可验证事实都有证据；不能只给段落末尾一个笼统引用。
- **引用正确性**：证据确实蕴含该事实，而不是仅主题相关。可用自然语言推断模型、第二个 LLM 或确定性规则验证。
- **证据质量**：来源是否属于当前领域的权威层级；一手来源优先于二手摘要。
- **冲突检测**：不同来源冲突时不得静默择一，应说明版本、辖区或时间差异。
- **数值与实体检查**：日期、金额、剂量、条款号可交给规则或程序重新计算、比对。

ALCE 将引用质量区分并评估为引用是否覆盖陈述及引用是否真正支持陈述；FActScore 则把长文本拆成原子事实，计算被可靠知识源支持的比例。这两类方法共同说明：只检查“有没有引用”远远不够。

高风险字段优先使用确定性程序，例如日期标准化、单位换算、条款号匹配和实体 ID 对齐。复杂语言关系才交给 NLI 模型或结构化输出的 LLM judge，并要求返回支持原文片段。

### 5. 长文本渲染

验证通过的 claim 按 `sections -> blocks -> claims` 顺序渲染为自然语言段落，引用编号和 URL 由程序根据 evidence ID 生成。

```text
证据 A ─支持─> claim 1 ┐
                       ├─组织和渲染─> 最终长文本
证据 B ─支持─> claim 2 ┘
```

过渡语可以标为 `transition` 而不引用；事实标为 `factual_claim` 并强制绑定证据；推断标为 `inference`，既绑定依据又明确说明它是推断。如果再使用第二个模型润色，润色结果必须重新拆 claim 并验证，防止新增事实。

### 6. 发布闸门与治理

最终答案由程序而非模型自行决定是否发布。例如：

```text
if source_not_allowlisted
   or unsupported_claim_count > 0
   or citation_coverage < 100%
   or critical_conflict_exists:
       refuse_or_escalate_to_human()
else:
       publish_with_citations()
```

高风险领域还需要保存问题、检索查询、原始文档版本、证据片段、模型与提示版本、验证结果，形成可复现的审计链。NIST AI RMF 将风险管理组织为 Govern、Map、Measure、Manage，并强调风险管理应贯穿系统生命周期；这说明溯源只是可信系统的一项控制，不是全部。

## 验证结果的推荐模型

不应只保存一个总分。每个 claim 应保存独立检查结果：

```json
{
  "claim_id": "c1",
  "criticality": "high",
  "status": "pass",
  "checks": {
    "reference_validity": "pass",
    "citation_completeness": "pass",
    "entailment": "pass",
    "source_quality": "pass",
    "applicability": "pass",
    "conflict": "pass",
    "numeric_entity": "pass"
  }
}
```

关键 claim 的单项失败不能被其他普通 claim 的高分抵消。发布策略应明确规定哪些失败直接拒答，哪些不确定性进入人工复核。

## 主流 Agent 框架中的落点

主流框架已经提供结构化输出入口：OpenAI Agents SDK 使用 `output_type`，LangChain 使用 `response_format`，Pydantic AI 使用 `output_type`，LlamaIndex 使用 `output_cls` 或 `structured_output_fn`。Python 常用 Pydantic，TypeScript 常用 Zod。

这些接口可以完成 Schema 生成、JSON 解析、本地类型验证以及部分失败重试，但不能自动完成来源真实性、适用性、claim-evidence 蕴含和冲突验证。后几项仍需业务验证节点实现。

## 什么叫“强制”

强度从低到高大致如下：

1. 提示词要求引用：模型仍可能编造文献，不能算强制。
2. 只允许引用检索结果中的文档 ID：杜绝虚构 ID，但仍可能错引。
3. 原子事实逐项绑定证据并做语义验证：能过滤大部分无依据陈述。
4. 白名单来源、版本管理、确定性校验、拒答阈值和人工复核：适合高风险场景。
5. 对关键结论不用生成模型裁决，而由规则引擎、数据库查询或专业人员签署：这是接近“绝对要求”时必要的架构。

因此，工程目标不应写成“保证模型永远正确”，而应写成可测试的约束，例如：关键事实 100% 有一手证据；证据不足时 100% 拒答；所有发布结果可复现；关键数值经过独立程序校验。

## 常见误区

- 给出 DOI、URL 或书名不等于引用真实；必须实际解析并确认内容。
- 搜索结果摘要不是稳定证据，应保存或链接原始文档及精确位置。
- 向量相似度只代表语义接近，不代表逻辑蕴含。
- 单一“裁判 LLM”也会犯错，关键规则应确定性校验，并抽样人工评估。
- 来源权威不等于适用于当前时间、地区和对象，必须管理元数据与适用范围。
- 引用只能提高可核查性，不能自动保证来源本身正确。
