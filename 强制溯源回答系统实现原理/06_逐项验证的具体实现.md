# 强制溯源回答中的逐项验证实现

## 核心结论

逐项验证不是调用一个 LLM 问“答案是否正确”，而是把最终答案拆成若干原子 claim，为每个 claim 建立独立验证记录，再由多个专用验证器依次检查。

```text
回答
  -> 原子 claim 列表
  -> claim 与 evidence ID 绑定
  -> 引用有效性检查
  -> 引用完整性检查
  -> 证据蕴含检查
  -> 来源质量与适用性检查
  -> 冲突检测
  -> 数值、日期和实体检查
  -> 聚合为发布 / 拒答 / 人工复核
```

验证器的输出必须是结构化记录，最终是否发布由确定性程序决定。

## 一、统一的数据结构

建议先把生成结果规范化为：

```json
{
  "claims": [
    {
      "claim_id": "c1",
      "text": "《示例条例》自 2026 年 1 月 1 日起施行。",
      "type": "effective_date",
      "evidence_ids": ["reg-2025-17#article-42"],
      "criticality": "high"
    }
  ]
}
```

证据库中的记录至少包含：

```json
{
  "evidence_id": "reg-2025-17#article-42",
  "document_id": "reg-2025-17",
  "title": "示例条例",
  "publisher": "示例监管机构",
  "document_type": "regulation",
  "version": "2025-12-01",
  "valid_from": "2026-01-01",
  "valid_to": null,
  "jurisdiction": "CN-example",
  "section": "第四十二条",
  "text": "本条例自2026年1月1日起施行。",
  "content_hash": "sha256:...",
  "retrieved_at": "2026-07-14T10:00:00+08:00"
}
```

每个验证器返回统一结果：

```json
{
  "validator": "entailment",
  "claim_id": "c1",
  "status": "pass",
  "score": 0.99,
  "reason_code": "DIRECT_SUPPORT",
  "details": "证据明确给出相同生效日期"
}
```

`status` 最好限制为 `pass`、`fail`、`uncertain`，不要只输出一个容易被误用的浮点分数。

## 二、Step 1：原子 claim 拆分

### 为什么先拆分

一句话可能包含多个事实：

```text
该条例由 A 机构发布，于 2026 年 1 月 1 日生效，并适用于所有金融机构。
```

实际包含至少三个 claim：

```text
c1：该条例由 A 机构发布。
c2：该条例于 2026 年 1 月 1 日生效。
c3：该条例适用于所有金融机构。
```

一个证据可能只支持 c1 和 c2，而不支持 c3。如果整句只做一次判断，容易把部分支持误判成全部支持。

### 实现方式

可以让 LLM 按 Schema 抽取原子事实：

```json
{
  "claims": [
    {
      "text": "该条例由 A 机构发布。",
      "verifiable": true,
      "type": "publisher"
    }
  ]
}
```

之后再做确定性后处理：

- 删除纯观点、建议和连接句；
- 拆开由“且、并、以及”连接的独立事实；
- 保留原文字符区间，便于把验证结果映射回答案；
- 对日期、金额、机构、法规号等实体做标准化。

对于模型已经按 `claims[]` 输出的系统，这一步可以前移到生成阶段，从而避免二次拆分产生偏差。

## 三、Step 2：引用有效性检查

这是确定性数据库检查，不需要 LLM：

```python
def validate_evidence_reference(claim, evidence_store):
    results = []

    if not claim.evidence_ids:
        return fail("MISSING_EVIDENCE")

    for evidence_id in claim.evidence_ids:
        evidence = evidence_store.get(evidence_id)

        if evidence is None:
            results.append(fail("EVIDENCE_NOT_FOUND", evidence_id))
        elif hash(evidence.text) != evidence.content_hash:
            results.append(fail("CONTENT_HASH_MISMATCH", evidence_id))
        elif evidence.withdrawn:
            results.append(fail("SOURCE_WITHDRAWN", evidence_id))
        else:
            results.append(pass_("REFERENCE_VALID", evidence_id))

    return results
```

需要检查：

- ID 是否来自当前检索结果，而非模型编造；
- 原文片段是否存在；
- URL、文档号、页码或条款是否可定位；
- 内容哈希是否与入库版本一致；
- 文档是否撤回、废止或被替代；
- 当前用户是否有访问和引用权限。

## 四、Step 3：引用完整性检查

完整性回答的是：**所有应当验证的 claim 是否都有证据**。

```python
verifiable = [c for c in claims if c.verifiable]
supported_candidates = [c for c in verifiable if c.evidence_ids]

coverage = len(supported_candidates) / len(verifiable)
```

但不能简单按句子计数。建议按风险加权：

```python
WEIGHT = {"critical": 5, "high": 3, "normal": 1}

coverage = (
    sum(WEIGHT[c.criticality] for c in claims if c.evidence_ids)
    / sum(WEIGHT[c.criticality] for c in claims)
)
```

高风险规则可以设置为：

```text
critical claim 缺证据 -> 立即失败
high claim 覆盖率必须为 100%
普通说明性 claim 可按策略允许 uncertain
```

注意：此阶段只检查“绑定了证据”，尚未确认绑定是否正确。

## 五、Step 4：证据是否蕴含 claim

这是最关键的语义验证。输入应限制为单个原子 claim 和它绑定的证据原文：

```json
{
  "claim": "该条例于 2026 年 1 月 1 日生效。",
  "evidence": "本条例自2026年1月1日起施行。"
}
```

输出只允许：

```json
{
  "label": "entailed",
  "reason": "证据明确给出相同日期",
  "supporting_spans": ["自2026年1月1日起施行"]
}
```

标签通常至少分为：

- `entailed`：证据直接或必然支持 claim；
- `contradicted`：证据明确反驳 claim；
- `insufficient`：证据相关，但不足以推出 claim。

### 可用实现

1. NLI 模型：将 evidence 作为 premise、claim 作为 hypothesis，输出 entailment/contradiction/neutral。
2. LLM judge：使用严格提示和结构化输出判断，并要求返回精确 supporting span。
3. 专业规则：日期、条款、剂量等高风险字段用规则比对。
4. 多验证器组合：规则优先，NLI/LLM 处理剩余语言现象。

### 避免常见误判

```text
证据：药物 A 在体外实验中抑制病毒复制。
claim：药物 A 已被证明能够治疗患者。
```

两者主题高度相关，但证据不足，应判为 `insufficient`，而不是 `entailed`。

多证据联合时应明确采用：

- `ANY`：任一证据独立支持即可；
- `ALL`：必须联合所有证据才能推出；
- `CORROBORATE`：要求至少两个独立来源分别支持。

不要把多个互不相关的片段拼接成证据，产生原文从未表达的新结论。

## 六、Step 5：来源质量与适用性检查

来源质量最好由元数据规则计算，而不是只问 LLM“是否权威”。

```python
SOURCE_RANK = {
    "official_regulation": 5,
    "official_guidance": 4,
    "peer_reviewed_primary": 4,
    "systematic_review": 4,
    "institutional_summary": 2,
    "news": 1,
    "anonymous_web": 0,
}
```

适用性检查包括：

```python
def applicable(evidence, context):
    return (
        evidence.valid_from <= context.as_of_date
        and (evidence.valid_to is None or context.as_of_date < evidence.valid_to)
        and context.jurisdiction in evidence.jurisdictions
        and context.subject_type in evidence.applicable_subjects
    )
```

不同领域需要不同的来源层级。例如法律问题优先正式法条和司法解释；医疗问题需要区分指南、系统综述、随机试验和个案报告，不能使用一套通用权威分数。

## 七、Step 6：冲突检测

冲突检测有两类。

### 1. claim 与证据冲突

由蕴含验证器的 `contradicted` 标签发现。

### 2. 证据之间冲突

先从证据中抽取可比较的标准化事实：

```json
[
  {
    "subject": "reg-2025-17",
    "predicate": "effective_date",
    "object": "2026-01-01",
    "source": "e1"
  },
  {
    "subject": "reg-2025-17",
    "predicate": "effective_date",
    "object": "2026-03-01",
    "source": "e2"
  }
]
```

同一 `subject + predicate + 适用上下文` 出现不同 object 时触发冲突。然后检查是否可以由以下原因解释：

- 新旧版本；
- 不同司法辖区；
- 不同适用人群；
- 发布日与生效日混淆；
- 一般规则与例外条款。

无法消解的关键冲突应进入人工复核，不能静默选择检索排名更高的来源。

## 八、Step 7：数值、日期和实体检查

高风险字段尽量不用纯 LLM judge，而使用解析器和确定性程序。

### 日期

```python
claim_date = normalize_date(extract_date(claim.text))
source_date = normalize_date(extract_date(evidence.text))

if claim_date != source_date:
    fail("DATE_MISMATCH")
```

### 数值与单位

```python
claim_value = parse_quantity("5 mg/kg")
source_value = parse_quantity("0.005 g/kg")

assert convert_to_base_unit(claim_value) == convert_to_base_unit(source_value)
```

### 实体

使用权威实体表把简称、旧名和别名映射到稳定 ID：

```text
“国家市场监管总局” -> org:CN-SAMR
“市场监管总局”     -> org:CN-SAMR
```

这样可以区分“文本看起来相似”和“实际是同一法律主体”。

## 九、结果聚合与发布闸门

每个 claim 最终形成：

```json
{
  "claim_id": "c1",
  "status": "pass",
  "checks": {
    "reference_validity": "pass",
    "citation_completeness": "pass",
    "entailment": "pass",
    "source_quality": "pass",
    "applicability": "pass",
    "conflict": "pass",
    "numeric_entity": "pass"
  }
}
```

聚合逻辑应该由代码明确配置：

```python
def decide(report):
    for claim in report.claims:
        if claim.criticality == "critical" and claim.has_any_failure():
            return "reject"

        if claim.checks.entailment == "contradicted":
            return "reject"

        if claim.has_unresolved_conflict():
            return "human_review"

    if report.weighted_coverage < 1.0:
        return "reject"

    if report.has_uncertain_high_risk_claim():
        return "human_review"

    return "publish"
```

不建议简单计算平均分，例如 `0.9` 就发布。一个无关紧要的 claim 高分不能抵消一个关键剂量或法律条款验证失败。

## 十、完整伪代码

```python
def verify_answer(answer, context):
    claims = atomize(answer)
    report = VerificationReport()

    for claim in claims:
        claim_report = ClaimReport(claim=claim)

        references = validate_references(claim.evidence_ids, context)
        claim_report.add(references)

        if references.failed:
            report.add(claim_report)
            continue

        evidence = load_evidence(claim.evidence_ids)

        claim_report.add(check_completeness(claim))
        claim_report.add(check_source_quality(evidence, context.domain))
        claim_report.add(check_applicability(evidence, context))
        claim_report.add(check_entailment(claim.text, evidence))
        claim_report.add(check_conflicts(claim, evidence, context))
        claim_report.add(check_numbers_dates_entities(claim, evidence))

        report.add(claim_report)

    report.decision = apply_release_policy(report)
    persist_audit_record(answer, context, report)
    return report
```

## 十一、上线前如何评估验证器

验证器本身也会犯错，必须准备人工标注集，分别测量：

- claim 拆分准确率；
- 引用覆盖判断的 precision / recall；
- entailment、contradiction、insufficient 的混淆矩阵；
- 关键数值错误召回率；
- 错误放行率，即 false acceptance rate；
- 正确答案被拒绝率，即 false rejection rate；
- 不同领域、语言和文档格式下的性能。

高风险系统应优先降低错误放行率，即宁可把不确定结果转人工，也不要让缺乏支持的关键 claim 自动发布。
