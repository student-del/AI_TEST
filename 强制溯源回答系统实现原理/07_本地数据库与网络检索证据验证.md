# 本地数据库与网络检索证据验证

## 核心结论

实现逐项验证不一定需要长期本地数据库，但必须有一个可信的 **evidence store（证据存储层）**，保证生成器和验证器看到的是同一份证据。

证据存储可以是：

1. 单次请求内存：请求结束后删除；
2. 临时缓存：保存数小时或数天；
3. 文件或对象存储：保存网页/PDF 快照；
4. 正式数据库或知识库：支持版本、权限和长期审计。

高风险场景需要解决的不是“是否一定使用数据库”，而是：证据能否被稳定定位、复现、校验版本并接受审计。

## 一、不使用长期数据库也可以验证

一次请求中可以维护内存 evidence map：

```python
evidence_store = {
    "web-1#chunk-3": {
        "url": "https://authority.example/rule-17",
        "title": "规则第 17 号",
        "retrieved_at": "2026-07-14T10:00:00+08:00",
        "text": "本规则自2026年1月1日起施行。",
        "content_hash": "sha256:..."
    }
}
```

模型只允许引用 `web-1#chunk-3`。验证器通过这个 map 获取证据原文：

```python
claim = "该规则自2026年1月1日起施行。"
evidence = evidence_store["web-1#chunk-3"]["text"]

result = verify_entailment(claim, evidence)
```

这足以完成本次请求的结构和语义验证。缺点是请求结束后无法重新审计；网页之后发生变化，也不能证明当时模型实际看到了什么。

## 二、网络检索的正确流水线

```text
搜索引擎返回候选 URL 和摘要
  -> 来源白名单/域名信誉检查
  -> 抓取实际网页或 PDF
  -> 提取正文与文档元数据
  -> 切分为可引用证据片段
  -> 为文档和片段分配稳定 ID
  -> 保存原文、URL、时间与哈希
  -> 模型生成 claim + evidence ID
  -> 验证器对原文执行逐项验证
  -> 通过后发布
```

搜索结果摘要只适合召回候选页面，不宜直接作为最终证据，原因包括：

- 摘要可能截断关键限定词；
- 摘要可能来自搜索引擎缓存；
- 页面正文可能已经更新或删除；
- 摘要可能把页面中不相邻的文字拼接在一起；
- 搜索结果标题、日期可能是推断值，不是原始文档字段。

## 三、网络证据记录什么

建议每次抓取后建立文档记录：

```json
{
  "document_id": "web-20260714-0017",
  "canonical_url": "https://authority.example/rule-17",
  "final_url": "https://authority.example/rule-17.html",
  "title": "规则第 17 号",
  "publisher": "示例监管机构",
  "published_at": "2025-12-01",
  "updated_at": "2026-02-10",
  "retrieved_at": "2026-07-14T10:00:00+08:00",
  "http_status": 200,
  "content_type": "text/html",
  "content_hash": "sha256:...",
  "extractor_version": "web-extractor-3.2",
  "raw_snapshot_uri": "object://evidence/web-20260714-0017.html"
}
```

证据片段记录：

```json
{
  "evidence_id": "web-20260714-0017#section-4-p2",
  "document_id": "web-20260714-0017",
  "section": "第四条 生效日期",
  "char_start": 1832,
  "char_end": 1850,
  "text": "本规则自2026年1月1日起施行。",
  "chunk_hash": "sha256:..."
}
```

原始快照与提取后的正文都值得保留：前者证明网页当时的实际内容，后者用于检索和验证。

## 四、网络结果的六层验证

### 1. 来源身份

检查：

- URL 最终跳转到了哪里；
- HTTPS 证书和域名是否符合预期；
- 是否属于官方白名单域名；
- 页面声明的发布者能否由站点身份支持；
- 是否是转载、镜像或用户上传内容。

域名白名单不能单独证明内容正确，但可以降低伪造来源风险。

### 2. 文档真实性和完整性

优先使用带数字签名、官方文档编号、DOI、稳定版本号或校验和的文档。对 HTML/PDF 保存原始字节哈希：

```python
content_hash = sha256(raw_response_bytes)
```

如果后来同一 URL 的哈希变化，应创建新版本，而不是覆盖旧证据。

### 3. 时间与适用性

网络页面必须区分：

- 页面抓取时间；
- 原始发布日期；
- 最后更新时间；
- 法律或规则生效时间；
- 数据统计周期。

“网页今天仍可访问”不表示其内容当前仍有效。

### 4. 精确片段定位

HTML 可以记录标题层级、段落号、字符区间；PDF 记录页码和文本坐标；法规优先记录条款号。只保存整个网页 URL 会让引用难以复核。

### 5. claim-evidence 蕴含验证

验证器使用抓取到的实际原文，而不是搜索摘要：

```python
verify_entailment(
    claim="该规则于2026年1月1日生效",
    evidence="本规则自2026年1月1日起施行"
)
```

日期、数值、机构和条款号再用确定性解析器比对。

### 6. 独立来源交叉验证

交叉验证不是简单找两个网页。两个网站可能都转载同一篇错误文章，因此要检查来源独立性：

```text
政府正式文件 + 监管机构公告 -> 较独立
新闻网站 A + 转载 A 的网站 B -> 不是独立证据
论文原文 + 引用该论文的博客 -> 不是两个同等级来源
```

关键事实可要求一个一手来源，或至少两个真正独立的高质量来源。

## 五、三种部署方案

### 方案 A：单次请求内存

```text
搜索 -> 抓取 -> 内存 evidence map -> 生成与验证 -> 返回 -> 删除
```

优点：简单、隐私暴露少、无需维护数据库。

缺点：不可长期审计，无法复现动态网页。

适用：普通问答和低风险研究辅助。

### 方案 B：短期证据缓存

```text
搜索 -> 抓取 -> Redis/文件缓存 -> 生成与验证 -> TTL 自动过期
```

优点：可以重试、复核和避免重复抓取。

缺点：仍不适合长期审计。

适用：企业内部搜索、客服和一般知识系统。

### 方案 C：版本化证据库

```text
搜索/采集
  -> 原始快照存对象存储
  -> 元数据存关系数据库
  -> 文本片段存检索索引
  -> 哈希和版本形成审计链
```

优点：可复现、可追踪、支持权限和版本管理。

缺点：成本更高，还要处理版权、隐私、数据保留和网页更新。

适用：法律、医疗、金融、合规和正式报告生成。

## 六、数据库本身也不是权威来源

本地数据库只是证据载体，不会自动使网络内容可信。仍然必须记录：

```text
这条内容来自哪里
什么时候抓取
抓取的是哪个版本
原始内容有没有被修改
来源属于什么权威等级
适用于什么时间和范围
```

错误内容保存进数据库后，仍然是可复现的错误内容。因此来源治理和语义验证不能被“已经入库”取代。

## 七、推荐的最小实现

即使不建设正式数据库，也建议在一次请求内至少建立：

```python
class Evidence:
    id: str
    url: str
    title: str
    publisher: str | None
    retrieved_at: datetime
    text: str
    content_hash: str
```

并遵守以下规则：

1. 搜索摘要不直接进入最终引用；
2. 必须打开并提取原页面；
3. 模型只能引用 evidence map 中的 ID；
4. 验证器只根据 evidence map 中冻结的原文判断；
5. 返回答案时把 ID 渲染为原 URL 和精确片段位置；
6. 证据不足或页面无法获取时明确拒答或降低结论强度。
