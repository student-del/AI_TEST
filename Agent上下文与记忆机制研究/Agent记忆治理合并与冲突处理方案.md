# Agent 记忆治理、合并与冲突处理方案

## 官方证据边界

OpenAI 官方将 Codex memories 定义为从既往任务带入未来任务的有用上下文，并明确要求：必须始终遵守的团队指导应放在 `AGENTS.md` 或版本化文档中，记忆只能作为辅助召回层。Codex 本地记忆包含摘要、持久条目、近期输入及支持证据；配置中区分 per-task memory extraction 与 global memory consolidation，但官方页面没有公开具体的冲突合并算法。

Anthropic 官方把 Claude Code 的 `CLAUDE.md` 与 auto memory 区分为人写的指令和 Agent 写的学习笔记。Auto memory 按项目存放在可审计、可编辑、可删除的 Markdown 文件中；官方也警告，矛盾指令可能被模型任意选择。因此，下文是自拟工程方案，不是 OpenAI 或 Anthropic 已披露的内部实现。

## 核心原则

记忆系统不应是“把所有历史摘要塞进上下文”，而应是一个有来源、作用域、时效、证据和生命周期的知识治理系统。最重要的原则是：

> 规则不降格为记忆；记忆不升级为权威。冲突不是文本去重问题，而是带来源、时间和作用域的主张解析问题。

## 一、先把信息分层

### 1. 权威指令

系统策略、开发者指令、当前用户明确要求、`AGENTS.md` / `CLAUDE.md`、权限与 Hook。它们不进入普通记忆合并池。记忆若与有效指令冲突，记忆必须失效或被屏蔽。

### 2. 外部事实

例如依赖版本、法律规则、当前负责人、API 行为。必须记录证据和 `observed_at`，高时变事实应在使用前重新验证，不能仅因被记住就当作当前事实。

### 3. 项目事实

例如“测试命令是 `pnpm test`”“认证入口在某文件”。可由仓库文件、成功执行结果或用户确认支持。代码变化后可能过期。

### 4. 用户偏好

例如“用户偏好中文、简洁回答”。偏好可以被用户后来明确修改，且通常具有用户级、项目级或会话级作用域。

### 5. 情节记忆

记录一次任务发生了什么、尝试过什么、为什么失败。主要用于追溯和避免重复踩坑，不应直接被提升为普遍规则。

### 6. 推断与假设

模型从行为中猜测的偏好或因果关系。必须标记为 `inferred`，低于用户明确陈述和可验证事实；不应直接触发高风险动作。

## 二、记忆条目的最小数据模型

即使物理存储是 Markdown，逻辑上也应包含：

```yaml
id: mem-20260715-001
subject: test.command
claim: pnpm test
type: project_fact
scope: repo:E:/AI_TEST
source:
  kind: observed_tool_result
  ref: task-123/tool-9
authority: observed
confidence: 0.95
valid_from: 2026-07-15
valid_until: null
observed_at: 2026-07-15T10:00:00+08:00
status: active
supersedes: []
contradicts: []
sensitivity: internal
last_verified_at: 2026-07-15
```

其中 `authority` 与 `confidence` 必须分开：用户有权决定自己的偏好，但未必有权定义外部客观事实；模型对某件事很确信，也不会因此获得更高权威。

## 三、写入治理

不是所有对话内容都值得写入。候选记忆应通过以下门槛：

1. **未来效用**：跨会话再次出现的概率和价值是否足够高。
2. **可归属性**：能否确定 subject、scope 和来源。
3. **敏感性**：秘密、凭证、一次性隐私数据默认不写入。
4. **稳定性**：高度短暂的信息优先留在会话上下文或情节日志。
5. **证据质量**：推断不得伪装成用户确认或观测事实。
6. **权限**：用户或组织是否允许该任务用于生成未来记忆。

推荐采用两阶段写入：先写 append-only 候选事件，再由 consolidation 过程生成或更新 durable entry。这样可以审计合并过程，也能在错误合并时回滚。

## 四、合并算法

### 第一步：标准化

把自然语言转成 `subject + claim + scope + time + source`，统一同义词和实体。例如“用 pnpm 跑测试”和“测试命令为 pnpm test”映射到同一 subject。

### 第二步：仅在可比较集合中判断冲突

只有 subject 相同、scope 相交、有效时间重叠且 claim 不能同时成立时，才构成真正冲突。以下通常不是冲突：

- 全局偏好“默认中文”和项目偏好“本项目英文”：作用域不同，后者在项目内更具体。
- “2025 年负责人是 A”和“2026 年负责人是 B”：有效期不同，是版本演化。
- “Windows 用 PowerShell”和“Linux 用 Bash”：条件不同，应拆成条件化记忆。

### 第三步：按类型使用不同解析规则

不能用一个统一分数决定所有冲突：

- **用户偏好**：用户最新的明确陈述覆盖旧偏好；项目级偏好只在该项目内覆盖用户级默认。
- **外部事实**：最新不是充分条件；优先重新查询权威源，并保留证据。无法验证时标记 disputed。
- **项目事实**：以当前仓库状态、成功工具观测和版本化文档为准；旧条目标记 superseded，不物理删除。
- **情节记忆**：不同事件可以并存，不应强制合并成一个“真相”。
- **推断**：不得覆盖明确陈述或高质量观测；冲突时优先撤销推断。

### 第四步：生成解析结果，而不是覆盖历史

结果应是以下之一：

- `merge`：两条等价或互补，合并证据和适用条件。
- `supersede`：新条目在相同作用域和时间上替代旧条目，旧条目保留历史状态。
- `scope_split`：拆成不同项目、目录、平台或用户范围。
- `temporal_split`：拆成不同有效期。
- `coexist`：不同事件或可同时成立的观点并存。
- `disputed`：证据不足，禁止无提示地选边。
- `reject`：低质量、敏感或越权候选不进入持久记忆。

## 五、冲突升级策略

### 可自动处理

- 用户明确说“以后改用英文”，可将旧语言偏好标记 superseded。
- 工具验证 `pnpm test` 已不存在而 `npm test` 成功，可在同一 commit/branch 作用域更新项目事实。
- 两条记忆实际适用于不同平台，可自动 scope split。

### 必须重新验证

- 当前价格、版本、负责人、法律、服务状态等时变事实。
- 项目事实与当前代码或配置不一致。
- 记忆来源是旧网页、旧分支或不明摘要。

### 必须询问用户

- 两个相互排斥的用户偏好都来自明确陈述，且无法从时间或作用域判断。
- 冲突会显著影响结果、成本、隐私或不可逆动作。
- 用户分别以不同角色给出要求，而系统无法确认当前角色或授权范围。

提问时不应只问“选 A 还是 B”，而应展示来源和影响：

```text
我发现两条有效记忆冲突：
A. 2026-06-10：所有报告使用中文（用户级）
B. 2026-07-01：研究报告使用英文（项目级，但项目未标明）

当前任务是本项目研究报告。应采用哪条？
你的选择是否只适用于本项目，还是更新全局偏好？
```

### 无法获得反馈时

采用安全默认：不执行不可逆或高风险动作；对可逆输出使用最窄作用域、当前任务中明确出现的要求，并披露假设。不能为了“不中断”而静默选择一条冲突记忆。

## 六、检索时治理

即使存储正确，检索也可能把过期信息带入上下文。检索排序至少考虑：

```text
适用性 × 权威 × 证据质量 × 新鲜度 × 置信度 − 冲突/敏感风险
```

但这是召回排序，不是指令优先级。候选记忆进入上下文前还要经过：

1. scope filter；
2. validity/TTL filter；
3. authority boundary；
4. conflict detection；
5. sensitive-data filter；
6. current-source revalidation（适用于时变事实）。

只向模型注入解析后的 active 视图，同时保留 provenance 链供需要时展开。不要把互相矛盾的原始记忆无标记地同时塞入提示词，让模型临场猜测。

## 七、生命周期与审计

- 每条记忆可查看、编辑、禁用、删除和导出。
- 维护 `created_at`、`last_used_at`、`last_verified_at` 和使用计数。
- 低价值、长期未使用、无来源记忆自动降级或过期。
- 被替代条目进入历史层，不参与默认召回，但保留审计链。
- 合并过程记录输入条目、决策、模型/规则版本和原因。
- 对高影响记忆设置人工确认或双证据门槛。
- 定期运行 contradiction scan、staleness scan 和 secret scan。

## 八、简化决策表

| 冲突类型 | 默认处理 |
|---|---|
| 记忆 vs 当前明确用户要求 | 当前要求胜；评估是否更新持久记忆 |
| 记忆 vs 有效项目/组织规则 | 规则胜；记忆屏蔽或纠正 |
| 新旧明确用户偏好 | 同作用域下新偏好 supersede 旧偏好 |
| 不同作用域偏好 | 保留两者，检索时选择最具体适用项 |
| 外部事实互相矛盾 | 查权威当前来源；否则 disputed |
| 项目事实与仓库现状冲突 | 当前可验证仓库状态胜，旧记忆归档 |
| 推断 vs 明确陈述 | 明确陈述胜，撤销推断 |
| 两条高质量证据仍冲突 | 标记 disputed；高影响时询问用户 |

## 九、模型在什么时候“想起”记忆

“想起”至少包含三个阶段，不能混为一谈：

1. **可用（stored/available）**：信息已经写入记忆库，但尚未进入当前模型上下文。
2. **召回（retrieved/injected）**：系统或 Agent 根据会话、项目、任务和查询，选择记忆并放入当前上下文，或读取相关记忆文件。
3. **采用（attended/used）**：模型在生成答案或行动时真正注意到并使用该记忆。

只有第三阶段在用户体验上像“模型想起来了”。但即使记忆已经注入上下文，模型也可能因为上下文过长、相关性弱、指令冲突或注意力分散而没有使用它。

### 官方公开的触发方式

#### OpenAI Codex

OpenAI 官方说明，启用本地 memories 且当前任务允许使用记忆时，Codex 可以把已有记忆注入未来会话。用户可通过 `/memories` 分别控制当前任务是否使用既有记忆，以及当前任务是否成为未来记忆的生成输入。配置中的 `memories.use_memories` 控制是否向未来会话注入既有记忆。

公开页面说明本地存储含摘要、durable entries、recent inputs 和 supporting evidence，并存在 global consolidation；但没有公开 Codex 如何为每个具体问题计算相关性、选择哪些条目、如何排序或达到什么阈值。因此，不能把以下自拟检索流程表述为 Codex 官方内部算法。

#### Anthropic Claude Code

Anthropic 官方公开了两类加载：

- 会话启动时，auto memory 的 `MEMORY.md` 前 200 行或前 25KB（取先达到者）进入上下文。
- 更详细的 topic files 不在启动时自动加载；Claude 在认为相关时，通过普通文件工具按需读取。

`CLAUDE.md`、auto memory、会话历史、文件和工具结果共同占用上下文。因此，预载只是“模型可见”，不是遵循或使用保证。用户可以通过 `/memory` 查看、编辑、删除记忆，并在 UI 中看到 Writing memory 或 Recalled memory 状态。

### 自拟的触发模型

一个合理的 Agent 记忆系统应在以下时点尝试召回：

1. **会话初始化**：加载稳定的用户偏好、项目摘要和未完成事项索引，但控制体积。
2. **任务理解完成后**：从当前用户请求提取实体、意图、项目、文件路径和任务类型，用它们检索相关记忆。
3. **环境或作用域切换时**：进入新仓库、目录、分支、客户、平台或身份角色后，重新检索该 scope 的记忆。
4. **模型遇到不确定性时**：在向用户提问前，先查询是否已有经过确认的偏好或既往决定；不得用低置信推断代替用户授权。
5. **关键决策前**：部署、删除、外发、花费或隐私相关动作前，召回既往约束，但仍需经过当前权限和审批机制。
6. **工具返回新证据后**：若代码、配置或外部权威来源改变了已知事实，重新检索并检测旧记忆冲突。
7. **压缩或恢复后**：重新附加必要的持久记忆索引，避免会话摘要丢失关键背景。

### 一个简化的检索循环

```text
用户请求
  -> 解析任务与作用域
  -> 生成 memory query
  -> scope / validity / authority 过滤
  -> 相关性排序与冲突解析
  -> 注入少量 active memories
  -> 模型规划或作答
  -> 若证据变化，重新检索
```

检索 query 不应只有用户原句，还应包含结构化线索：

```yaml
intent: create_research_report
repo: E:/AI_TEST
topic: agent_memory
artifact: markdown
language: unknown
risk: low
```

这能召回“本项目 AI Agent 学习结论需保存为 Markdown”之类的项目记忆，而不会因为用户本轮没重复关键词就遗漏。

### 何时不应该依赖记忆

- 当前用户已经明确给出要求时，不应让旧偏好覆盖当前要求。
- 法律、价格、版本、负责人等时变事实应重新查权威来源。
- 高风险动作需要当前授权，不能把“用户上次同意过”当成永久批准。
- 记忆处于 `disputed`、过期、无来源或作用域不明时，不应静默使用。
- 必须执行的规则应来自指令、policy、permissions 或 Hook，而不是期待模型刚好召回记忆。

因此，更精确的说法不是“模型自己在某一刻突然想起”，而是：**宿主系统在若干触发点使记忆可见，Agent 可能主动读取更详细内容，模型随后在当前生成中选择是否利用它。**

## 十、启动时最少需要加载什么

启动时不一定要把任何具体记忆正文交给模型。应区分两种架构：

### 架构 A：模型主动检索

模型至少需要看到“记忆能力描述”，例如：

```text
可用工具：memory_search(query, scope, types)
用途：查询跨会话用户偏好、项目事实和历史决策。
限制：记忆不是权威规则；时变事实必须验证。
```

当前用户请求本身即可作为第一次检索的种子。因此，具体记忆正文可以为零；真正不可缺少的是工具 schema、使用政策和当前作用域信息。

### 架构 B：宿主预检索

宿主在调用模型前，直接根据 user ID、repo、cwd、任务文本等检索少量记忆，再把结果随初始上下文注入。模型甚至不必知道底层记忆库如何搜索。这种架构需要 runtime 掌握作用域键，但同样不要求先给模型完整记忆索引。

### 官方公开情况

Anthropic 明确说明 Claude Code 在会话开始时加载 auto-memory `MEMORY.md` 的前 200 行或 25KB（取先达到者）；该文件被设计成简洁索引，详细 topic files 按需读取。因此 Claude Code 的启动包确实包含一部分记忆索引/摘要正文。

OpenAI 官方说明 Codex 在 memories 开启且任务允许使用时可向未来会话注入既有记忆，并公开本地存储包含 summaries、durable entries、recent inputs 和 supporting evidence；但当前公开页面没有逐字段说明某次会话启动时固定注入哪几类、多少条以及检索顺序。因此不能断言 Codex 必定预载某个固定 `MEMORY.md` 式索引。

### 自拟的最小启动包

一个稳健实现可以加载以下六类信息，其中只有第 4 类属于具体记忆内容：

1. **能力清单**：是否有 `memory_search`、`memory_read`、`memory_write_candidate`，参数和返回结构是什么。
2. **治理政策**：哪些内容能写入、记忆低于当前指令、时变事实需验证、敏感信息限制、冲突如何升级。
3. **当前作用域身份**：用户/组织、repo、cwd、branch、workspace、设备或环境，以及哪些 scope 可以访问。它们通常由可信 runtime 提供，不应依赖记忆猜测。
4. **小型核心记忆**：少量稳定且高频的 active 用户偏好、项目摘要、进行中事项；可以为空。
5. **记忆目录索引**：可选的 topic 名称、摘要、更新时间和状态，不加载详细正文。
6. **检索触发规则**：何时必须搜索，例如不确定用户偏好、进入新项目、关键决策前、工具证据与旧事实冲突时。

示例：

```yaml
memory_capability:
  enabled: true
  tools: [memory_search, memory_read]
scope:
  user: user-42
  repo: E:/AI_TEST
  branch: main
policy:
  memory_is_authoritative: false
  verify_time_sensitive_facts: true
core_memories:
  - id: pref-language
    claim: 默认使用中文
    scope: user:user-42
    source: explicit_user
memory_index:
  - topic: agent-memory-research
    summary: Agent 上下文与记忆机制研究
    updated_at: 2026-07-15
```

### 哪些不应该默认预加载

- 全部历史对话和工具输出；
- 大型 topic files 正文；
- 已 superseded、expired 或 disputed 的条目；
- 密钥、令牌及不必要的敏感数据；
- 与当前用户、项目或权限域不匹配的记忆；
- 可从当前权威源快速重新获得的高时变事实。

因此，启动时真正必需的不是“一批旧记忆”，而是：**记忆访问能力、治理规则和可信作用域**。少量核心记忆或索引只是提高首次响应质量和降低检索延迟的优化。
