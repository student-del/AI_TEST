# LLM 压缩时如何处理历史?会话开头的核心意图会丢吗?

> 讨论问题:调用 LLM 压缩上下文(Auto-Compact)时,是把全部历史一起压吗?会完整保留一部分吗?会话初始几轮常含用户核心意图,这些也会被直接压缩吗?
>
> 结论:**不是一股脑压。历史被分成"逐字保留 / 摘要化 / 丢弃"三种待遇。逐字保留的是尾部最近若干轮 + 外部持久文件(CLAUDE.md/plan/最近文件),开头几轮的原始文本会被摘要化,但其核心意图被 9 段模板刻意提取保留(语义保留,非逐字)。**
>
> 本文承接《上下文压缩机制详解.md》与《压缩机制如何区分信息重要性.md》。
> 更新时间:2026-07-12

---

## 一、压缩时历史的三种待遇

| 待遇 | 对象 | 处理方式 |
|------|------|---------|
| 逐字保留(verbatim) | ①尾部最近若干轮 ②重注入的 CLAUDE.md / plan / 最近 5 文件 / 技能 | 原样,不经 LLM |
| 摘要化(summarized) | 头部 + 中部历史对话 | LLM 压成 9 段结构化摘要 |
| 丢弃(dropped) | 图像、文档附件 | 剥离为 `[image]` / `[document]` |

**所以"是否直接把全部历史压缩"的答案是:否。** 只有头+中部进摘要;尾部与外部文件逐字保留。

## 二、完整保留的是"尾部",不是"开头"

`calculateMessagesToKeepIndex` 从最后一条往前扩,保留最小窗口:

```
minTokens   = 10,000   ← 至少保留最近 1 万 token
minTextMsgs = 5        ← 至少 5 条文本消息
maxTokens   = 40,000   ← 硬上限
```

外加 CLAUDE.md / plan / 最近 5 文件(50K 预算,每文件≤5K)/ 技能 逐字重注入。

Auto-Compact 触发通常在 ~167K token,而保留窗口仅 10K–40K → **会话开头几轮必然在保留窗口之外**,原始逐字文本不会留在发给模型的上下文里。

## 三、开头的核心意图:语义保留,非逐字保留

9 段模板中两段专门承载开头意图:

```
# Current State        当前在做什么、下一步
# Task specification   用户要什么？设计决策？澄清上下文？  ← 核心意图
```

压缩提示词明确要求抽取"任务规格 / 关键决策 / 约束与偏好"。因此:

- **原始对话文本**:被摘要化(逐字原话不留)
- **意图语义**:被刻意提取进 Task Spec / Current State(保留)

## 三·附:Auto-Compact 9 段结构化摘要逐段详解

> 这 9 段来自 Stage 4 Auto-Compact 压缩提示词(`autoCompact.ts` 的 compactPrompt)。设计思想是**"交接式摘要"(handoff summary)**——假设一个全新的模型中途接手任务,每一段回答它必然会问的一个问题;9 段答全,接手的模型就能无缝续上。

| # | 段名(英 / 中) | 记录什么 | 回答的交接问题 |
|---|---------------|---------|---------------|
| 1 | Current State / 当前状态 | 正在做什么、进行到哪一步、哪些任务未完成 | "我现在在哪?" |
| 2 | Task Spec / 任务规格 | 用户最初要什么、设计决策、约束、澄清过的上下文 | "用户到底要什么?"(**核心意图所在**) |
| 3 | Key Files / 关键文件 | 读过或改过的文件路径 + 每个文件与任务的相关性 | "该看哪些文件?" |
| 4 | Key Functions / 关键函数 | 关键函数名 + `文件:行号` + 用途 | "关键代码在哪、干什么?" |
| 5 | Errors & Fixes / 错误与修复 | 遇到过的错误及对应的修复方式 | "踩过哪些坑、怎么绕过?" |
| 6 | Learnings / 经验教训 | 什么方法有效、什么无效、该避免什么 | "有哪些已验证的经验?" |
| 7 | Work Log / 工作日志 | 按时间顺序记录已完成的步骤 | "已经做了什么?" |
| 8 | TODOs / 待办事项 | 还没做完、需要继续的事项 | "还剩什么没做?" |
| 9 | Next Steps / 下一步 | 紧接着应该做什么 | "下一步做什么?" |

**逐段要点**:

1. **Current State(当前状态)**——给接手者一个"你现在站在任务的哪个位置"的定位,是整份摘要的入口。
2. **Task Spec(任务规格)**——承载会话开头的用户核心意图,决策与约束都在这;它把"埋在前几轮对话里的意图"提炼出来,是开头意图能存续的关键段。
3. **Key Files(关键文件)**——路径 + 相关性,让模型不必重新遍历目录就知道该读哪些文件。
4. **Key Functions(关键函数)**——精确到 `文件:行号`,避免压缩后重新全局搜索代码。
5. **Errors & Fixes(错误与修复)**——防止压缩后重复犯同样的错、重走死路。
6. **Learnings(经验教训)**——沉淀"什么有效/无效",约束后续尝试方向。
7. **Work Log(工作日志)**——按时间线记已完成步骤,保证进度不丢、不重做。
8. **TODOs(待办)**——明确剩余工作项。
9. **Next Steps(下一步)**——给出紧接着的行动,让新上下文能立刻开工。

**与"会话记忆"模板的关系**:零成本替代路径(会话记忆压缩)用的是一套**平行但略有差异**的 9 段模板——多出 `Session Title`、`Workflow`(常用命令/输出解读)、`Codebase and System Documentation`(系统组件原理)、`Key results`(用户要的特定产出)等段,少了 `Next Steps`/`TODOs` 的独立拆分。两者思想一致(都是交接式结构化),但 **Auto-Compact 版更聚焦"续接当前任务",会话记忆版更聚焦"长期笔记"**。上文第三节出现的 `# Current State`、`# Task specification` 正是两套模板共有的段。

## 四、风险:LLM 摘要有损

若开头意图含精确约束("必须用 POST")、细微差别或未明说的偏好,摘要可能糊掉——对应"五类高危丢失"中的硬约束 / 决策理由。且自动压缩触发时模型常猜不准后续走向,最易压错。

## 五、业界对比

| 系统 | 对开头/用户意图的保护 |
|------|----------------------|
| Claude Code | 靠"9 段摘要 Task Spec"承载,语义提取,不逐字钉第一条 |
| Codex | 压缩时**按内容保留用户消息**(最近的、20K 预算),用户消息优先级高于工具结果 |
| Cursor | 摘要前把全量历史存文件,压缩后仍可搜回开头细节 |

Codex / Cursor 对"用户原话"的保护比 Claude Code 更直接。

## 六、实用结论

想让核心意图扛过压缩、绝不丢,**别指望埋在第一轮对话里的话被逐字保住**,而要:

1. **写进 CLAUDE.md 或 plan 文件** → 逐字重注入,压不掉
2. **主动 `/compact` 时加引导**("focus on X,保留 Y 约束")→ 指挥摘要偏向
3. **长任务边做边记会话笔记** → 压缩时直接复用

核心机制层面:压缩保护的是"尾部 + 外部持久文件",不是"会话开头";开头意图的存续依赖 LLM 摘要的质量,而这正是需要用外部持久层(CLAUDE.md / plan / memory)兜底的地方。
