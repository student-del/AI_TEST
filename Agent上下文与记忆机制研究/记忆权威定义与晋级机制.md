# Code Agent 中的记忆权威、置信度与晋级机制

> 面向开发者的概念澄清与工程设计指南  
> 修订日期：2026-07-15

## 0. 先给结论

在 Code Agent 中，“记住了”不等于“是真的”，更不等于“必须执行”。开发者至少要分清四个维度：

| 维度 | 它回答的问题 | 典型处理 |
|---|---|---|
| **指令优先级（precedence）** | 冲突时听谁的？ | 按产品定义的指令层级处理 |
| **规范权威（normative authority）** | 这是不是团队认可、应持续遵循的规则？ | 放入经审查的项目指导或配置 |
| **事实置信度（epistemic confidence）** | 这条事实有多可信、是否仍然有效？ | 用当前代码、配置、测试和外部事实验证 |
| **检索重要性（retrieval importance）** | 上下文有限时是否值得召回或保留？ | 按任务相关性、风险和时效排序 |

最重要的工程原则是：

1. **自动记忆是线索，不是裁决者。**
2. **重复出现提高的是置信度，不会自动产生团队规范。**
3. **只有经过授权的人或流程写入权威载体，才算真正晋级。**
4. **高权威载体也可能过时；代码、配置、测试与文档冲突时必须显式处理。**
5. **需要确定性执行的约束应进入配置、权限、Hook、CI 等机制，而不是只写在提示文档中。**

### 0.1 最终精炼结论

经过对官方资料、本机真实 memory 和 Claude Code 社区逆向工程的对照，本文对最初三个问题给出如下最终回答。

#### 记忆权威如何定义

记忆权威不是“模型有多确信”，也不是“这条内容被提到多少次”。本文建议将 **规范权威** 定义为：

> **某条信息因为获得了具备相应作用域决策权的人或治理流程的明确授权，而被允许约束后续行为的程度。**

权威由四个因素共同决定：

```text
权威 = 授权者身份 × 明确决策意图 × 适用作用域 × 受治理载体
```

| 因素 | 要回答的问题 |
|---|---|
| 授权者身份 | 谁有资格决定：当前用户、代码所有者、架构组、安全团队？ |
| 明确决策意图 | 这是猜测、讨论、建议，还是明确的“以后按此执行”？ |
| 适用作用域 | 只对当前任务、某个目录、整个仓库，还是整个组织有效？ |
| 受治理载体 | 是否进入 `AGENTS.md`、`CLAUDE.md`、ADR、配置、Hook 或 CI？ |

因此：

- 工具结果和源码主要提供 **事实证据**，通常没有规范权威；
- 自动 memory 主要提供 **历史线索**，没有制定规则的权力；
- 当前用户指令在当前任务内具有指令效力，但不会自动跨会话成为团队规范；
- 经授权并写入项目指导或 ADR 的内容具有持久规范权威；
- 权限、Hook、沙箱和 CI 具有确定性执行力，但属于控制系统而不是 memory。

#### 低权威记忆如何晋级

低权威 memory **不能靠重复、置信度分数或 LLM 自我判断自动晋级为规则**。必须区分两条路径：

```text
事实路径：memory 线索 → 当前证据验证 → 已验证事实
治理路径：聊天建议 → 授权者明确批准 → 写入受治理载体 → 正式规则
```

第一条路径只提高事实可信度，不提高规范权威。例如 memory 记得“项目使用 pnpm”，检查 `package.json` 和锁文件后可以确认这是当前事实，但仍不能自动推出“团队永久禁止 npm”。

第二条路径才是真正的权威晋级。例如用户明确说“这个项目以后统一使用 pnpm，请写入 AGENTS.md”，Agent 按授权修改项目指导；如果再配置 CI 阻止其他包管理器，规则进一步进入确定性执行层。

真正的晋级条件是：

1. 有明确、可识别的候选内容；
2. 区分事实陈述与规范要求；
3. 验证它没有与当前代码、配置或既有决策冲突；
4. 确认提出者对目标作用域具有决策权；
5. 得到明确批准，而不是从沉默、重复或习惯中推断授权；
6. 写入适合的受治理载体；
7. 对高风险要求使用可执行控制，而非只依赖提示文本。

#### 聊天信息何时成为架构决策

聊天消息本身只是决策输入、讨论记录或用户指令。它成为架构决策至少要通过以下闸门：

| 闸门 | 判断标准 |
|---|---|
| **1. 决策意图** | 用户明确表示“决定采用 X”，而不是“可以考虑 X”“我猜 X 更好” |
| **2. 决策权限** | 发言者对相应系统和作用域具有决策权，或获得负责人的批准 |
| **3. 问题与范围** | 明确解决什么问题、影响哪些组件、在什么条件下有效 |
| **4. 证据核验** | 与当前代码、约束、成本、安全和运行环境一致 |
| **5. 备选与理由** | 至少记录选择 X 的原因、主要替代方案及为何不选 |
| **6. 风险与后果** | 记录兼容性、迁移、回滚、运维和安全影响 |
| **7. 正式记录** | 写入 ADR 或团队认可的架构文档，带日期、状态和批准者 |
| **8. 落地验证** | 实现、测试或配置与决策一致；若尚未落地，应标为 proposed/accepted 而非 implemented |

最小判断公式：

```text
架构决策
= 明确选择
+ 有权批准
+ 理由与范围
+ 正式记录
```

如果缺少其中任何一项，聊天内容最多是：

- `observation`：观察；
- `hypothesis`：假设；
- `proposal`：方案建议；
- `preference`：个人偏好；
- `task_instruction`：当前任务指令。

它们不能被 memory 提取器自动重写成 `architecture_decision`。

#### 两个典型例子

**例 1：还不是架构决策**

> 用户：“微服务可能更适合以后扩展，你先研究一下。”

这是研究任务和方案假设。Agent 可以保存调查上下文，但不能写成“项目已决定采用微服务”。

**例 2：可以形成架构决策**

> 有决策权的用户：“我们决定订单模块采用事件驱动架构。原因是需要解耦支付和库存；不采用同步调用是因为故障传播。请创建 ADR，状态标为 Accepted，并记录迁移与回滚方案。”

在核对当前项目约束后，Agent可以创建 ADR。这时聊天消息是授权来源，ADR 才是可审查、持久的架构决策载体。

一句话总结：

> **记忆可以提供线索，证据可以确认事实，只有授权和治理才能产生规则；聊天只有在“明确决定 + 有权批准 + 理由范围 + 正式记录”后才成为架构决策。**

### 0.2 对端到端流程的准确理解

可以把整体流程理解为“满足门控条件后，LLM 从若干新增对话中提取结构化记忆候选”，但不能直接理解为“LLM 给记忆赋予权威等级”。更准确的流程是：

```text
传统代码满足触发条件
  ↓
LLM 阅读若干新增回合，判断是否有长期价值
  ↓
LLM 输出记忆候选：内容、类型、建议作用域、来源引用
  ↓
传统代码校验来源、秘密、schema、重复和写入范围
  ↓
保存为辅助 memory
  ↓
未来召回时重新验证
  ↓
若要成为规则，必须由用户/团队明确授权并迁移到治理载体
```

建议的候选结构是：

```json
{
  "content": "用户偏好在修改代码前先看计划",
  "type": "preference",
  "scope": "user",
  "source_turn_ids": ["turn_18", "turn_24"],
  "needs_verification": false
}
```

这里故意不让 LLM 输出可直接生效的 `authority: high`。即使为了审计保留 authority 字段，它也应由代码和治理流程派生：

```text
authority = derive(
  source_role,
  explicit_authorization,
  approved_by,
  governed_destination
)
```

而不是：

```text
authority = llm_guess(conversation)
```

原因是 LLM 可以识别“这句话看起来像长期偏好”，但不能仅凭措辞判断发言者是否有权制定全项目规则，也不能把重复行为解释成授权。

对实际产品需要保留证据边界：

- Anthropic 官方说明 Claude 会判断未来有用的信息并写入 auto memory；本机 Claude memory 实例只有 `name`、`description`、`type` 和正文，没有 authority 字段。
- OpenAI 官方确认 Codex 使用 extraction/consolidation 模型，并保存 summaries、durable entries、recent inputs 和 supporting evidence，但没有公开完整 memory schema，不能断言其中包含 authority 字段。
- 因此，“包含权威性的丰富数据结构”是自建治理型系统的可选设计，不是 Claude/Codex 已公开的统一实现。

一句话修正：

> **LLM 负责把对话抽象成记忆候选；代码负责把候选变成可审计数据；用户和治理流程负责赋予规则权威。**

### 0.3 Claude 没有 authority 字段，如何区别对待 memory

准确答案是：Claude 并不需要从单个 memory 文件中“读取权威值”。目前能确认的是一种 **基于来源载体和上下文包装的隐式待遇**，而不是显式权威字段。

可以概括为：

```text
单个文件内容
  + 文件来自 auto-memory 目录
  + 客户端注入时附带的 memory 使用说明
  + type 的语义分类
  + 当前任务中的代码/配置/用户指令
  = Claude 对该信息的实际处理方式
```

#### 官方能够确认的部分

Anthropic 官方文档确认：

- `MEMORY.md` 是 auto-memory 入口索引，前 200 行或 25KB 在每次会话开始时加载；
- 主题文件按需读取；
- auto memory 用于 Claude 自己发现的构建命令、调试经验、偏好和工作习惯；
- `CLAUDE.md` 是用户/团队编写的持久指导；
- `CLAUDE.md` 仍只是行为上下文，不是硬执行层；
- 用户可以查看、编辑和删除 auto memory。

这说明 Claude Code 在产品结构上已经把两类内容放入不同载体：

| 载体 | Claude 得到的来源语义 | 应有待遇 |
|---|---|---|
| Auto memory | Claude 历史上保存的辅助上下文 | 可以参考，可能陈旧 |
| `CLAUDE.md` | 用户/团队明确维护的持久指导 | 应尝试遵守，但不是硬执行层 |
| 当前代码/配置/测试 | 当前可验证状态 | 用于核对事实 |
| 权限/Hook/沙箱 | 客户端执行控制 | 确定性允许或拒绝 |

官方没有公开一个数值 authority 计算器，也没有说明 `type: feedback` 比 `type: reference` 拥有更高的规范权威。因此不能把 `type` 当作权威等级。

#### 参考自 Claude Code 社区逆向工程的包装机制

以下观察来自 `E:\ClaudeCode\claude-code-main`，是 **Claude Code 社区逆向工程复原，不是 Anthropic 官方实现**：

- `src/memdir/memdir.ts` 的 `buildMemoryLines(...)` 在注入 memory 前构造统一的行为说明，而不是给每个文件计算 authority；
- `src/memdir/memoryTypes.ts` 将内容分为 `user`、`feedback`、`project`、`reference`，这些类型说明“内容是什么”，不是“必须服从到什么程度”；
- 同一提示要求 memory 错误或过时时更新/删除，避免重复；
- `MEMORY_DRIFT_CAVEAT` 要求使用 memory 前检查当前文件或资源，冲突时信任当前观察并修改陈旧 memory；
- `TRUSTING_RECALL_SECTION` 明确把 memory 中的文件、函数和 flag 视为“写入当时存在的主张”，在给出行动建议前要重新检查。

因此，在该逆向工程中，Claude 接收到的逻辑更接近：

```text
“下面是 auto memory。它可能对当前任务有用，也可能已经陈旧；
具体事实使用前请检查当前状态；用户要求忽略时不要使用。”
```

而不是：

```text
memory.authority == 3，所以服从
```

#### `type` 字段到底做什么

本机 memory 中可见的 `type: feedback`、`type: reference` 主要帮助 Claude理解内容的语义用途：

- `user`：用户角色、目标、知识和偏好；
- `feedback`：用户对协作方式的反馈；
- `project`：无法从当前代码直接推导的持续项目上下文；
- `reference`：外部系统和资料入口。

即使是 `feedback`，也不等于绝对规则。例如“用户通常喜欢先看计划”可以影响协作方式，但不能覆盖用户当前明确说“直接修改”。如果反馈确实要成为项目长期规范，应由用户写入或批准写入 `CLAUDE.md`/项目指导。

#### 权威信息实际来自哪里

Claude 对信息的“权威待遇”主要来自：

1. **来源身份：** auto memory、当前用户消息、`CLAUDE.md`、工具结果还是客户端策略；
2. **注入包装：** 客户端如何向模型说明这类内容应被怎样使用；
3. **当前性：** 是否能被当前代码、配置、测试或外部资源验证；
4. **冲突关系：** 当前用户是否给出新要求，项目指导是否与 memory 冲突；
5. **执行层：** 是否有权限、Hook 或沙箱真正强制。

这是一种“上下文 provenance + 元指令 + 当前验证”的隐式编码。

#### 本项目实例

`conversation_local_save.md` 与当前 `AGENTS.md` 已经冲突：memory 仍写“所有技术讨论都保存”，当前项目指导只要求保存 AI Agent 学习内容。

Claude 如果同时读取两者，应把 auto memory 识别为旧历史，把当前项目指导视为当前规则。但由于没有 `updated_at`、`verified_at` 或 `authority` 字段，这一纠错依赖上下文包装和 LLM 的冲突识别，并非数据库保证。最可靠的处理仍是更新或删除陈旧 memory。

一句话总结：

> **Claude 不是从 memory 文件里读取权威字段，而是从“它来自 auto memory”这一来源、客户端附带的使用说明、内容类型以及当前证据中推断如何对待；这是一种隐式信任模型，不是显式权威模型。**

### 0.4 以本次长对话为例：哪些信息应被提取

长对话不等于需要生成大量 memory。提取器首先判断信息是否值得 **跨会话额外保存**，而不是把对话压缩后全部搬进 memory。

#### 判断顺序

参考 Anthropic 官方对 auto memory 的定位，以及 Claude Code 社区逆向工程中的 memory prompt，可以把判断顺序概括为：

```text
1. 是否只对当前任务有用？              是 → 不存
2. 是否已在代码、Git、AGENTS.md 或文档？ 是 → 不重复存
3. 是否包含秘密或敏感信息？             是 → 不存/脱敏
4. 是否对未来会话有明确价值？           否 → 不存
5. 是否具有一定稳定性和清晰作用域？      否 → 不存或仅作候选
6. 是否能用较低成本重新获得？            是 → 优先下次重读来源
7. 是否是用户背景、反馈、非代码项目状态或外部引用？ 是 → 可存
```

这里不一定存在数值 `weight`。对 Claude Code 当前可见机制，更接近 LLM 按提示做语义准入，然后用 `type` 分类、用 `description` 和 `MEMORY.md` 索引支持未来相关性判断。

#### 本次对话的具体分类

| 对话信息 | 是否保留为 auto memory | 原因 |
|---|---:|---|
| “AI Agent 方案默认依据 Anthropic/OpenAI 官方资料” | **不应重复保存** | 已明确写入项目 `AGENTS.md`，项目指导是更合适载体 |
| “可以参考 `E:\ClaudeCode\claude-code-main`，但必须标注社区逆向工程” | **不应重复保存** | 已写入 `AGENTS.md`，下次可直接读取 |
| “只保存 AI Agent 学习相关讨论” | **不应重复保存** | 当前项目规则已记录；旧 auto-memory 反而应更新/删除 |
| 关于权威、验证、晋级和架构决策的最终结论 | **不应保存到 auto memory** | 已整理进本项目研究文档，可从仓库恢复且更可审查 |
| OpenAI/Anthropic 官方链接和当前阈值 | **通常不存** | 产品信息可能变化，应下次重新查官方文档 |
| 工具调用输出、文件行数、补丁过程 | **舍弃** | 仅用于当前操作，长期价值低 |
| 曾经找不到 `codex` 命令 | **舍弃** | 一次环境状态，容易变化 |
| 本机 Claude memory 目录位置 | **通常不存** | 可由固定规则重新计算/检查；已写入研究实例文档 |
| 用户持续使用简体中文 | **可保留，但已有 memory** | 跨项目/跨会话协作偏好；应更新已有条目而不是重复创建 |
| 用户在研究上反复强调“不要让自动 memory 获得规则权威” | **谨慎，可视为研究立场；本项目中不必存** | 已成为项目文档内容；除非用户明确说这是其跨项目长期偏好 |

因此，本次长对话对 Claude auto-memory 的理想新增结果很可能是：

```text
no_memory
```

或者最多更新已有的 `user_language.md` / 纠正陈旧的 `conversation_local_save.md`，而不是创建多条关于记忆机制的新 memory。研究结论应该留在仓库文档中。

#### “哪些保留”的语义信号

| 信号 | 倾向 |
|---|---|
| 用户明确说“以后都这样”“请记住” | 提高保存候选概率，但仍需区分 memory 与项目规则 |
| 多次纠正同一种协作方式 | 倾向保存为 `feedback` |
| 跨会话仍有用且无法从仓库推导 | 倾向保存 |
| 有明确来源、原因和适用范围 | 倾向保存 |
| 只对当前任务有用 | 舍弃 |
| 可从代码、Git、项目文档低成本恢复 | 舍弃或只保存引用入口 |
| 容易过时的当前产品事实 | 舍弃，下次重新核验 |
| 原始日志、大段工具结果、重复解释 | 舍弃或只提炼非显然经验 |

#### “权重高”实际意味着什么

在没有显式权重字段时，“高权重”通常不是一个存储数值，而是以下实际待遇之一：

- 被加入 `MEMORY.md` 索引，因此每次会话启动时可见；
- `description` 写得更明确，更容易在相关任务中被选择；
- 被归类为 `feedback` 或 `user`，触发特定使用方式；
- 在相关任务中主动读取主题文件；
- 冲突时先检查当前证据，而不是直接相信记忆。

所以，Claude Code 的判断更接近：

> **LLM 根据未来效用、稳定性、可重建性、来源和作用域做语义筛选；文件索引和上下文包装决定未来可见度；当前证据决定是否采用。**

参考自 Claude Code 社区逆向工程的具体限制：其 memory prompt 明确排除可从项目状态、Git、`CLAUDE.md` 推导的内容以及当前任务临时状态，并要求先检查既有 memory、避免重复、更新或删除陈旧内容。这些是社区逆向工程观察，不是 Anthropic 官方实现保证。

## 1. 本文所说的“权威”是什么

“权威”不是所有产品都公开定义的数据字段。本文把它作为一个工程分析术语：

> **某条信息在决定 Agent 行为时，被允许直接采用的程度，以及发生冲突时的优先地位。**

这个定义包含两类问题，必须分开：

- **规范性问题**：“必须运行哪些测试”“禁止修改哪些目录”。答案来自有授权的规则制定者。
- **事实性问题**：“项目当前使用 PostgreSQL 还是 MySQL”“这个命令是否仍有效”。答案来自可验证的当前状态。

同一个载体对两类问题的权威并不相同。例如，`AGENTS.md` 很适合表达团队规范，但其中写的依赖版本仍可能落后于锁文件。

### 1.1 不要混淆“载体”与“真值”

Git 入库只能证明内容可审查、可共享、可追踪，不能证明内容永远正确。自动记忆保存在本地，也不意味着它一定错误。

更准确的判断是：

```text
行为决策 = 指令优先级 + 来源授权 + 当前证据 + 任务风险
```

而不是：

```text
入库文件 = 永远正确
自动记忆 = 永远不可信
```

## 2. 官方产品实际承诺了什么

本节只陈述官方文档能够直接支持的内容。没有公开保证的内部实现，不作为事实写入。

### 2.1 OpenAI Codex：AGENTS.md 是持久指导，memories 是辅助回忆

OpenAI 当前官方文档明确建议：

- 必须长期生效的团队指导应放在 `AGENTS.md` 或入库文档中；
- memories 应作为辅助回忆层，而不是必须始终执行的规则的唯一来源；
- 本地 Codex memories 默认关闭，启用后会从符合条件的历史任务中后台生成；
- memories 位于 `~/.codex/memories/`，属于生成状态，可检查，但不应把手工编辑这些生成文件当作主要控制面；
- 可以分别控制是否从任务生成记忆，以及是否向新会话注入既有记忆。

因此，对 Codex 最稳妥的工程解释是：

| 载体 | 官方定位 | 工程待遇 |
|---|---|---|
| `AGENTS.md` / 入库文档 | 持久项目指导 | 用于团队规则、命令、约定和验证要求 |
| Local memories | 跨任务辅助回忆 | 用作候选上下文；重要事实使用前复核 |
| 当前代码、配置、测试 | 当前项目状态 | 用于验证事实是否仍成立 |

Codex 会在一次运行开始时建立 `AGENTS.md` 指令链：从全局范围开始，再从项目根目录走到当前工作目录；越靠近当前目录的文件越晚进入合并提示，因而可以覆盖较早的指导。默认合并大小上限为 32 KiB。

需要注意：这描述的是 **Codex 的 AGENTS.md 发现与合并规则**，不能直接套用到 Claude Code。

### 2.2 Claude Code：CLAUDE.md 与 auto memory 的角色不同

Anthropic 官方文档将两者区分为：

| 载体 | 谁写 | 适合内容 | 加载方式 |
|---|---|---|---|
| `CLAUDE.md` | 用户/团队 | 编码规范、工作流、架构、长期规则 | 每个会话加载 |
| Auto memory | Claude | 构建命令、调试经验、偏好、发现的模式 | `MEMORY.md` 的前 200 行或 25KB 在会话开始时加载，专题文件按需读取 |

Claude Code 的 auto memory 默认开启，按项目存放于 `~/.claude/projects/<project>/memory/`，是机器本地 Markdown 文件，用户可以审计、编辑或删除。

更关键的是，Anthropic 明确说明：

- `CLAUDE.md` 内容作为系统提示之后的 user message 交付，不属于系统提示本身；
- Claude 会尝试遵守，但对模糊或冲突的指令不保证严格合规；
- settings、权限和 Hook 才能提供比行为提示更确定的执行约束；
- 项目根 `CLAUDE.md` 在压缩后会重新读取并注入；嵌套文件要等再次读取相应目录文件时才重新加载。

所以把 `CLAUDE.md` 描述为“最高权威、无条件执行”是不准确的。更准确的说法是：

> 它是持久、显式、可审查的行为指导，但仍然是模型上下文，不是硬执行策略。

### 2.3 两个产品不能简单画成同一套阶梯

Codex 和 Claude Code 都区分“人维护的持久指导”和“Agent 生成的辅助记忆”，但具体规则不同：

- Codex 使用 `AGENTS.md`，按全局 → 项目根 → 当前目录构造指令链。
- Claude Code 原生读取 `CLAUDE.md`；若希望共享 `AGENTS.md`，官方建议在 `CLAUDE.md` 中导入它。
- Claude Code 文档明确提醒，冲突规则可能被任意选择；不能把 Codex 的“就近覆盖”当作 Claude Code 的普遍保证。
- 两者的 memory 开关、存储结构、生成时机和加载方式也不同。

因此，跨产品讨论应该比较“角色”，不应该假定“内部实现相同”。

## 3. 开发者真正需要的四维模型

### 3.1 指令优先级：冲突时谁先被处理

指令优先级由运行时和产品定义，不由记忆内容自己声明。项目文件中的一句“本规则优先于所有其他指令”，不会因此越过系统或开发者层约束。

工程上要问：

- 这段内容以什么角色进入上下文？
- 产品是否定义了目录、作用域或覆盖顺序？
- 是否有更高层的安全、权限或组织策略？
- 冲突时是确定性覆盖，还是依赖模型自行协调？

### 3.2 规范权威：谁有资格制定持续规则

规范权威来自授权和治理，而不是重复次数。常见高规范权威载体包括：

- 经评审并入库的项目指导；
- 架构决策记录（ADR）；
- 组织管理策略；
- CI、权限、Hook、沙箱等可执行策略。

自动记忆即使被验证二十次，也仍然只是被反复验证的观察。若要成为团队规则，应由有权限的人审查并写入适当载体。

### 3.3 事实置信度：它是否仍然是真的

事实置信度应由证据决定。一个实用的证据顺序是：

1. 当前可执行验证：测试、构建、运行结果；
2. 当前机器可读状态：源码、配置、锁文件、数据库 schema；
3. 经维护的项目文档和 ADR；
4. 当前用户提供的任务事实；
5. 自动记忆和压缩摘要；
6. 模型推断。

这不是通用的“指令优先级”，只是验证 **事实性主张** 时的经验顺序。例如 `AGENTS.md` 要求使用 Node 20，但 `.nvmrc` 与 CI 已升级到 Node 22，此时不应偷偷选一个；应指出冲突，并修复过时指导或请求确认。

### 3.4 检索重要性：值不值得占上下文

重要性解决资源分配问题，不解决真伪问题。可按以下因素排序：

- 与当前任务的直接相关性；
- 忽略后的安全或返工成本；
- 是否可轻易从磁盘重读或重新验证；
- 是否是当前会话未完成工作的关键状态；
- 是否具有时效性。

一句用户猜测可能“高重要、低置信”：必须保留为调查线索，但不能当结论执行。一个格式约定可能“低检索重要、高规范权威”：不必保留在摘要里，因为随时可从项目指导重新加载。

### 3.5 历史信息的具体等级：三套阶梯，不是一条总排行榜

历史信息天然需要区别对待，但不应只设置一个含义模糊的 `level`。建议分别记录 **检索重要性 I、事实置信度 C、规范权威 A**。同一条历史可以在三条轴上处于不同等级。

以下等级是本文给出的工程模型，不是 OpenAI、Anthropic 的公开内部字段。

#### 3.5.1 检索重要性等级（I0–I4）

它决定压缩、召回和上下文预算紧张时“先保留谁”。

| 等级 | 名称 | 典型信息 | 建议处理 |
|---|---|---|---|
| **I0 噪声** | 对当前及后续任务几乎无价值 | 空输出、重复确认、无信息量的失败调用、已被完整替代的中间结果 | 优先删除，不进入长期记忆 |
| **I1 可再生细节** | 有少量价值，但可低成本重建 | 旧目录列表、大段可重读文件内容、普通成功日志 | 压缩或仅保留来源位置 |
| **I2 有用背景** | 能减少重复探索 | 常用命令、普通偏好、已知模块关系、非关键历史决策 | 摘要保存，按任务召回 |
| **I3 任务关键** | 丢失会中断当前工作或导致明显返工 | 当前目标、未完成步骤、关键错误根因、用户本次约束、重要测试结果 | 高优先保留；压缩时保留结论、证据和下一步 |
| **I4 安全/治理关键** | 丢失可能导致安全、合规或不可逆后果 | 禁止操作、生产边界、授权限制、破坏性动作前置条件 | 不应只依赖会话历史；同时固化到权限、Hook、CI 或项目规则 |

重要性是动态的。例如，一份普通构建日志最初可能是 I1；一旦其中唯一的一行错误揭示了根因，该错误片段就变成 I3，而其余日志仍可保持 I1。

#### 3.5.2 事实置信度等级（C0–C4）

它决定“能否直接当作事实使用”。置信度必须基于来源和验证，而不是文本说得多肯定。

| 等级 | 名称 | 典型信息 | 建议处理 |
|---|---|---|---|
| **C0 无有效证据** | 没有形成事实证据 | 工具未执行、超时且无结果、权限拒绝、空结果被误解为“不存在” | 不得据此形成事实结论 |
| **C1 假设/单点回忆** | 可能有用但未经验证 | 模型推断、旧摘要、自动记忆中的陈旧线索、用户带“不确定”措辞的猜测 | 作为搜索线索，使用前验证 |
| **C2 有来源的观察** | 有直接来源，但范围或时效有限 | 单次成功工具输出、用户明确陈述、一次测试结果 | 标注时间和作用域；重要决策前复核 |
| **C3 多证据验证** | 当前多个独立证据一致 | 配置与运行结果一致、代码与测试共同支持、重复复现的错误 | 可作为当前任务事实使用 |
| **C4 受控事实** | 由权威系统持续保证或强验证 | schema、锁文件与 CI 一致，受策略管理的配置，签名/审计记录 | 高可信使用；仍保留版本和作用域边界 |

`C4` 也不是“永不变化”。升级、配置迁移或环境切换后，旧事实仍可能失效，因此置信度必须绑定时间、版本和作用域。

#### 3.5.3 规范权威等级（A0–A4）

它决定“这条内容有没有资格约束行为”。这不是事实真假评分。

| 等级 | 名称 | 典型信息 | 建议处理 |
|---|---|---|---|
| **A0 非规范信息** | 不构成规则 | 工具输出、模型分析、压缩摘要、事实观察 | 不能据此创造长期义务 |
| **A1 候选偏好** | 可能影响体验，但未形成持久授权 | Agent 推断的用户习惯、auto memory 中的偏好 | 可温和参考，不得覆盖明确要求 |
| **A2 当前任务指令** | 对本次任务有效 | 用户当前要求、任务范围、一次性禁止事项 | 在当前任务和上级约束允许范围内执行；不自动跨会话 |
| **A3 持久项目规范** | 经用户/团队维护、可审查、可版本化 | `AGENTS.md`、`CLAUDE.md`、项目规范、ADR 中的约定 | 按产品加载和作用域规则执行；发现过时或冲突时显式报告 |
| **A4 确定性策略** | 由运行时强制而非仅靠模型遵守 | 权限拒绝、沙箱、managed policy、Hook、CI 门禁 | 由系统执行；模型不能自行绕过 |

严格来说，A4 已经超出“记忆权威”，属于执行控制层。把它放在阶梯顶端，是为了提醒开发者：真正不可违反的规则必须从自然语言记忆晋级为机器可执行策略。

#### 3.5.4 为什么“失败的工具结果最低”只对了一半

应将“工具失败事件”和“失败返回的信息价值”分开：

| 场景 | I | C | A | 解释 |
|---|---:|---:|---:|---|
| 工具根本未执行，只有超时 | I0–I1 | C0 | A0 | 不能把超时解释为目标不存在或命令错误 |
| 权限层拒绝危险命令 | I3–I4 | C3 | A4 | 命令结果不存在，但“策略禁止该动作”本身是高价值、强制事实 |
| 测试执行失败并给出稳定堆栈 | I3 | C2–C3 | A0 | 失败内容可能是定位根因的关键证据 |
| 网络临时失败 | I1，若阻塞任务则 I3 | C1–C2 | A0 | 能证明当次请求失败，不能证明服务永久不可用 |
| 重复的同类失败，已有更完整记录 | I0–I1 | 继承主记录 | A0 | 去重后只保留代表性证据和次数 |

所以更准确的规则是：

> **无信息量、不可归因、已被替代的失败结果通常最低；能够证明约束、解释根因或阻塞当前任务的失败结果必须提高重要性。失败本身不自动降低证据价值。**

#### 3.5.5 常见历史信息的默认分级

以下是初始默认值，随后应按任务相关性、验证和作用域动态调整：

| 历史信息 | 默认 I | 默认 C | 默认 A |
|---|---:|---:|---:|
| 空工具结果、重复确认 | I0 | C0–C1 | A0 |
| 未验证的模型推断 | I1 | C1 | A0 |
| 压缩摘要中的二手事实 | I2 | C1 | A0 |
| 一次成功工具输出 | I1–I2 | C2 | A0 |
| 当前用户提出的事实猜测 | I2–I3 | C1–C2 | A0 |
| 当前用户明确任务约束 | I3–I4 | 不适用 | A2 |
| Auto/local memory 中的偏好 | I2 | C1–C2 | A1 |
| 当前代码、配置和测试的一致结果 | I3 | C3 | A0 |
| 经评审的项目指导或 ADR | I2–I4 | 对事实部分 C2–C3 | A3 |
| 权限、Hook、沙箱或 CI 拒绝 | I3–I4 | C3–C4 | A4 |

表中“不适用”表示该内容是规范性指令，不应硬套事实置信度。可以验证的是“用户是否说过这句话”和“它的作用域”，而不是给指令本身判真假。

#### 3.5.6 分级后的压缩与召回策略

可以采用以下简单决策：

```text
先看 A：A4/A3 的规则不依赖普通历史摘要保存，应从权威载体重新加载。
再看 I：I4/I3 保留；I2 摘要；I1 保留引用或可再生位置；I0 删除。
最后看 C：C0 不形成结论；C1 召回后验证；C2 标注来源与时间；C3/C4 可在作用域内采用。
```

这解释了为什么不能使用单一等级：A3 的格式规则可能只有 I1，因为随时可从 `AGENTS.md` 重读；一个关键失败堆栈可能是 I3/C3/A0，因为它非常重要且可信，却不是行为规范。

## 4. “晋级”到底是什么意思

原文最大的问题，是把置信度增长、检索频率增长和规范权威增长混成一件事。正确的模型应包含三条彼此独立的轴：

```text
重复观察 ──→ 置信度可能上升
任务相关 ──→ 检索优先级上升
人工审查并写入权威载体 ──→ 规范权威上升
```

### 4.1 不是晋级：重复观察与记忆保活

反复观察同一个模式，只能说明它更可能稳定。例如连续十次构建都需要 `pnpm`，可以提高“项目使用 pnpm”的置信度，也可以使它更值得召回。

但这不能自动推出：

- 团队永久禁止 npm；
- Agent 获得修改项目规则的授权；
- 以后无需检查 `packageManager`、锁文件或 CI。

### 4.2 真正的晋级：从观察变成经治理的规则

建议使用以下晋级流水线：

```text
聊天/工具观察
    ↓ 提取
候选记忆（带来源、时间和范围）
    ↓ 当前状态验证
可信事实或稳定模式
    ↓ 判断是否应长期约束团队
规则候选
    ↓ 人工/代码评审
AGENTS.md、CLAUDE.md、ADR、配置、Hook 或 CI
```

每道闸门分别回答：

1. **来源是什么？** 用户明确要求、工具结果，还是模型推断？
2. **能否复现？** 当前代码、配置或测试是否支持？
3. **作用域是什么？** 当前任务、单个开发者、子目录还是全项目？
4. **有效期是什么？** 一次性、版本相关，还是长期约定？
5. **是否规范性？** 它是在描述现状，还是要求以后都这样做？
6. **谁有权批准？** Agent、当前用户、代码所有者还是安全团队？
7. **应放在哪里？** 文档、ADR、Skill、配置、Hook、权限还是 CI？

### 4.3 用户纠正的正确处理

用户纠正通常是高价值信号，但仍要区分：

- “这次先不要修改测试”是当前任务约束，不应自动写成永久规则；
- “这个仓库永远使用 pnpm，请加入 AGENTS.md”是明确的持久化授权；
- “数据库是 PostgreSQL 16”是事实主张，应与配置核对；
- “所有迁移必须先备份”是规范性要求，若影响团队应进入评审过的项目指导或执行流程。

Agent 不应因为一句聊天消息看起来重要，就自行把它升级为永久团队政策。

### 4.4 自动记忆可以做什么

自动记忆适合：

- 保存重新探索成本较高的调试线索；
- 记录用户偏好和常用工作流；
- 记录“下次应先检查什么”；
- 为后续任务提供候选上下文。

自动记忆不适合单独承担：

- 安全边界；
- 合规要求；
- 破坏性操作许可；
- 团队必须执行的测试门禁；
- 需要精确、实时的生产事实。

### 4.5 自拟工程方案：记忆成熟度与规则外部化（M0–M5）

> **性质声明：** 本节是面向自建 Code Agent 的自拟工程方案，不是 OpenAI 或 Anthropic 的官方等级。官方资料只提供了边界条件：memory 是辅助上下文，持久指导应进入项目指令，确定性约束应由权限、Hook、沙箱或 CI 执行。
>
> **重要修正：M0–M3 是自动记忆的处理成熟度，不是权威等级；M4/M5 是经过用户或团队授权后的外部化目标，已经不属于自动记忆。**

#### 4.5.0 到底有没有必要区分记忆等级

如果“等级”表示 **约束权力**，则没有必要，而且不应该设置。模型自动提取的偏好、习惯和历史观察，无论被重复多少次，都不能仅凭内部评分变成绝对约束。

真正重要的规则应由用户或团队亲自维护、明确批准，进入 `AGENTS.md`、`CLAUDE.md`、ADR、权限、Hook 或 CI。自动记忆系统不能替用户立法。

如果“等级”表示 **处理状态**，则有必要区分，但只需要解决四个工程问题：

1. **降噪：** 原始历史中哪些内容值得进入长期存储？
2. **验证：** 记忆只是旧线索，还是已被当前状态证实？
3. **召回：** 哪些内容值得主动注入有限上下文？
4. **维护：** 哪些内容已经过时、矛盾、应降级或删除？

因此，更准确的命名不是“权威晋级”，而是：

```text
M0–M3：记忆成熟度（memory maturity）
M3 → M4：经人授权的规则外部化（governed externalization）
M4 → M5：规则的确定性执行化（policy enforcement）
```

一个小型系统甚至不必使用 M0–M3 的离散等级，只要为每条记忆保存 `source`、`verified_at`、`scope`、`expires_at`、`relevance` 和 `status` 等字段即可。离散等级的价值主要是让数据流、权限校验和审计更容易实现，并不是让模型获得更多权力。

#### 4.5.1 核心设计：成熟的是信息质量，权威只能来自外部授权

建议把一条信息的生命周期建模为：

```text
M0 原始事件
  ↓ 提取
M1 候选记忆
  ↓ 去重、分类、敏感信息检查
M2 已接纳记忆
  ↓ 当前状态验证
M3 已验证记忆
  ║ 到此为自动记忆系统的最高状态；仍然没有规范权力
  ╚═ 用户/团队明确批准并迁移出 memory
       ↓
     M4 受治理知识或项目规则（不是自动记忆）
       ↓ 工程评审并转译为机器可执行控制
     M5 强制策略（不是 memory）
```

“权力”在这里指系统被允许如何使用该信息，而不是让记忆自行执行代码。M0–M3 的变化只会增加检索、注入或有限默认能力；规范指导和强制执行必须来自 M4/M5 的外部授权。建议定义五种能力：

| 能力 | 含义 |
|---|---|
| **检索 R** | 可以在相关任务中被搜索或读取 |
| **注入 I** | 可以主动进入模型上下文 |
| **默认采用 D** | 低风险场景可以不再次询问而作为默认值 |
| **规范指导 G** | 可以作为项目行为规范约束方案选择 |
| **强制执行 E** | 可以确定性阻止或要求某个系统动作 |

#### 4.5.2 各等级的权力边界

| 等级 | 名称 | 存储形态 | R | I | D | G | E | 核心限制 |
|---|---|---|:---:|:---:|:---:|:---:|:---:|---|
| **M0** | 原始事件 | 对话、工具结果、审计日志 | 按需 | 否 | 否 | 否 | 否 | 只是发生过的记录，尚未抽取语义 |
| **M1** | 候选记忆 | 暂存区/候选表 | 是 | 否 | 否 | 否 | 否 | 可能重复、错误、敏感或无长期价值 |
| **M2** | 已接纳记忆 | 正式 memory store | 是 | 相关时可 | 否 | 否 | 否 | 只能作为线索；事实使用前验证 |
| **M3** | 已验证记忆 | memory + 证据引用 | 是 | 是 | 有条件 | 否 | 否 | 只在验证过的时间、版本和作用域内成立 |
| **M4** | 受治理知识/规则（非 memory） | `AGENTS.md`、`CLAUDE.md`、ADR、团队文档 | 是 | 按产品加载 | 是 | 是 | 否 | 用户/团队授权并迁移出自动记忆；仍是行为指导而非硬控制 |
| **M5** | 强制策略（非 memory） | 权限、Hook、沙箱、CI、policy-as-code | 不依赖记忆检索 | 不依赖模型注入 | 是 | 是 | 是 | 经工程评审转译为确定性系统机制 |

这里最重要的边界有三个：

1. **M2 不得默认执行。** 被记住只代表未来值得看一眼。
2. **M3 是自动记忆的终点。** 它不得自动变成团队规则；事实验证和规范授权是两套流程。
3. **M4/M5 不是更高级的自动记忆。** 它们是用户或团队批准后的外部治理产物，运行时不应依赖模型是否想起。

#### 4.5.3 每一级具体能做什么

**M0 原始事件：只能作为证据材料。**

- 保留原始时间、来源、工具调用 ID、退出码和内容哈希；
- 可供审计和重新抽取；
- 不允许直接注入长期上下文；
- 无信息量的失败结果可以在保留最小审计元数据后过期删除。

**M1 候选记忆：只能参与筛选。**

- 允许去重、分类、关联原始证据；
- 必须进行秘密、个人信息和提示注入风险检查；
- 不允许影响 Agent 当前决策；
- 被判定为可从代码轻易重建、纯临时状态或重复噪声时直接淘汰。

**M2 已接纳记忆：允许召回，不允许裁决。**

- 可以进入语义/关键词索引；
- 与当前任务相关时可作为提示注入；
- 必须携带来源、创建时间、作用域和验证状态；
- 可以建议“检查 X”，不能直接断言“X 当前仍成立”；
- 用户要求忽略或删除时，应停止使用并按产品能力处理。

**M3 已验证记忆：允许有限默认。**

- 必须绑定验证证据，例如文件版本、配置哈希、测试运行或外部资源版本；
- 在低风险、可逆且作用域匹配的情况下，可以作为默认值减少重复确认；
- 高风险动作前仍需实时验证；
- 证据发生变化、TTL 到期或出现反例时自动降级到 M2；
- 不得因为验证次数多就自动进入 M4。

**M4 受治理知识或项目规则：经人授权后迁移出 memory。**

- 必须有明确批准者、评审记录、作用域和目标载体；
- 描述“应该如何做”的内容进入 `AGENTS.md`、`CLAUDE.md` 或团队规范；
- 记录架构选择及理由的内容进入 ADR；
- 它可以成为 Agent 的持久行为指导，但模型仍可能误解、遗漏或受冲突指令影响；
- 过时后必须通过评审修改或撤销，不能只在 memory 中写一条相反内容。

**M5 强制策略：经工程评审后进入执行控制层。**

- 把“禁止删除生产数据”转译为权限拒绝、命令规则或沙箱边界；
- 把“提交前必须通过测试”转译为 CI 门禁；
- 把“每次编辑后必须执行检查”转译为 Hook；
- 必须支持审计、版本控制、回滚和紧急例外流程；
- Agent 没有自行晋级到 M5 或绕过 M5 的权力。

#### 4.5.4 晋级条件

| 迁移 | 必要条件 | 可自动完成吗？ |
|---|---|---|
| **M0 → M1** | 信息可能跨任务有用，且保留符合法规与隐私要求 | 可以，由抽取器完成 |
| **M1 → M2** | 去重完成、类型明确、来源可追踪、通过敏感信息检查 | 可以，由记忆服务完成 |
| **M2 → M3** | 当前证据验证通过，作用域与有效期明确 | 可以或半自动；高风险事实应人工确认 |
| **M3 → M4** | 用户/团队明确决定将其制定为规范，有授权者批准，并写入受治理载体 | **禁止由模型全自动完成** |
| **M4 → M5** | 规则可机器化、失败代价高、已有测试与回滚方案 | **必须工程评审** |

重复出现可以触发“请求验证”或“询问用户是否要固化”，不能直接跨越治理闸门。例如同一用户十次要求先跑测试，可以让 M2 候选获得更高检索优先级，但模型最多只能询问“是否写入项目规则”；只有用户或团队明确批准后，才能迁移到 M4；只有配置 CI 后，才成为 M5。

#### 4.5.5 晋级对自动记忆真正有什么意义

在 M0–M3 内，“晋级”的收益只有工程效率，不包含规范权力：

- **减少噪声：** 不必把所有对话和工具结果都注入未来会话；
- **减少重复探索：** 已验证的构建命令、调试入口和用户背景可更快召回；
- **降低陈旧风险：** M2 线索与 M3 已验证信息采用不同的使用策略；
- **控制上下文成本：** 只有相关、成熟的信息进入提示上下文；
- **支持纠错：** 有明确状态才能在证据变化时降级、更新或删除；
- **提供固化建议：** 稳定出现的模式可以提示用户是否要写入正式规则，但不能代替用户决定。

如果一个记忆系统没有验证、过期、召回预算或审计需求，那么设置复杂等级的收益很小；简单的“本地辅助记忆 + 使用前验证”反而更安全。

#### 4.5.6 降级、撤销与过期

完整系统必须支持双向状态迁移：

```text
证据变化：M3 → M2
用户纠正：M2/M3 → 更新或删除
规则废止：M4 → archived
策略回滚：M5 → M4 或 disabled
敏感信息发现：任意 M0–M3 → quarantined/delete
```

建议每次降级都保留原因和审计记录，而不是静默降低一个分数。对于错误记忆，删除错误内容通常比简单降低置信度更安全，防止它继续被检索污染上下文。

#### 4.5.7 与 I/C/A 三轴如何配合

M 等级描述生命周期和可用权限，I/C/A 描述当前属性，两者不能互相替代：

| M 等级 | 常见 I/C/A 状态 |
|---|---|
| M0 | 任意 I；通常 C0–C2；A0 或当前用户指令对应 A2 |
| M1 | I1–I3；C1；A0–A1 |
| M2 | I2–I3；C1–C2；A0–A1 |
| M3 | I2–I4；C3–C4；通常仍是 A0–A1 |
| M4（非 memory） | I 取决于任务；事实部分 C2–C4；A3 |
| M5（非 memory） | I/C 不再决定是否执行；A4 |

例如，“测试命令是 `pnpm test`”经过当前项目验证后可以成为 M3/C3；团队评审后写入 `AGENTS.md`，成为 M4/A3；CI 配置真正阻止未通过测试的合并后，相关要求才成为 M5/A4。

#### 4.5.8 参考自 Claude Code 社区逆向工程的启发

以下观察来自 `E:\ClaudeCode\claude-code-main`，它是 **Claude Code 社区逆向工程复原项目，不是 Anthropic 官方实现**：

- `src/memdir/memoryTypes.ts` 将记忆分为 `user`、`feedback`、`project`、`reference` 四类；这是内容类型，不是权威等级。
- 该文件要求从当前项目可推导的信息尽量不存入 memory，并要求在依赖 memory 中的文件、函数或 flag 前检查当前状态。
- `src/services/extractMemories/prompts.ts` 展示了候选内容经后台提取、去重并写入独立文件和 `MEMORY.md` 索引的思路。
- 逆向项目中的 private/team scope 提示说明“共享范围”与“内容类型”应分开建模；共享并不自动等于更可信或更有权威。

这些实现细节只能用于启发自建系统，不能表述为 Anthropic 官方 Claude Code 的确定内部实现。与 Anthropic 官方文档冲突时，以官方文档为准。

### 4.6 模型在什么情况下提取记忆

这一问题要区分三个层次：产品是否启动一次提取任务、提取器认为哪些内容值得保存、以及保存后的内容是否能成为规则。

#### 4.6.1 OpenAI Codex 官方公开的触发条件

根据 OpenAI 官方 Memories 文档，本地 Codex memory 的生成至少受以下条件控制：

| 条件 | 官方公开行为 |
|---|---|
| 功能开关 | Local memories 默认关闭，必须先启用 |
| 任务级同意 | 当前任务可以分别选择“使用既有记忆”和“贡献未来记忆” |
| 会话状态 | 跳过仍然活跃的会话，等待任务空闲后再后台处理 |
| 会话规模 | 跳过短生命周期会话 |
| 配额条件 | 剩余 rate-limit 百分比低于配置阈值时，可以跳过后台生成 |
| 外部上下文 | 配置 `memories.disable_on_external_context=true` 时，使用 MCP、web search 或 tool search 的任务不参与记忆生成 |
| 内容处理 | 从符合条件的历史任务中提取有用上下文，并对生成字段进行秘密脱敏 |

官方没有公开“多少消息算短会话”“空闲多久”“语义评分公式”或“某类内容必定保存”。因此不能把具体数字写成 Codex 官方机制。

#### 4.6.2 Anthropic Claude Code 官方公开的触发场景

根据 Anthropic 官方 memory 文档：

- Auto memory 默认开启；
- Claude 在工作过程中判断某条信息是否会对未来对话有用，并不保证每次会话都保存；
- 官方列举的候选内容包括构建命令、调试经验、架构笔记、代码风格偏好和工作流习惯；
- 用户明确要求“记住 X”时，Claude 会把它保存到 auto memory；
- Claude 可以在会话期间读写 memory 文件；用户可通过 `/memory` 审计、编辑和删除。

官方没有公开 Claude Code 自动提取的完整触发器、评分公式或最小消息数。可以确定的是“未来有用性”判断和用户显式请求，不能确定更细的内部阈值。

#### 4.6.3 参考自 Claude Code 社区逆向工程的触发流程

以下内容参考 `E:\ClaudeCode\claude-code-main`，属于 **Claude Code 社区逆向工程复原，不是 Anthropic 官方实现**：

- `src/services/extractMemories/extractMemories.ts` 在完整 query loop 结束、模型给出不再包含工具调用的最终响应后，尝试触发后台提取；
- 仅主代理参与，子代理跳过；关闭 auto memory、远程模式或功能门未开启时跳过；
- 如果主代理本轮已经直接写入 memory，后台 fork 提取器会跳过，避免重复写入；
- 提取器只处理上次游标之后新增的 model-visible messages；并发触发会合并为一个尾随任务；
- 复原代码存在“每 N 个 eligible turns 运行一次”的功能门控，仓库中的回退默认值为 1；这只是该逆向项目的实现，不能当作 Anthropic 官方常量；
- `src/services/extractMemories/prompts.ts` 要求提取器先检查现有 memory，更新已有主题而非制造重复文件。

这套逆向流程说明：**触发一次提取任务，不等于一定写入记忆。** 运行时触发器只决定“要不要检查”；真正的语义筛选由提取模型完成，完全可能得到“本轮无内容值得保存”。

#### 4.6.4 自拟工程方案：两级触发器

> 本节是自建 Agent 的工程建议，不是 OpenAI 或 Anthropic 官方实现。

建议把“什么时候运行提取器”和“提取什么内容”拆成两级，避免每轮都写 memory。

**第一级：运行触发器（是否启动 extraction job）**

| 触发场景 | 是否启动 | 时机 |
|---|---:|---|
| 用户明确说“记住 X” | 是 | 当前回合立即启动，不等会话结束 |
| 用户纠正模型，并说明以后都应避免/采用 | 是 | 当前完整 query loop 结束后 |
| 一个多步骤任务完成或形成稳定阶段结论 | 是 | 最终响应后异步启动 |
| 会话长时间空闲且产生了足够的新内容 | 是 | 空闲窗口到达后后台启动 |
| 只有寒暄、一次简单查询或极短会话 | 否 | — |
| 会话仍在执行工具或等待关键结果 | 否 | 延迟到稳定边界 |
| 本轮已经直接写入 memory | 否 | 去重，避免第二个提取器重复写 |
| 用户关闭记忆或禁止本任务用于记忆 | 否 | 硬门控 |
| 含无法安全脱敏的秘密或敏感内容 | 否 | 丢弃或隔离，不进入模型提取 |

一组可落地但需要通过评测调整的建议默认值：

```yaml
memory_extraction:
  enabled: true
  explicit_remember: immediate
  task_boundary: true
  idle_delay_seconds: 120
  min_new_model_messages: 4
  skip_short_session: true
  skip_if_direct_memory_write: true
  skip_if_external_context: true
  secret_scan_before_model: true
```

这些数字是自拟初始参数，不具有官方含义。显式“记住”可以越过 `min_new_model_messages`，但不能越过用户禁用、敏感数据和安全门控。

各字段含义如下：

| 字段 | 含义 | `true` / 当前值的行为 |
|---|---|---|
| `enabled` | 记忆提取总开关 | `true` 表示允许系统运行自动记忆提取；`false` 时其他触发条件全部失效 |
| `explicit_remember` | 用户明确要求记忆时的处理模式 | `immediate` 表示用户说“记住 X”后立即启动提取，不等待任务结束或空闲计时 |
| `task_boundary` | 是否在任务稳定边界触发提取 | `true` 表示任务完成、阶段完成或主 Agent 给出最终响应后，检查本阶段是否有内容值得保存 |
| `idle_delay_seconds` | 普通后台提取前要求的空闲时间 | `120` 表示会话连续空闲 120 秒后才允许启动，避免在用户仍可能继续补充时过早总结 |
| `min_new_model_messages` | 两次提取之间至少需要积累的新增模型可见消息数 | `4` 表示游标之后至少新增 4 条 user/assistant 消息才触发普通提取，用于过滤极短交互 |
| `skip_short_session` | 是否跳过短会话 | `true` 表示只有寒暄、单次简单问答或信息不足的会话不启动提取；实际“短”的判定需要结合消息数和内容 |
| `skip_if_direct_memory_write` | 主 Agent 已直接写 memory 时是否跳过后台提取 | `true` 表示本轮如果已经因“记住 X”等请求写入 memory，就不再启动第二个提取器，避免重复和并发覆盖 |
| `skip_if_external_context` | 使用外部上下文的任务是否排除出记忆生成 | `true` 表示会话使用 MCP、网页搜索或外部工具数据后默认不生成长期记忆，降低把第三方内容、敏感信息或提示注入固化的风险 |
| `secret_scan_before_model` | 是否在历史发送给记忆提取模型前扫描秘密 | `true` 表示先检测并删除/脱敏 API key、令牌、密码和其他敏感字段，再允许 LLM 读取候选历史 |

这些字段可以分成四类：

```text
总控制：enabled
强触发：explicit_remember、task_boundary
节流降噪：idle_delay_seconds、min_new_model_messages、skip_short_session
安全与一致性：skip_if_direct_memory_write、skip_if_external_context、secret_scan_before_model
```

字段之间存在优先级：

```text
用户禁用/总开关关闭
  > 秘密和安全门控
  > 显式 remember 强触发
  > 任务边界或空闲触发
  > 消息数量与短会话过滤
```

例如：

- 用户说“记住我使用 pnpm”：`explicit_remember=immediate`，即使不足 4 条新消息也可立即提取；
- 用户只是问“1+1 等于多少”：命中 `skip_short_session=true`，不提取；
- 长任务刚结束：`task_boundary=true`，立即检查候选，不必再等待 120 秒；
- 会话没有明确任务边界：空闲 120 秒且新增消息不少于 4 条后，启动后台检查；
- 本轮已经直接写入 memory：命中 `skip_if_direct_memory_write=true`，后台提取器跳过；
- 对话包含网页搜索结果：`skip_if_external_context=true` 时整次任务不进入自动记忆生成；如果产品需要保存，应改为更细粒度的“只允许保存用户原话，排除外部内容”。

**第二级：内容准入器（哪些候选可以写入 M2）**

建议只有同时满足以下条件的内容才进入长期 memory：

```text
未来跨会话可能有用
AND 不只是当前任务临时状态
AND 不能以很低成本从当前代码/配置重新推导
AND 来源与作用域可以记录
AND 不包含秘密或不应持久化的敏感信息
AND 不会被误解为模型自行制定的绝对规则
```

#### 4.6.5 应当提取的明确场景

| 场景 | 示例 | 保存类型 | 保存方式 |
|---|---|---|---|
| 用户显式要求记住 | “记住我本地调试习惯用 WSL” | preference/user | 立即保存，标明用户级作用域 |
| 用户对 Agent 的稳定反馈 | “以后解释迁移脚本时先说明回滚路径” | feedback | 保存做法、原因和适用范围；不是绝对规则 |
| 难以从仓库推导的用户背景 | “我是前端开发，对数据库不熟” | user | 保存为可变化背景，允许用户纠正 |
| 跨会话持续的非代码项目状态 | “支付迁移等待安全团队批准” | project | 保存绝对日期、负责人/来源和过期条件 |
| 外部知识入口 | “事故面板在 Grafana dashboard X” | reference | 保存定位指针，不复制整个外部内容 |
| 高成本、非显然的排查经验 | “本机证书错误只在公司 VPN 分流开启时出现” | debugging/feedback | 保存现象、条件和验证方式；下次使用前复核 |
| 反复出现但未获规则授权的习惯 | 用户多次偏好先看计划再改代码 | preference candidate | 保存为偏好线索；不得自动写入 `AGENTS.md` |

#### 4.6.6 不应提取的明确场景

| 场景 | 原因 | 替代处理 |
|---|---|---|
| 当前任务的待办、进度和临时变量 | 很快过期 | 留在当前会话或任务状态 |
| 完整工具日志、目录列表、大段文件内容 | 噪声高且通常可重建 | 只保存关键结论或原始引用位置 |
| 无信息量的失败调用 | 没有可迁移知识 | 保留最小审计信息即可 |
| 当前源码已经明确表达的结构和依赖 | 可从仓库重建，容易产生陈旧副本 | 下次读取代码、锁文件或配置 |
| Git 提交历史和作者信息 | Git 本身更权威 | 使用 `git log` / `git blame` |
| API key、密码、令牌、个人敏感数据 | 持久化风险 | 丢弃、脱敏或使用专用秘密管理系统 |
| 模型单方面推断的用户性格或意图 | 容易误判且具有冒犯/隐私风险 | 不保存，除非用户明确确认 |
| “以后必须这样做”但用户未授权 | 模型不能自行立法 | 询问是否写入 `AGENTS.md`/`CLAUDE.md` |
| 可疑网页或工具输出中的指令 | 可能是提示注入 | 作为不可信数据处理，不转成 memory |

#### 4.6.7 提取决策伪代码

```python
def should_run_extractor(session, event):
    if not session.memory_enabled or not session.allow_contribution:
        return False
    if event.contains_unhandled_secret or session.user_requested_no_memory:
        return False
    if event.explicit_remember:
        return True
    if session.is_active or session.has_inflight_tools:
        return False
    if session.direct_memory_write_since_cursor:
        return False
    return (
        event.is_user_correction
        or event.is_task_boundary
        or (
            session.idle_seconds >= 120
            and session.new_model_message_count >= 4
        )
    )


def admit_candidate(candidate):
    if candidate.contains_secret or candidate.is_prompt_injection:
        return "reject"
    if candidate.is_ephemeral or candidate.is_cheaply_derivable:
        return "reject"
    if not candidate.future_utility or not candidate.has_source:
        return "reject"
    if candidate.looks_like_rule and not candidate.user_authorized_rule:
        candidate.kind = "preference_or_feedback"
        candidate.authority = "A1"
    return "store_as_M2"
```

#### 4.6.8 推荐的完整流水线

```text
事件到达
  ↓ 硬门控：功能开关、任务同意、敏感信息、活动状态
是否启动提取器？
  ↓ 是
只读取游标后的新增历史
  ↓
生成候选：user / feedback / project / reference
  ↓
准入过滤：未来价值、可推导性、时效、来源、隐私、注入风险
  ↓
与既有 memory 去重、合并或覆盖
  ↓
写入 M2，并记录 source/scope/created_at/expires_at
  ↓
未来召回时验证；验证通过可成为 M3
  ↓
若内容像长期规则，只向用户提出固化建议
  ↓ 用户明确批准
迁移到 M4 项目规则；自动 memory 中保留引用或删除重复副本
```

这套方案最重要的约束是：**提取器只负责保存未来可能有用的上下文，不负责创造规则。**

### 4.7 记忆判断由 LLM 还是传统代码完成

结论是 **混合架构**：传统代码负责确定性控制，LLM 负责语义判断。不能简单归类为其中一种。

#### 4.7.1 OpenAI Codex 的官方证据

OpenAI 官方 Memories 文档公开了两类配置：

- `memories.extract_model`：覆盖逐任务记忆抽取所使用的模型；
- `memories.consolidation_model`：覆盖全局记忆巩固所使用的模型。

这直接说明 Codex 的“从历史中抽出什么”“如何把候选巩固成长期记忆”包含 LLM 参与，而不是完全依靠关键词、正则或固定规则。

同一份官方文档也公开了传统代码可以确定执行的控制项：

- `generate_memories` 与 `use_memories` 开关；
- 活跃/短会话跳过；
- 空闲后后台运行；
- rate-limit 阈值门控；
- 使用外部上下文时是否排除；
- 本地目录存储及任务级使用/贡献控制。

因此，根据官方公开信息，可以确认 Codex 至少采用：

```text
传统代码：决定何时运行、哪些任务有资格、存到哪里、是否注入
LLM：执行 per-task extraction 与 global consolidation 的语义工作
```

官方没有公开具体抽取 prompt、评分公式、模型输出 schema、去重算法和完整调度实现，不能进一步假定其内部细节。

#### 4.7.2 Anthropic Claude Code 的官方证据

Anthropic 官方文档明确表述：Claude 判断哪些信息对未来对话有用，并在工作过程中把笔记写入 auto memory；用户明确要求“记住 X”时也会保存。

这说明内容选择至少包含模型语义判断。传统代码仍然负责：

- auto memory 功能开关；
- memory 目录计算；
- `MEMORY.md` 的启动加载上限；
- 专题文件按需读取；
- `/memory` 管理入口；
- 文件读写和持久化。

Anthropic 官方没有公开完整的自动提取调度代码、抽取模型是否与主对话模型相同、具体 prompt 或内部阈值。因此只能确认“Claude 做语义选择 + 客户端做确定性管理”，不能仅凭官方文档断言更细的实现。

#### 4.7.3 参考自 Claude Code 社区逆向工程的补充

以下观察来自 `E:\ClaudeCode\claude-code-main`，是 **Claude Code 社区逆向工程复原，不是 Anthropic 官方实现**：

- `src/services/extractMemories/extractMemories.ts` 使用 `runForkedAgent(...)` 启动一个 memory extraction agent；
- `src/services/extractMemories/prompts.ts` 为该提取 agent 构造语义抽取 prompt，并让它判断是否创建、更新或不写入 memory；
- 传统 TypeScript 代码负责 feature gate、auto-memory 开关、主/子代理过滤、remote mode、频率门控、游标、并发合并和工具权限；
- 提取 agent 只允许读操作和在 memory 目录内写入，说明 LLM 的判断能力被传统权限代码包围；
- 一次提取任务可以最终写入零个文件，说明“代码触发检查”与“LLM 决定有内容值得保存”是两个不同阶段。

这个逆向工程与官方公开的混合边界相符，但其中的 `runForkedAgent`、功能门名称、默认频率和工具列表不能表述为 Anthropic 官方事实。

#### 4.7.4 两者的职责分工

| 环节 | 更适合传统代码 | 更适合 LLM |
|---|---:|---:|
| 功能开关、用户同意 | ✓ | |
| 会话是否空闲、消息数量、配额 | ✓ | |
| 秘密扫描、路径权限、写入范围 | ✓ | 辅助识别，但不能单独负责 |
| 游标、去重键、并发、事务 | ✓ | |
| 判断内容是否具有跨会话价值 | | ✓ |
| 将多轮对话抽象成简洁记忆 | | ✓ |
| 区分偏好、反馈、项目状态、引用 | 先做 schema 校验 | ✓ 语义分类 |
| 检查事实当前是否仍成立 | 调工具和比对结果 | ✓ 规划验证、解释冲突 |
| 最终写入 schema 和字段校验 | ✓ | 生成候选内容 |
| 把内容升级为团队规则 | 用户/评审流程 | 不允许模型自行决定 |

#### 4.7.5 为什么不能只用传统代码

传统代码擅长判断“消息数是否大于 4”“是否包含密钥格式”“工具是否仍在运行”，但很难可靠判断：

- 用户的一句话是临时要求还是稳定偏好；
- 一次失败中真正可迁移的经验是什么；
- 多轮对话中哪条纠正具有未来价值；
- 两段不同措辞是否表达同一个经验。

这些是开放语义问题，LLM 更适合生成候选。

#### 4.7.6 为什么不能只用 LLM

如果全部交给 LLM，会出现：

- 每轮是否运行不可预测，成本和延迟失控；
- 可能保存秘密、临时状态或提示注入内容；
- 重复写入、并发覆盖和文件损坏；
- 模型把自己的推断保存成“用户事实”；
- 模型自行把习惯升级成规则。

因此必须由传统代码建立硬边界，并把 LLM 输出视为候选数据：

```text
代码门控
  → LLM 生成结构化候选
  → 代码校验 schema、来源、敏感信息和作用域
  → 去重/合并
  → 写入辅助 memory
  → 使用前由代码取当前证据，LLM解释证据
```

一句话总结：

> **代码决定“能不能提取、什么时候提取、允许写到哪里”；LLM 决定“历史中什么值得记、如何概括”。规则权威仍由用户和治理流程决定。**

### 4.8 提取方案的来源、Token 成本与硬编码实现

#### 4.8.1 上一组 YAML 是如何得到的

`memory_extraction` YAML 是本文的自拟工程配置，不是从 Claude Code 或 Codex 官方配置中复制的。每个字段的来源性质如下：

| 自拟字段 | 设计依据 | 来源性质 |
|---|---|---|
| `enabled` | 两家产品都提供 memory 开关 | 官方边界的抽象 |
| `explicit_remember` | Anthropic 官方说明用户说“记住 X”时会保存；Codex 提供任务级贡献控制 | 官方场景的抽象 |
| `task_boundary` | 只在稳定工作边界提取可避免处理中状态被过早固化 | 自拟工程策略；社区逆向工程也在完整 query loop 后触发 |
| `idle_delay_seconds` | OpenAI 官方说明 Codex 等待任务空闲后后台更新 | 官方原则 + 自拟数值；`120` 不是官方值 |
| `min_new_model_messages` | 用于跳过极短交互、控制成本 | 自拟工程策略；`4` 不是官方值 |
| `skip_short_session` | OpenAI 官方明确说 Codex 跳过短生命周期会话 | 官方边界的抽象 |
| `skip_if_direct_memory_write` | 防止显式写入与后台抽取重复 | 参考自 Claude Code 社区逆向工程的互斥思路 |
| `skip_if_external_context` | Codex 官方提供 `disable_on_external_context` 配置 | 官方配置的通用化命名 |
| `secret_scan_before_model` | OpenAI 官方说明生成 memory 字段会做秘密脱敏；提前扫描可减少模型接触秘密 | 官方安全边界 + 自拟的前置防护方案 |

因此，这套配置应理解为“基于官方边界设计的参考接口”，不能描述为任一产品的真实配置格式。

#### 4.8.2 是否每轮对话都由 LLM 判断

不应该默认每轮都调用一次额外 LLM。需要区分三件事：

1. **每轮运行廉价代码门控：** 检查开关、消息数、是否空闲、是否有显式 remember、是否有工具在运行。
2. **满足触发条件后才运行 LLM 提取器：** 例如显式请求、任务完成或累计足够新增内容。
3. **较低频率运行 consolidation：** 合并重复记忆、清理陈旧条目，而不是每轮执行。

官方并未公开 Claude Code 是否在每一轮都调用额外 LLM。参考自 Claude Code 社区逆向工程的复原代码，会在完整 query loop 后尝试进入提取流程，但仍有功能门、频率门、主代理限制和直接写入互斥；“尝试触发”也不等于每次都产生记忆。

Codex 官方说明记忆在后台生成、等待任务空闲、跳过活跃或短会话，并可因 rate-limit 余额不足跳过。这些公开行为不支持“每轮必定执行一次完整 LLM 提取”的说法。

#### 4.8.3 Token 开销会不会过大

如果每一轮都把完整会话再次发给提取模型，开销确实会快速增长。假设第 `i` 轮累计历史为 `H_i` tokens：

```text
错误方案：每轮重读完整历史
总输入 ≈ H_1 + H_2 + ... + H_n
历史线性增长时，总开销接近 O(n²)
```

更合理的是维护消息游标，只读取上次提取后的增量 `ΔH_i`：

```text
增量方案：只处理新消息
总输入 ≈ ΣΔH_i + 每次固定提取 prompt
历史只被语义处理一次，主体开销接近 O(n)
```

但即使使用增量方案，若每轮都启动模型，固定 prompt、输出和请求延迟仍然明显。因此应继续采用批处理和事件触发。

参考自 Claude Code 社区逆向工程的复原代码使用消息 UUID 游标，只考虑上次位置后的新消息，并用 forked agent 共享父对话的 prompt cache。后者只能说明该逆向项目的优化思路，不能当作 Anthropic 官方成本承诺。

#### 4.8.4 哪些判断可以完全硬编码

以下判断适合传统代码，不需要 LLM：

| 判断 | 硬编码方法 |
|---|---|
| 功能是否开启 | 布尔配置 |
| 用户是否允许本任务贡献记忆 | 任务级枚举/开关 |
| 是否达到空闲时间 | monotonic clock / timer |
| 新增消息是否达到阈值 | 游标 + 计数器 |
| 是否存在未完成工具调用 | query-loop 状态机 |
| 是否已经写过 memory | write event / 路径审计 |
| 是否为短会话 | 消息数、有效字符数、工具次数阈值 |
| 是否使用外部上下文 | MCP/web/tool-search 事件标记 |
| 是否包含常见秘密 | secret scanner、熵检测、已知 token 格式 |
| 是否重复 | 内容哈希、规范化精确匹配 |
| TTL 是否到期 | 时间字段比较 |
| 是否允许写入目标路径 | 路径白名单、沙箱权限 |

显式 remember 也可以通过结构化 UI 或命令完全硬编码，例如 `/remember <text>`、`remember=true` 按钮或 API 字段。这比只靠自然语言正则更可靠。

#### 4.8.5 哪些判断不适合只靠硬编码

纯规则很难可靠处理：

- “以后解释迁移时先说回滚方案”是长期反馈还是本次抱怨；
- 一个长错误日志中真正值得迁移的经验是什么；
- 两段不同措辞是否表达同一个偏好；
- 某条信息能否从代码轻易推导；
- 用户的纠正适用于全项目、某个目录还是一次任务；
- 如何将十轮对话压缩成一句不失真的记忆。

可以堆叠关键词和正则，但规则会迅速膨胀，并对否定、反讽、条件句和多语言表达非常脆弱。例如“不要记住这个”“我不是说以后都这样”都可能被简单的 `记住|以后|总是` 正则误判。

#### 4.8.6 推荐方案：代码优先、LLM 按需

> 以下为自拟工程建议。

建议使用三级流水线：

```text
Level 0：每轮纯代码门控，零额外 LLM token
  - 开关、同意、空闲、消息数、工具状态、秘密扫描
  - 80%–95% 的普通回合在此直接跳过（目标值，需通过真实流量评测）

Level 1：候选触发后调用轻量语义提取
  - 只发送游标后的增量消息
  - 强制输出结构化候选或 no_memory
  - 候选只能写入 M1/M2，不产生规则权威

Level 2：低频 consolidation
  - 会话结束、累计候选达到阈值或定时后台执行
  - 合并重复、处理矛盾、建议删除陈旧内容
  - 不自动写入 AGENTS.md/CLAUDE.md
```

其中“80%–95% 跳过”是成本控制目标，不是官方统计，也不是未经评测即可保证的结果。

#### 4.8.7 更节省 Token 的具体策略

1. **显式请求走代码路径：** `/remember` 直接形成候选，不先调用分类模型；只在需要摘要或分类时调用 LLM。
2. **维护增量游标：** 绝不重复发送已处理历史。
3. **先用规则过滤：** 空回复、重复日志、可重读工具结果和寒暄先删除。
4. **批量提取：** 累积多个有效回合后一次调用，而非每轮调用。
5. **限制输入：** 只发送 user/assistant 语义消息及关键工具摘要，不发送完整工具原文。
6. **结构化短输出：** 允许 `no_memory`，候选限制条数和字段长度。
7. **低频巩固：** 合并任务按数量、时间或存储大小触发。
8. **缓存与内容哈希：** 同一增量不重复分析；失败可幂等重试。
9. **预算门控：** 达到每日 token/费用预算后停止非必要提取。
10. **离线评测：** 用真实会话标注“该记/不该记”，调节硬规则召回率和 LLM 调用率。

#### 4.8.8 一个可实现的混合伪代码

```python
def on_turn_complete(session, turn):
    # 纯代码路径
    if not session.memory_enabled or not session.allow_contribution:
        return
    if session.has_inflight_tools or contains_secret(turn):
        return

    if turn.command == "/remember":
        candidate = make_candidate_from_explicit_text(turn.payload)
        validate_and_store(candidate)  # 必要时再用 LLM 摘要/分类
        return

    session.pending_messages.extend(normalize(turn))

    if not hard_trigger_reached(session):
        return  # 大多数回合在这里结束，零额外 LLM 调用

    delta = session.pending_messages
    session.pending_messages = []

    result = extraction_model.generate(
        messages=delta,
        schema=MemoryCandidatesOrNoMemory,
        max_candidates=3,
    )

    for candidate in result.candidates:
        if code_policy_accepts(candidate):
            deduplicate_and_store(candidate, lifecycle="M2")
```

最终建议是：

> **硬编码负责高精度地排除“不该运行”和“不该保存”的情况；LLM 只处理规则难以表达的语义候选。不要每轮把完整上下文交给 LLM 重新判断。**

### 4.9 “记忆晋级/退化”是不是伪命题

对 Claude Code 当前公开机制而言，如果“晋级/退化”指一条 memory 通过 `confidence`、`level`、`verified_at` 等字段自动改变权威等级，那么 **没有官方证据表明存在这套机制**。本机实际 memory 文件也只有 `name`、`description`、`type` 和 Markdown 正文，没有显式等级。

因此必须区分两种说法：

| 说法 | 是否成立 | 含义 |
|---|---|---|
| Claude memory 有显式 M0–M3 状态机 | 没有证据，不能这样描述 | M0–M3 是本文自拟方案 |
| Claude memory 会创建、改写、召回、忽略或删除 | 官方文档支持这些外部行为 | 这是文件级、语义级生命周期，不是字段升级 |
| Claude memory 会自动晋级为 CLAUDE.md 规则 | 不成立 | 官方区分 auto memory 与用户维护的 CLAUDE.md |
| 用户可以要求把内容写入 CLAUDE.md | 成立 | 这是用户授权的载体迁移，不是 memory 自我晋级 |
| 陈旧 memory 可以被更新或删除 | 官方允许用户编辑/删除；社区逆向 prompt 要求更新/删除陈旧项 | 更适合称“维护”，而不是权威退化 |

#### 4.9.1 Claude 实际如何产生类似“晋级”的效果

即使没有等级字段，以下结构仍会让不同 memory 获得不同的实际可见度：

1. **进入或不进入 `MEMORY.md` 索引：** 被索引的主题更容易在会话启动时被看到；未索引专题只能在按需读取时出现。
2. **摘要措辞改变：** LLM 可以把一条模糊观察改写成更明确的说明，但这只是内容变化，不是权威授权。
3. **合并重复主题：** 多条相似观察可被整理成一个稳定主题，减少噪声。
4. **按相关性召回：** 相关任务中读取专题文件，不相关时不读取；这是检索待遇差异。
5. **用户主动迁移：** 用户明确要求写入 `CLAUDE.md` 后，信息离开 auto-memory 角色，成为持久项目指导。

前四项最多提高“更容易被想起、内容更稳定”，不能提高规范权威。第五项才是规则载体变化，而且必须来自用户授权。

#### 4.9.2 Claude 实际如何产生类似“退化”的效果

Claude 不需要先把 `level: 3` 改成 `level: 2` 才能弱化一条记忆。可以直接：

- 从 `MEMORY.md` 删除索引；
- 修改正文，增加条件、时间和例外；
- 用当前信息覆盖旧内容；
- 删除错误或过时的主题文件；
- 在使用时发现冲突，转而信任当前代码或资源；
- 用户关闭 auto memory、要求忽略或手工删除。

这是一种 **离散文件操作 + LLM 语义重写** 的维护模型，不是数据库状态机。

#### 4.9.3 本项目真实样本说明了什么

本机 `C:\Users\juwei\.claude\projects\E--AI-TEST\memory\conversation_local_save.md` 仍保存旧规则“所有技术讨论都要记录”，而当前 `AGENTS.md` 已收窄为“仅 AI Agent 学习内容”。该 memory 没有自动降低置信度，也没有自动删除。

这个反例说明：

- Claude auto-memory 至少不能被假定为持续自动验证；
- 没有字段就无法靠传统查询判断它是否陈旧；
- 是否发现冲突取决于后续 LLM 是否同时看到当前规则并进行比较；
- 若希望可靠退化，需要用户审计、定期整理任务，或自建带元数据的治理层。

#### 4.9.4 最终判断

“记忆晋级/退化”不是完全没有意义，但用于描述 Claude Code 时容易夸大：

> **作为 Claude Code 已公开的产品机制，它更接近一个伪命题——官方没有公开显式权威等级和自动升降状态机。**

> **作为自建记忆系统的工程抽象，它可以有意义——前提是把它明确定义为验证、召回和维护状态，而不是让模型自动获得规则权威。**

对于 Claude Code，建议使用更准确的词：

```text
提取（extract）
索引（index）
召回（recall）
合并/改写（consolidate/rewrite）
陈旧校验（validate for staleness）
删除（delete）
用户授权迁移到项目指导（promote by user governance）
```

### 4.10 用户明确说“记住 X”时实际会发生什么

需要先确认用户想要的持久范围：只在当前会话记住、跨会话作为辅助记忆，还是成为项目长期规则。这三者不是同一种写入。

#### 4.10.1 当前会话记住

如果用户只是说“这次对话里记住 X”，Agent 不需要写文件或调用工具：X 已经存在于当前对话上下文中，后续回合直接引用即可。它会随上下文压缩受到摘要影响，离开会话后也不保证继续存在。

#### 4.10.2 成为项目长期规则

如果用户明确要求“把 X 作为这个项目以后都要遵守的规则”，正确动作是修改 `AGENTS.md`、`CLAUDE.md` 或其他项目治理文件。对当前 Codex 工作环境而言，这是普通、可审计的文件编辑操作，例如通过 `apply_patch` 修改仓库文件，不是写 local memory。

这一步属于用户授权的规则外部化，应展示修改结果；它不会因为被写入 auto-memory 就自动获得规则权威。

#### 4.10.3 Codex local memory

OpenAI 官方文档说明，本地 Codex 客户端可以让当前任务使用既有 memories，或成为未来 memory generation 的输入；生成的内容存放在 `~/.codex/memories/`，并由后台 extraction/consolidation 模型处理。

但官方同时建议把这些文件视为 generated state，不要把手工编辑它们作为主要控制面。因此，从公开资料不能得出“用户说记住 X 后，主 Agent 必定立即调用一个公开 MemoryWriteTool”的结论。

在本次 Codex 会话中：

- 当前可用工具列表没有专门的 `memory_write` / `remember` 工具；
- 本机没有发现 `C:\Users\juwei\.codex\memories`；
- 因此我不能声称能通过产品级 Codex memory tool 将 X 写入跨会话 local memory；
- 如果用户要求持久化，我能明确执行的是写入项目文件；若只要求当前会话记住，则保留在会话上下文。

#### 4.10.4 Claude Code 官方能确认什么

Anthropic 官方文档说明：当用户要求 Claude 记住某件事，例如“always use pnpm”或“API 测试需要本地 Redis”，Claude 会保存到 auto memory。官方还说明 Claude 在会话期间读写 memory 文件，界面会显示 “Writing memory” 或 “Recalled memory”。

但官方文档没有公开底层是否存在一个名为 `MemoryWriteTool` 的专用工具，也没有公开完整工具调用协议。只能确认最终表现为本地 memory 目录中的 Markdown 文件被创建或修改。

#### 4.10.5 参考自 Claude Code 社区逆向工程：是受限的普通文件工具

以下观察来自 `E:\ClaudeCode\claude-code-main`，是 **Claude Code 社区逆向工程复原，不是 Anthropic 官方实现**：

- `src/services/extractMemories/extractMemories.ts` 的 `hasMemoryWritesSince(...)` 会检查 assistant message 中是否存在 `Write`/`Edit` tool use，且目标路径位于 auto-memory 目录；
- 这表示主 Agent 可以通过普通文件 `Write`/`Edit` 工具直接写 memory；
- 后台 extraction agent 也使用普通 `Read`、`Edit`、`Write` 等工具，但传统代码把写权限限制在 memory 目录；
- 如果主 Agent 本轮已经写过 memory，后台提取器会跳过，避免重复写入；
- 界面可以把这种受限文件操作包装成“Writing memory”，但底层不需要一个独立的 MemoryTool。

因此，参考该逆向工程，流程可能是：

```text
用户：“记住以后使用 pnpm”
  ↓
LLM 判断应保存为 feedback/user 类型
  ↓
Read 现有 MEMORY.md / 主题文件
  ↓
Edit 或 Write 主题 Markdown 文件
  ↓
Edit MEMORY.md 索引
  ↓
客户端显示 Writing memory
```

这只是社区逆向工程所呈现的实现，不能表述为 Anthropic 官方源代码事实。

#### 4.10.6 对自建系统的选择

两种实现都可行：

| 实现 | 优点 | 风险/代价 |
|---|---|---|
| 直接给 LLM 普通文件 Write/Edit | 简单；复用现有工具；Markdown 可审计 | 必须严格限制路径；容易格式漂移、并发覆盖 |
| 提供专用 `memory_upsert` 工具 | schema 稳定；容易去重、审计和权限控制 | 需要额外服务和工具实现 |

如果是正式产品，推荐对 LLM 暴露专用工具：

```json
{
  "name": "memory_upsert",
  "arguments": {
    "scope": "user",
    "type": "preference",
    "content": "用户偏好使用 pnpm",
    "source_turn_id": "turn_123"
  }
}
```

工具服务再负责秘密扫描、去重、schema 校验、写文件/数据库和审计。即使底层最终仍写 Markdown，对模型也不必开放任意文件写权限。

一句话总结：

> **在当前 Codex 会话中，我没有专用 memory 工具；持久规则通过普通项目文件编辑保存。Claude Code 官方只确认会写 auto-memory 文件；参考其社区逆向工程，底层是受目录权限约束的普通 Read/Edit/Write 工具，而不是必需的专用 MemoryTool。**

## 5. 冲突处理：不要只做一个静态权威排行榜

### 5.1 先判断冲突类型

| 冲突类型 | 示例 | 推荐处理 |
|---|---|---|
| 指令 vs 指令 | 根目录要求 REST，子目录要求 gRPC | 按产品明确的作用域与优先规则；规则不明确则询问 |
| 指令 vs 当前事实 | 文档写 Node 20，CI 使用 Node 22 | 报告漂移，以当前可验证状态完成诊断，并修正文档 |
| 记忆 vs 当前事实 | memory 记得测试命令已改名 | 重新检查项目文件，不直接采用记忆 |
| 用户猜测 vs 工具证据 | 用户猜测缺索引，执行计划显示另一瓶颈 | 保留猜测的调查价值，以证据决定技术结论 |
| 两份同级规则冲突 | 两个 CLAUDE.md 给出相反要求 | Anthropic 不保证确定覆盖；消除冲突或改用确定性机制 |

### 5.2 “当前代码胜出”也不是无条件规则

当前代码可以证明“现在是什么”，但不能自动证明“应该是什么”。例如代码里存在明文密钥，并不意味着项目规范允许明文密钥。

所以：

- 描述现状时，优先可执行和机器可读证据；
- 判断目标状态时，优先授权明确的需求、规范和架构决策；
- 涉及安全或不可逆动作时，使用权限、审批和验证机制兜底。

### 5.3 高风险冲突应停止并升级

以下情况不应由 Agent 静默猜测：

- 安全策略与用户要求冲突；
- 生产环境事实无法验证；
- 两份项目规范对破坏性操作意见相反；
- 需要把个人偏好升级为团队规则；
- 当前状态显示权威文档可能严重过时。

## 6. 自建治理型记忆系统的参考数据模型

> **性质声明：** 以下字段不是 Claude Code 或 Codex memory 的实际格式，也不应再称为所有系统都需要的“最小模型”。它是一套适合强调审计、验证和规则治理的自建方案。简单的个人辅助记忆完全可以只使用 Markdown 正文和少量 frontmatter。

如果自行开发需要强治理的 Agent 记忆系统，可以记录：

```yaml
id: mem_123
content: "API 测试似乎需要本地 Redis"
kind: observation          # observation | preference | fact | rule_candidate
lifecycle: M2              # 自动记忆只使用 M0–M3；M4/M5 是外部治理载体
source: user_message       # user_message | tool_result | repo_file | model_inference
source_ref: session/turn-42
created_at: 2026-07-14T10:00:00Z
last_verified_at: null
scope: repository          # task | user | directory | repository | organization
valid_until: null
levels:
  importance: I2          # I0–I4：是否值得召回或保留
  confidence: C1          # C0–C4：事实证据强度
  authority: A0           # A0–A4：规范约束力；普通记忆通常为 A0/A1
verification:
  status: unverified       # unverified | verified | contradicted | stale
  evidence: []
governance:
  normative: false
  approved_by: null
  promoted_to: null
```

### 6.1 为什么这些字段重要

- `source` 防止把模型推断伪装成用户事实；
- `lifecycle` 控制该信息只能审计、可以召回、可以有限默认，还是已经迁移到治理/执行层；
- `scope` 防止把个人偏好传播成团队规则；
- `last_verified_at` 与 `valid_until` 暴露陈旧风险；
- `levels` 避免把重要性、事实置信度和规范权威压缩成一个含义不清的总分；
- `verification` 将“记得”与“证实”分开；
- `governance` 将“高置信事实”与“正式规范”分开；
- `promoted_to` 允许追踪规则最终进入了哪个权威载体。

### 6.2 推荐的使用决策

```python
def use_memory(memory, task):
    if not relevant(memory, task):
        return "ignore"

    if memory.verification.status in {"contradicted", "stale"}:
        return "ignore_or_refresh"

    if task.is_high_risk or memory.kind in {"fact", "rule_candidate"}:
        return "verify_before_use"

    return "use_as_hint"
```

不要让 `confidence == C4` 直接触发“升级为项目规则”。规范晋级必须走独立的授权流程：C 轴的上升不能替代 A 轴所要求的授权与治理。

## 7. 载体选择指南

| 内容 | 推荐载体 | 原因 |
|---|---|---|
| 当前任务的一次性限制 | 当前对话/任务状态 | 避免污染长期规则 |
| 跨会话但可变化的偏好或线索 | Auto/local memory | 便于召回，使用前可复核 |
| 团队长期编码约定 | `AGENTS.md` / `CLAUDE.md` / 项目文档 | 可审查、共享、版本化 |
| 架构选择及其理由 | ADR | 保留决策上下文与替代方案 |
| 多步骤、按需加载的工作流 | Skill 或专门操作文档 | 避免主指导文件膨胀 |
| 必须阻止的命令或路径 | 权限、Hook、沙箱、管理策略 | 提供确定性执行 |
| 必须通过的质量门禁 | CI、测试、lint、policy-as-code | 可重复验证，不依赖模型记忆 |

一个实用判断：

> 如果“Agent 忘记或忽略它”会造成严重后果，就不应只依靠 memory 或提示文档。

## 8. 常见误区与修正

### 误区 1：写进 Git 就是真理

修正：入库意味着可治理，不意味着不会过时。应定期用代码和测试检查文档漂移。

### 误区 2：重复验证会让记忆自动晋级

修正：重复验证提高事实置信度；规范权威只能由授权和评审产生。

### 误区 3：CLAUDE.md/AGENTS.md 是硬约束

修正：它们主要是上下文指导。需要确定性时使用产品提供的权限、Hook、沙箱或 CI。

### 误区 4：越近的文件在所有 Agent 中都优先

修正：这是产品特定行为。Codex 官方定义了 AGENTS.md 合并顺序；Claude Code 有自己的加载机制，并明确警告冲突规则可能被任意选择。

### 误区 5：重要信息就应该无条件相信

修正：重要性决定是否保留，置信度决定是否验证，规范权威决定是否作为规则执行。

### 误区 6：摘要和记忆是原始历史的等价替代

修正：两者都是有损表示。精确数值、授权、否定条件和决策理由应回到原始来源核对。

---

## 9. 一份可落地的治理清单

设计或审查 Agent 记忆系统时，逐项确认：

- [ ] 是否记录信息来源与原始证据？
- [ ] 是否区分事实、偏好、观察和规则候选？
- [ ] 是否记录作用域、时间和验证状态？
- [ ] 是否避免把重复次数当成规范授权？
- [ ] 是否有人工审查和晋级目标载体？
- [ ] 是否能发现记忆与当前代码/配置的冲突？
- [ ] 是否允许用户查看、纠正和删除记忆？
- [ ] 是否禁止秘密和高敏感数据进入记忆？
- [ ] 高风险规则是否由确定性机制执行？
- [ ] 是否为过时文档和记忆设计清理流程？

---

## 10. 总结

可以用三句话记住全文：

> **重要性管“要不要想起”；置信度管“要不要验证”；规范权威管“有没有资格成为长期规则”。**

> **重复使用不会让记忆自动变成制度；只有经过授权、审查并写入正确载体，才是真正晋级。**

> **提示文档塑造模型行为，确定性机制约束系统行为。高风险要求必须落到后者。**
