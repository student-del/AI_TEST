# 上下文压缩如何区分信息重要性?——代理信号 vs 显式打分

> 讨论问题:上下文压缩机制里似乎没提"信息重要性等级",压缩时不区分重要程度吗?
>
> 结论:**区分,但不用显式的重要性分数,而用一组零成本的"结构化代理信号"隐式编码重要性;只在最贵的兜底阶段(Auto-Compact / 会话记忆)才用 LLM 做真正的语义重要性判断。** 全程没有 `importance` 数值字段。
>
> 本文是《上下文压缩机制详解.md》与《历史信息重要性分级与动态调整机制.md》之间的桥接说明。
> 更新时间:2026-07-11

---

## 一、核心澄清

压缩管线走的是**范式 A(规则分层)+ 范式 C(LLM 兜底)**,不是**范式 B(连续打分)**。因此它"处处在区分重要性",只是判断依据是类型/位置/时效等**间接代理**,而非给每条消息算一个分数。

## 二、各阶段用的代理信号

| 阶段 | 代理信号(判断"该压谁") | 重要性因子 | 判断类型 |
|------|------------------------|-----------|---------|
| 0 Tool Result Budget | 类型:工具结果先落盘;Read 结果豁免(Infinity) | 来源/角色 | 规则(类型) |
| 1 Snip | 显式低价值:空结果 / 被拒调用 / 已折叠 | 内在重要性 | 规则(二元) |
| 2 Microcompact | 时效:保留最近 5 条,压更旧的(>12) | 时效/引用 | 规则(位置) |
| 3 Context Collapse | 位置:压中部,系统指令层与最近轮次不动 | 结构位置 | 规则(位置) |
| 4 Auto-Compact | LLM 按 9 段模板挑高价值内容 | 语义理解 | 模型(语义) |

**关键点**:前四级是零成本的结构代理;只有第 4 级(及零成本替代路径"会话记忆")做真正的语义重要性筛选。

## 三、唯一的真正语义判断:9 段结构化模板

Auto-Compact / 会话记忆用固定模板,把内容按"重要类别"归档——这张清单本身就是"什么算重要"的定义:

```
Current State / Task Spec / Key Files / Key Functions /
Errors & Fixes / Learnings / Work Log / TODOs / Next Steps
```

重要性在这里被编码成"该进哪个桶",而非数值分数。这是范式 C。

## 四、为什么前几级不用显式重要性分数

**成本权衡。** 给每条消息算真实重要性,要么每轮调 LLM(太贵),要么算并存 embedding(有开销),都违背"廉价压缩"初衷。代理信号的价值在于:**零成本,且与真实重要性高度相关**(工具结果通常确实不如用户约束重要,中部通常确实不如头尾重要)。用便宜代理逼近真实重要性,是整条管线的核心权衡——可逆性梯度(越可逆越先用)是同一逻辑的另一面。

## 五、代价:代理信号的系统性软肋

因为大部分阶段用代理而非真实重要性,经典失败模式是**"真实重要性高、但代理信号低"的信息被误伤**:

| 被误伤的信息 | 为什么代理信号低 |
|-------------|-----------------|
| 早期说过一次的硬约束("别动测试文件") | 位置在中部、非最近轮次 → 被折叠/摘要吞掉 |
| 埋在旧工具结果里的精确配置值 | 工具结果被判低价值 → 被 Microcompact 屏蔽 |
| 决策的"为什么" | 摘要只留"做了什么",理由随中部丢失 |

这正是"压缩五类高危丢失"(精确数值、硬约束、决策理由、跨任务依赖、隐式偏好)的根源——它们共同特征就是**真实重要性高但结构代理信号低**。显式重要性打分(范式 B)本可挽救,但代价太高,工程上改用"代理 + LLM 兜底 + 尽量可逆"来对冲。

## 六、一句话总结

压缩**从不无视重要性**,但它把重要性判断**外包给了廉价的结构代理**(类型/位置/时效/低价值标记),只在最后关头才请 LLM 做一次真正的语义筛选。这套设计在成本上极优,代价是"高价值但不显眼"的信息容易被漏掉——这也是为什么需要跨会话记忆、CLAUDE.md 等**外部持久层**来兜住那些不能丢的硬信息。
