# 模型提问与用户反馈的交互机制

## 结论

“模型提问—用户反馈”不是只有一种实现。主流 Agent 系统至少支持两条路径：

1. **普通对话路径**：模型输出一段自然语言问题并结束当前 assistant turn；用户回答作为下一条 user message，启动新的模型回合。
2. **结构化交互路径**：模型发出专门的用户输入工具调用；Agent runtime 暂停当前运行，在 UI 中展示问题，收到用户答案后将其作为工具结果返回，原 Agent 循环继续。

因此，从用户界面看，两者都像“Agent 问、用户答”；从协议和控制流看，它们明显不同。

## 普通对话路径

典型序列：

```text
Model -> assistant message: “A 与 B 冲突，你希望采用哪一个？”
Agent turn ends
User  -> user message: “采用 A”
New agent/model turn starts
Model -> reads conversation history and continues
```

用户回答的身份是普通 `user` 消息。它与用户主动补充需求没有协议上的本质差异。宿主应用通常只需保存会话历史，然后再次调用模型。

优点是兼容所有聊天界面、支持自由文本；缺点是难以进行结构校验，自动化程序不容易区分“澄清回答”与一条新的普通请求，而且当前 Agent 调用通常已经结束。

## 结构化用户输入工具路径

典型序列：

```text
Model -> tool call: request_user_input / AskUserQuestion
Runtime -> validates tool input and pauses execution
UI -> renders question and choices
User -> selects or enters an answer
Runtime -> tool result containing the answer
Model -> receives tool result and continues the same agent run
```

用户的自然输入先由宿主 UI 收集，再被包装成与该 `tool_call_id` 对应的结果。对模型而言，它通常不是一条无关联的新 user message，而是“此前提问工具调用的返回值”。这使运行时能够可靠地关联问题与答案、验证选项、保持 Agent 状态，并在获得答案后继续原计划。

“同一个 Agent run”不一定表示底层只有一次网络请求。工具型 Agent 本来就是多次模型调用组成的循环：模型请求工具，宿主执行或等待，再把工具结果加入上下文并调用模型继续。所谓暂停和恢复，是运行时/会话层的连续性。

## OpenAI Codex 的公开实现

OpenAI 官方 `openai/codex` 仓库的协议文档公开了以下消息：

- `EventMsg::RequestUserInput`：Codex 向 UI 请求用户输入。
- `Op::UserInputAnswer`：UI 为 `request_user_input` 工具调用提供答案。

这说明 Codex 的结构化提问在协议层被建模为工具调用及其回答，而不只是渲染一条普通 assistant 文本。公开源码相关说明也显示：核心在发出请求后等待响应，回答到达前 turn 保持进行中。不同 Codex surface、协作模式和版本是否开放该工具可能不同；如果工具不可用，Agent 仍可用普通文本问题结束当前回合来询问。

## Anthropic Claude Code 的公开实现

Anthropic 官方将澄清问题建模为内置 `AskUserQuestion` 工具。Claude Agent SDK 文档明确区分：

- 普通对话：Claude 完成一个回合，等待下一条用户消息。
- `AskUserQuestion`：触发 `canUseTool` 回调，Agent 执行暂停，应用展示模型生成的问题和选项，然后将选择返回；回调未返回前可以一直等待。

在 Claude Code 非交互运行中，还可以通过 Hook 返回 `defer`：进程以 `tool_deferred` 停止并保留待处理工具调用，外部 UI 收集答案后用 session ID 恢复，再通过 `updatedInput.answers` 满足原工具调用。这里即使进程暂时退出，逻辑上仍通过持久化会话与工具调用 ID 恢复同一工作流。

## 澄清问题、权限审批与普通反馈的区别

| 类型 | 发起者 | 典型协议 | Agent 是否等待 | 主要用途 |
|---|---|---|---|
| 普通文本提问 | 模型 | assistant message -> user message | 当前回合通常结束 | 开放式讨论、工具不可用时澄清 |
| 结构化澄清 | 模型 | tool call -> tool result | 通常暂停并继续同一 run | 有限选项、需求收集、消歧 |
| 权限审批 | runtime/policy，或由工具动作触发 | approval request -> allow/deny | 暂停危险动作 | 授权命令、写文件、外部副作用 |
| 用户主动反馈 | 用户 | 新 user message / streaming input | 可开启新回合或中断运行 | 改方向、补充上下文、纠正结果 |

权限审批与“模型不知道选哪个”不应混为一谈。前者是安全控制面，即使模型认为应该执行，也可能必须等待批准；后者是认知或需求不确定性，可由模型发起澄清。某些 SDK 会让两者经过同一个回调入口，但工具名、数据结构和处理语义仍不同。

## 工程建议（自拟方案）

1. 有专用交互工具时，用它处理有限选项、不可逆决策和需要与原步骤精确关联的澄清。
2. 需要自由叙述、长文本或复杂谈判时，允许普通对话；不要强行压成几个选项。
3. 每个结构化问题携带稳定的 `question_id` / `tool_call_id`、冲突来源、默认行为和影响摘要。
4. 等待期间不得执行依赖该答案的动作；无回答时默认停止，而不是偷偷选择高风险方案。
5. 将“选择方案”与“授权副作用”拆成两个检查点。例如用户选择生产部署方案，并不自动等于批准真正发布。
6. 恢复时把答案作为原提问的结果关联回去，并记录审计信息；不要只把答案拼成一条无法溯源的文本。
