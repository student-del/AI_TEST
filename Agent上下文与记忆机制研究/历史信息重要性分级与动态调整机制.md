# Code Agent 历史信息与记忆的重要性分级及动态调整机制

> 本报告聚焦一个核心问题：在 Code Agent 与用户的长期协作中，历史信息（对话历史、工具结果、跨会话记忆、指令文件等）体量会不断膨胀，但上下文窗口有限且昂贵。**如何区分这些信息的重要性等级？重要性又如何随时间和使用被提升或降低？** 报告横向对比 Claude Code、OpenAI Codex、Cursor 三大工程化 Code Agent，以及 Generative Agents、MemGPT/Letta、Mem0 三个奠定记忆范式的系统。
>
> 与本仓库已有的《上下文压缩机制详解.md》互补：那份讲"信息超限后怎么压缩"，本份讲"压缩/保留/召回时凭什么判定优先级，以及优先级如何流动"。
>
> 更新时间：2026-07-11

---

## 一、问题定义：什么在"分级"，为什么要分级

### 1.1 历史信息的构成

一个 Code Agent 在运行时，"历史信息"并不是单一的一堆文本，而是异质的多种来源：

| 类别 | 例子 | 天然特征 |
|------|------|---------|
| 系统提示 / 工具定义 | "You are Claude Code..." + 20 种工具 schema | 版本内不变，永远需要 |
| 指令文件 | `CLAUDE.md` / `AGENTS.md` / `.cursor/rules` | 用户手写，稳定，约束性强 |
| 跨会话记忆 | `MEMORY.md`、`~/.codex/memories/` | 跨会话持久，需筛选与老化 |
| 用户消息 | "修复登录 bug"、"不要动测试文件" | 意图与硬约束的载体 |
| 助手中间输出 | 思考、工具调用意图 | 一次性，价值随时间快速衰减 |
| 工具结果 | Read 出的 5000 行文件、Bash 输出 | 体量最大，多为"看一次就不再引用" |

**关键观察**：这些类别的"单位 token 价值"差异巨大。一条 "不要提交到 main 分支" 的用户约束（20 token）远比一次 `ls` 的 3000 token 输出重要。分级的本质，就是为异质信息建立一个可比较的优先级排序。

### 1.2 为什么必须分级

- **窗口有限且昂贵**：即使是 1M token 窗口，长任务也会填满；且 token 越多 API 成本越高。
- **Context Rot（上下文腐烂）**：注意力被摊薄到海量 token 上，旧的无关内容会干扰当前任务，模型表现随上下文增长而下降。压缩/淘汰不只是为了省钱，更是为了保住模型质量。
- **压缩是有损的**：业界反复验证，摘要式压缩最容易丢失五类信息——精确数值、硬约束、决策理由、跨任务依赖、隐式偏好。谁被丢、谁被留，正是重要性分级要回答的。

### 1.3 两个核心子问题

1. **静态分级**：给定一堆历史信息，如何一次性判定各条的重要性等级？（维度、公式、分层）
2. **动态升降**：随着时间流逝、信息被访问/被取代/被反思，重要性如何被提升（promotion）或降低（demotion）乃至遗忘（forgetting）？

下文先建立分级维度框架（第二章），再归纳三种分级范式（第三章），然后逐一剖析业界案例（第四章），最后抽象出统一的升降模型（第五章）与横向对比（第六章）。

## 二、重要性的分级维度：七个正交因子

无论哪家系统，判定一条信息重要性时，实际都是在下面这七个维度上打分或做规则判断。理解这七个维度，就能看懂任何一家的设计。

### 因子 1：来源 / 角色（Provenance）

信息由谁产生，决定了它的基础权重。几乎所有系统都遵循类似的隐含优先级：

```
系统提示/工具定义  >  用户指令文件(CLAUDE.md)  >  用户消息  >  助手输出  >  工具结果
   (永不丢)            (受保护)                (高保留)     (可摘要)    (最先淘汰)
```

Codex 在压缩时"按内容保留用户消息、剥离陈旧的 system/developer 消息"，Claude Code 的"头部保护 + 尾部保护"，本质都是这一维度的规则化。

### 因子 2：时效性（Recency）

越近的信息越可能与当前任务相关。经典建模是**指数衰减**：

```
recency(t) = e^(-λ · Δt)
```

其中 `Δt` 常以"距上次被访问"计（而非距创建），λ 是衰减常数。这直接对应人类记忆的遗忘曲线（Ebbinghaus）。

### 因子 3：相关性（Relevance）

与"当前查询/任务"的语义接近度，通常用 embedding 的**余弦相似度**度量：

```
relevance = cos_sim(embedding(query), embedding(memory))
```

相关性是"按需召回"范式（Cursor 动态发现、Mem0 检索）的核心信号。

### 因子 4：内在重要性（Intrinsic Importance）

信息本身的分量，与时间和查询无关。Generative Agents 用 LLM 打 1–10 分（"刷牙"=1，"分手"=10）。在 Code Agent 语境下，高内在重要性的是：架构决策、硬约束、精确配置值、用户纠正；低的是：一次性的目录列举、临时的探索性读取。

### 因子 5：访问 / 引用频率（Frequency & Reinforcement）

被反复读取或引用的信息更重要。"访问即强化"——每次命中就刷新其 recency 时间戳，从而抬升其综合分数。这是让重要性"能升"的关键机制之一。

### 因子 6：结构位置（Structural Position）

在对话序列中的位置本身携带信息：**头部**（首轮任务定义、系统约束）和**尾部**（模型正在处理的最新几轮）价值最高，**中部**最适合被摘要。这也是"保护头尾、压缩中间"策略的依据。

### 因子 7：可逆性与成本（Reversibility / Cost）

这是一个"元维度"：处置一条信息的动作有多贵、多难撤销，反过来约束了我们敢不敢降它的级。可逆的折叠可以大胆用，不可逆的删除必须谨慎。Claude Code 的整条压缩管线本质就是按这个维度排序的。

### 经典综合公式

Generative Agents 给出了被后续系统广泛沿用的加权求和形式：

```
score = α_recency · recency + α_relevance · relevance + α_importance · importance
       （默认 α = 0.333，等权；实现中通常可配置）
```

这条公式是"打分范式"的数学骨架。工程化 Code Agent 往往不显式算这个连续分数，而是把这些因子固化成**规则分层**（见第三章范式 A）。

### 二·补：两个易混因子深入解析

#### 内在重要性（因子 4）——三轴正交，最易被误杀

内在重要性是信息**本身**的分量，与"何时说的"（recency）、"跟当前任务多相关"（relevance）**正交**。直觉测试：**"若整场对话只能留 10 条事实，这条算不算？"** 算的就是高内在重要性。

| 高内在重要性 | 低内在重要性 |
|-------------|-------------|
| 架构决策、硬约束（"别碰生产库"） | 一次性的 `ls`、探索性读取 |
| 精确配置值（端口、超时、版本） | "好的" / "继续" 之类的确认 |
| 用户纠正（"应该用 POST"）、安全事实 | 中间态思考、临时输出 |

**危险点**：内在重要性**稳定不衰减**。一条会话开头说过一次的硬约束——recency 低、relevance 低，但内在重要性极高。三轴不一致时，压缩的代理信号（时效/位置/类型）会**误杀**它，这正是"五类高危丢失"的根源。

**估算方式（由贵到便宜）**：
1. LLM 显式打分（Generative Agents 的 1–10）——最准，每条一次推理，贵。
2. 启发式——祈使句（must/never/don't）、含数字/配置、错误信息、纠正词（"不对/其实"），零成本近似。
3. 结构代理（类型/角色）——"用户消息 > 工具结果"，便宜但只是统计近似，会错。
4. 类别模板（9 段模板）——枚举"哪些类别值得留"，把"是否属高价值类别"当内在重要性的代理。

**模型到底怎么判断内在重要性？** 先厘清：整条压缩管线里真正"由模型判断"的只有一处——Auto-Compact / 会话记忆提取（及 Generative Agents 打分）；其余大多是 harness 用代理信号近似（上面方式 2/3/4），不是模型在判断。当模型真的判断时，靠三层机制：

- **① 预训练先验（根本来源）**：模型从海量人类文本学到"人类通常把什么当回事"（决策/错误/约束是大事，寒暄是小事）。打 1–10 分本质是一次 next-token 预测，没有独立的"重要性模块"，它在模式匹配"换作人类这里什么重要"。
- **② 提示词条件化 + 模板（把先验聚焦）**：9 段模板预先声明"哪些类别重要"（人设计的先验），模型只需判断具体事实属不属于这些桶、在有限篇幅里够不够显著——重要性判断藏在"写进摘要 vs 略去"这个动作里。
- **③ 内在显著性（最底层信号）**：模型天生对祈使句、否定、数字、命名实体、错误串、用户纠正更敏感；方式 2 的启发式规则其实就是对"模型自身敏感什么"的外部近似。

**本质 = 预训练先验 + 提示词条件化**，非从第一性原理计算，每次都是推理时从 prompt 现算，无持久重要性库。三个推论：(a) 是学来的先验、非保证——反映"人类普遍觉得重要"，通常≈但不总是=当前任务真正重要的；(b) 有损且受篇幅约束——空间紧时低显著性项被丢，误判即漏掉一次性硬约束（硬约束丢失的机制根源）；(c) **可被引导**——`/compact focus on X` 就是在推理时重新加权"模型认为什么重要"，是最实用的杠杆。

#### 可逆性与成本（因子 7）——是"框架"知道，不是"模型"知道

**关键澄清**：处置信息的代价，**不是 LLM 知道，而是框架代码（harness）知道；且大多不是运行时"算出来"，而是工程师设计时"定死"的。** 两个决策者分工不同：

| | 框架代码（harness） | LLM（模型） |
|---|---|---|
| 是什么 | 确定性调度代码 | 做推理的大模型 |
| 管什么 | **何时压、用哪种压缩**（靠成本/可逆性） | **哪些内容进摘要**（靠内在重要性） |

harness 的"代价知识"来自三个确定性来源：

- **① 可数指标（算术）**：token 数（`tokenCountWithEstimation` 精确数）、消息条数、字节偏移——是算术，不是判断。
- **② 静态操作属性（硬编码）**：每个操作可逆吗/要不要额外 API 调用/改不改本地数组，在实现时就定死。折叠保留原数组=可逆；LLM 摘要替换=不可逆；Auto-Compact 发一次 `api.messages.create()`=最贵。工程师从"怎么写这个函数"就知道，无需运行时测。
- **③ 固定顺序 + 硬规则（把成本模型冻进控制流）**：便宜→贵的级联、"每回合最多一次不可逆压缩"、Collapse 与 Auto-Compact 互斥、熔断器（连续失败 3 次禁用）。

最典型的证据是确定性成本收益公式：

```javascript
function shouldMicrocompact(compressionSavings, cacheInvalidationCost) {
  return compressionSavings > cacheInvalidationCost;  // 省的 > 亏的才做
}
```

"删这条 tool_result 会不会让前缀哈希断裂→缓存失效"，harness 从**字节位置**就能算出，全程无 LLM 参与。

**结论**：模型基本**不需要知道**处理代价。代价被工程师提前编码进**管线顺序与规则**这类确定性信号；LLM 只在 Auto-Compact 那一步决定"留什么内容"，而"值不值得付代价来压"是 harness 早已替它算好、定好的。

## 三、三种分级范式

业界对"如何分级"的实现，可归为三种范式。多数系统是它们的混合。

### 范式 A：结构化规则分层（Rule-based Tiering）

按因子 1/6/7（角色、位置、类型）把信息硬性分到不同"层"，每层有固定的处置策略。

- **代表**：Claude Code（头/中/尾 + 工具结果预算 + 折叠层）、MemGPT/Letta（core/recall/archival 三层）、Codex（AGENTS.md / memories / 对话）。
- **优点**：确定性强、可预测、零推理成本。
- **缺点**：粒度粗，无法表达"这条工具结果恰好很关键"。

### 范式 B：连续打分检索（Scored Retrieval）

按第二章公式给每条信息算连续分数，检索时取 top-K 填满上下文。

- **代表**：Generative Agents、Mem0、LangChain `TimeWeightedVectorStoreRetriever`。
- **优点**：粒度细、能表达"重要性梯度"、天然支持动态升降（改分数即可）。
- **缺点**：依赖 embedding 与打分质量，有额外计算/存储；打分错误难排查。

### 范式 C：模型自主判断（Model-in-the-loop）

把"什么重要"交给 LLM 自己决定——自己写摘要、自己编辑记忆、自己决定存什么。

- **代表**：MemGPT 的 self-edit（`core_memory_append/replace`）、Claude Code / Codex 的 LLM 摘要压缩、Cursor Composer 的自摘要。
- **优点**：语义理解强，能保留"决策理由"这类结构化难以捕捉的信息。
- **缺点**：每次判断耗推理 token；是个"黑盒"，摘错了很难追。

> **趋势**：工程化 Code Agent 普遍采用 **A 为骨架 + C 为兜底**：先用廉价的规则分层处理绝大多数情况，只在必须理解语义时（最终压缩、跨会话记忆抽取）才动用 LLM。打分范式 B 更多出现在专门的记忆中间件（Mem0）里。

## 四、业界案例详解

### 4.1 Claude Code：可逆性梯度即重要性降级链

Claude Code 对"会话内历史"和"跨会话记忆"采用两套分级。

#### （1）会话内历史：五段可逆性梯度

其压缩管线本质是一条**按重要性从"最可淘汰"到"最需保留"排序的降级链**，每一级对应一种重要性判断：

| 阶段 | 处置对象（被判为低重要性的） | 可逆性 | 重要性判断依据 |
|------|------------------------------|--------|----------------|
| 0 Tool Result Budget | 超大工具结果 | 可逆（存磁盘留 2KB 预览+路径） | 因子 1（工具结果最低）+ 体量 |
| 1 Snip | 空结果 / 被拒绝的调用轮次 | 不可逆 | 因子 4（内在价值≈0） |
| 2 Microcompact | 累积 >12 条的旧工具结果 | 可逆（`cache_edits` 服务端屏蔽，本地保留） | 因子 2+5（久未引用） |
| 3 Context Collapse | 中部早期对话 | 可逆（折叠视图，原始数据保留，可展开） | 因子 6（中部）+ 2 |
| 4 Auto-Compact | 全量历史 | 上下文层不可逆（LLM 摘要替换） | 兜底，语义理解（范式 C） |

**重要性"降级"的动态过程**：一条工具结果诞生时是 `fresh`（可自由处置），被模型看到后变 `frozen`；随着新结果累积超过 12 条，它被 Microcompact 在服务端屏蔽（重要性降级但仍可逆）；上下文占用破 90% 时，它所在的中部对话被 Context Collapse 折叠成一条"路标"摘要；只有到最后关头才被 Auto-Compact 永久摘要化。

**重要性"提升/恢复"的机制**——这是常被忽略的一面：

- **折叠可展开**：Context Collapse 的阈值是动态的。若后续轮次释放了空间（如 Microcompact 清理了旧结果），折叠范围可缩小甚至完全展开，让模型重新看到被遮住的内容——等于把重要性"升回来"。前提是原始数据从未被物理删除（这正是它保留原始数组的意义）。
- **413 Drain 恢复**：API 报"prompt too long"时，第一级恢复是把待提交的折叠一次性应用释放空间，而非直接丢信息。
- **压缩后重新注入**：Auto-Compact 后会主动"复活"高价值上下文——最近读过的 5 个文件（50K 预算）、活跃技能、plan 文件、CLAUDE.md 全部重新注入。等于压缩时先把它们判为"值得无条件保留"。
- **头尾保护**：首轮任务定义（头）与最近几轮（尾）在整条管线中始终免于压缩（因子 6）。

#### （2）跨会话记忆：分类 + 索引 + 时效校验

Claude Code 的 auto memory 系统（本仓库正在使用）把记忆按**类型**分级，不同类型有不同的读写触发与生命周期：

- **分类即重要性语义**：`user`（用户画像）、`feedback`（纠正与确认，最高价值）、`project`（项目动态，衰减快）、`reference`（外部指针）。`feedback` 类被特别强调"纠正和确认都要记"，因为它直接改变未来行为。
- **索引分层**：`MEMORY.md` 是常驻上下文的**索引**（每条 ~150 字符的钩子），完整内容在各自文件里**按需读取**——这是"渐进式披露"，用极小的常驻成本维持可发现性。
- **动态升降**：
  - *提升*：用户显式要求"记住"→ 立即落盘；某记忆被反复用到 → 其价值被隐性确认。
  - *降低/失效*：报告反复强调"记忆会过时"，使用前必须**回读当前代码/文件校验**（"memory says X exists" ≠ "X exists now"），冲突时**信当下、改记忆**。这是一种"按正确性动态降级"的遗忘机制。
  - *显式遗忘*：用户说"忘掉" → 找到并删除对应条目。
  - *去重合并*：写新记忆前先查是否可更新既有条目，避免重复——类似 Mem0 的 UPDATE 语义。

> Claude Code 的分级哲学：**用可逆性给信息排序，能不删就不删；跨会话记忆则靠分类+索引+时效校验，把"当下是否仍正确"作为重要性的一票否决。**

### 4.2 OpenAI Codex：三层静态优先级 + 记忆老化遗忘

Codex 的分级体现在三个层次，且各有独立的动态机制。

#### （1）AGENTS.md：最高优先级的静态层

- **层级发现**：从 `~/.codex/AGENTS.md`（全局）沿 git 根目录走到当前工作目录，逐级拼接；`AGENTS.override.md` 可就近覆盖。这本身是一种**就近优先**的重要性规则——离当前目录越近的约束越具体、优先级越高。
- **32 KiB 硬上限**：超出静默截断——用容量上限强制"最重要的约束要写在前面"。
- 用户手写、源码控制，Agent 不能自改——最高信任级。

#### （2）Memories：自动生成层的"老化遗忘"

Codex 的跨会话记忆最能体现**重要性随时间衰减直至遗忘**：

- **异步双模型抽取**：会话空闲约 6 小时后才在后台处理；一个模型抽取"值得记的"，另一个把候选合并进既有库——**合并即重要性仲裁**（新事实覆盖旧事实）。
- **老化淘汰（aging）**：最多考虑 256 个近期 rollout；**30 天未被使用的记忆被老化剔除**。这是明确的、基于访问频率（因子 5）的自动降级—遗忘机制。
- **召回方式**：会话启动读 `memory_summary.md` 全文（token 截断），再指示 Agent 对 `MEMORY.md` 做 `grep`——**不是向量检索**，而是"索引全读 + 关键词按需深挖"，与 Claude Code 的索引层思路一致。
- 读/写两个独立开关；内置密钥脱敏。

#### （3）Compaction：按内容而非位置保留

Codex 压缩的分级判断很有代表性：

- **交接式摘要**：提示词是"为另一个将接手任务的 LLM 写一份 handoff 摘要"，要求覆盖进度、关键决策、约束/偏好、剩余任务、关键数据。
- **用户消息按内容保留**：最近的用户消息按 **20K token 预算、由近及远**保留——即用户消息的重要性由"内容+时效"决定，而非固定位置。
- **陈旧 system/developer 消息被剥离**，压缩后重新注入新鲜的初始上下文（权限、环境、指令）。
- **多次压缩的降级警告**："长线程和多次压缩会让模型准确性下降"——承认反复压缩本身是一种质量损耗。

> Codex 的分级哲学：**AGENTS.md 按目录就近定优先级；跨会话记忆用"30 天未用即老化"实现自动遗忘；压缩时用户消息按内容+预算保留，陈旧系统消息直接剥离。**

### 4.3 Cursor：默认不加载，重要性 = 被检索到的相关性

Cursor 的立场最激进：**与其事先判断什么重要，不如默认什么都不加载，让 Agent 按需去取**。

- **动态上下文发现（Dynamic Context Discovery）**：长工具输出、聊天历史、技能、MCP 工具描述、终端会话全部落盘为文件，Agent 用 grep / 语义搜索按需拉取。仅把 MCP 工具"名字"放进常驻上下文，完整描述按需查——实测 **token 减少 46.9%**。这里"重要性"被彻底动态化为"当前是否被检索命中"（因子 3 相关性主导）。
- **摘要前先存全量历史**：总结前把完整对话写入文件，总结后 Agent 仍可搜索该文件找回被压缩掉的细节——用"可召回"对冲有损压缩。
- **Composer 自摘要（训练出来的重要性判断）**：Cursor 在 RL 训练中让模型学会给自己的上下文写摘要，奖励"保留关键信息的好摘要"。结果：摘要约 1000 token（对比提示式基线 5000+），**压缩错误减少约 50%**，token 用量降到 1/5。这是把"什么重要"内化进模型权重——范式 C 的极致。
- **规则分层**：`.cursor/rules/*.mdc` 分级加载——部分永远加载、部分按文件类型自动附加、部分按需，避免上下文膨胀。

> Cursor 的分级哲学：**默认惰性、文件兜底、按需召回；重要性不预先判定，而由"当前是否相关/被检索"实时决定；并把摘要能力训练进模型本身。**

### 4.4 Generative Agents：三因子打分的学术基石

Park 等人 2023 年的 "Generative Agents" 奠定了**打分范式**，几乎所有后续记忆系统都受其影响。

- **记忆流（Memory Stream）**：所有观察、对话、反思按 `ConceptNode` 顺序存储。
- **检索打分**：`score = recency × relevance × importance`（等权，可配）。
  - *recency*：指数衰减，基于 `last_accessed_at`。
  - *relevance*：query 与记忆 embedding 的余弦相似度。
  - *importance*：写入时用 LLM 打 1–10 分（poignancy），一次定分。
- **动态升降的两大机制**：
  - **访问即刷新**：每次读取更新 `last_accessed_at`，recency 被重置抬高——被用到的记忆自动"保鲜"（因子 5 → 因子 2 的联动）。
  - **反思提升（Reflection）**：Agent 周期性地把一堆低层观察提炼成更高层的洞察（reflection），后者作为新的、更高重要性的记忆存入，形成树状结构。这是重要性**主动提升**的典范——碎片信息被"晋升"为结论。

> 学术贡献：**把重要性拆成 recency/relevance/importance 三个可计算因子并加权，且通过"访问刷新"和"反思晋升"让分数动态流动。**

### 4.5 MemGPT / Letta：OS 式分层分页 + 自编辑

MemGPT（现 Letta）把上下文类比操作系统的内存管理，是**范式 A（分层）+ 范式 C（自编辑）**的组合。

- **三层内存**：
  - *Core Memory*（≈RAM，常驻，~500–2000 token）：persona、用户关键事实、当前任务——最高优先级。
  - *Recall / Agent Memory*（≈磁盘缓存，分页进出）：近期对话、工具结果。
  - *Archival Memory*（≈冷存储，向量库）：旧对话、背景事实，语义检索按需调入。
- **动态升降靠 Agent 自编辑**：模型用工具调用主动管理自己的记忆——`core_memory_append/replace`（提升到常驻）、`archival_memory_insert`（降到冷存）。分页系统在上下文满时把旧消息摘要后归档（降级），需要时检索回来（提升）。
- **自省整理（Sleeptime Compute）**：空闲时后台反思、巩固、重组记忆——对应 Generative Agents 的反思机制。
- **已知局限**：**无内置衰减/遗忘**（除非显式驱逐），也**无重要性加权检索**（靠语义相似度）。对比研究型的 FadeMem（长期 β=0.8、短期 β=1.2 的指数衰减曲线）——MemGPT 把"什么重要"完全押注在模型的自我判断上。

> 贡献：**首个把记忆分层+分页做成一等架构，并让 Agent 用工具调用自主决定信息在层间的升降——但缺乏自动遗忘，是"记得太多"的风格。**

### 4.6 Mem0 / 知识图谱类：事实级的覆盖与失效

Mem0 这类外置记忆中间件把重要性管理下沉到**事实（fact）粒度**：

- 每轮对话后抽取事实，与既有记忆比对，执行 **ADD / UPDATE / DELETE** 操作——新事实与旧事实矛盾时，胜出者提升、失效者降级或删除。这是**基于矛盾消解的动态升降**。
- 图 + 向量混合检索，支持关系推理。
- 在压缩把细节丢掉之前，就先把事实抽取落库——用"提前固化"对抗有损压缩。

> 贡献：**把重要性判断做到事实级，用 ADD/UPDATE/DELETE 处理信息的新增、覆盖和失效——最接近数据库式的记忆一致性管理。**

## 五、动态升降机制的统一抽象

抛开各家实现差异，"重要性如何变化"可以统一为一组**提升（Promotion）**与**降低/遗忘（Demotion / Forgetting）**的触发器。

### 5.1 提升（Promotion）：什么让信息变得更重要

| 触发器 | 机制 | 代表系统 |
|--------|------|---------|
| **被访问/引用** | 命中即刷新 recency 时间戳，抬高综合分 | Generative Agents（`last_accessed`）、Codex（用到才不被老化） |
| **被反思提炼** | 碎片观察 → 晋升为高层洞察/结论 | Generative Agents（Reflection）、Letta（Sleeptime） |
| **显式标记** | 用户说"记住"、Agent `core_memory_append` | Claude Code memory、MemGPT |
| **矛盾中胜出** | 新事实覆盖旧事实，成为权威版本 | Mem0（UPDATE）、Codex（memories 合并） |
| **压缩后重注入** | 判定为无条件保留，压缩后主动复活 | Claude Code（文件/技能/CLAUDE.md 重注入） |
| **折叠展开** | 空间释放后恢复被遮住的内容 | Claude Code（Context Collapse 可逆） |

### 5.2 降低 / 遗忘（Demotion / Forgetting）：什么让信息变得不重要

| 触发器 | 机制 | 代表系统 |
|--------|------|---------|
| **时间衰减** | recency 指数衰减，越旧分越低 | Generative Agents、FadeMem |
| **久未访问** | N 天/N 条未被引用则老化剔除 | Codex（30 天老化） |
| **被新信息取代** | 旧事实被 UPDATE/DELETE | Mem0、Codex |
| **超预算被驱逐** | 上下文/记忆满，按低分淘汰 | MemGPT（eviction）、Claude Code（工具结果预算） |
| **可逆折叠/屏蔽** | 中部对话折叠、旧工具结果服务端屏蔽 | Claude Code（Collapse / Microcompact） |
| **时效校验失败** | 与当前代码/事实冲突则失效 | Claude Code memory（stale 校验，信当下） |
| **有损摘要** | 中部历史被 LLM 摘要替换（不可逆） | 各家 Auto-Compact / Compaction |

### 5.3 一个统一视角：重要性是"流动"的，不是"标定"的

最先进系统的共识是：**不要给信息打一个一次性的固定标签，而要让重要性随"时间 × 使用 × 矛盾 × 空间压力"持续流动。**

```
        ┌──────────── 提升触发器 ────────────┐
        │ 被访问 · 被反思 · 显式标记 · 矛盾胜出 │
        ▼                                     │
[低重要性] ⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄⇄ [高重要性]
        │                                     ▲
        │ 时间衰减 · 久未用 · 被取代 · 超预算   │
        └──────────── 降低触发器 ────────────┘
                        │
                        ▼
                  [遗忘/物理删除]  ← 仅当不可逆动作被迫执行
```

可逆性是这套流动的"安全阀"：能用可逆手段（折叠、屏蔽、衰减降分）就绝不用不可逆手段（删除、有损摘要），因为流动要求信息随时可能被重新提升——一旦物理删除，提升路径就断了。

## 六、横向对比总表

| 维度 | Claude Code | OpenAI Codex | Cursor | Generative Agents | MemGPT/Letta | Mem0 |
|------|-------------|--------------|--------|-------------------|--------------|------|
| 主导范式 | A 规则分层 + C 兜底 | A 分层 + C 摘要 | C 自摘要 + 惰性召回 | B 打分检索 | A 分层 + C 自编辑 | B 打分 + 事实覆盖 |
| 会话内分级 | 五段可逆性梯度 | 头尾保护+内容保留 | 落盘按需拉取 | —（模拟为主） | 三层分页 | —（外置） |
| 跨会话记忆分级 | 类型分类(4类)+索引 | AGENTS.md+memories | rules 分层+文件 | 记忆流打分 | core/recall/archival | 事实级 |
| 时效衰减 | 折叠阈值动态 | 30 天老化 | —（惰性即可） | 指数衰减(核心) | 无内置 | 有 |
| 访问强化 | 隐性(重注入) | 用到才不老化 | 检索命中 | `last_accessed`刷新 | 分页调入 | 检索 |
| 提炼晋升 | Auto-Compact 摘要 | 双模型合并 | Composer 自摘要 | Reflection(核心) | Sleeptime | 事实合并 |
| 遗忘机制 | 时效校验+不可逆摘要 | 30 天老化+剥离 | 摘要(可召回) | 衰减出榜 | eviction(弱) | DELETE |
| 召回方式 | 索引+按需读 | grep memories | grep/语义搜索 | 向量+打分 top-K | 向量检索 | 图+向量 |
| 是否物理删原始 | 否(尽量保留) | 会剥离陈旧 | 否(落盘) | 否 | 归档 | 会 DELETE |

**读表要点**：

1. **工程化 Code Agent（左三）都倾向"少删、可逆、按需召回"**，把不可逆的有损摘要留到最后；学术/记忆系统（右三）更依赖连续打分与事实级操作。
2. **"访问即强化 + 久未用即遗忘"是跨系统的最大公约数**——这是让重要性动态化最普适的一对机制。
3. **反思/提炼晋升**（把碎片升级为结论）是高级系统的共同追求，但实现成本高，工程产品多用"压缩时的结构化摘要"近似之。

## 七、对本项目 auto memory 系统的启示

本仓库正在使用 Claude Code 的 auto memory（`MEMORY.md` 索引 + 分类记忆文件）。结合上述业界经验，可考虑的增强方向：

1. **给记忆加轻量元数据**：为每个记忆文件的 frontmatter 增加 `last_accessed` / `access_count` / `importance`，让"访问即强化"和"久未用降权"可落地——目前系统靠"使用前校验"来对冲过时，但缺少显式的时效衰减。
2. **引入老化复审**：借鉴 Codex 的 30 天老化，定期复审 `project` 类（衰减最快）记忆是否仍成立——这类记忆报告已明确指出"decay fast"。
3. **反思式合并**：当同一主题积累多条零散记忆时，主动提炼成一条更高层的结论（Generative Agents 的 Reflection），并在 `MEMORY.md` 索引里替换掉碎片条目，控制索引规模（报告要求 index 200 行内）。
4. **保持"信当下"的一票否决**：现有机制中"记忆与当前代码冲突时信当下、改记忆"是非常正确的遗忘触发器，应继续严格执行——这正是 Mem0 矛盾消解的手工版。

> 核心结论：**本项目的记忆系统已具备"分类分级 + 索引召回 + 时效校验"三要素，最值得补强的是"基于访问频率的自动升降"和"反思式提炼晋升"这两个让重要性真正流动起来的动态机制。**
